### 1. Executive summary (plain language)

The scoring sim did **not** soft-stall or hit a Survival bug. The VPS **ran out of memory**. Linux killed a **Chrome** process that the sim itself had started for headless map screenshots / movement validation. That kill was charged to the **`double-api` systemd service**, which then **restarted**. Restarting the API **did not restart the sim engine**, so status stayed “running / generating” while **no steps advanced** for ~15 hours.

**Primary memory offender:** Playwright **Chromium** (`chrome`) spawned by headless visualization.  
**Amplifier:** no swap; Chrome + 15-agent reverie + API sharing one small cgroup.  
**Secondary failure:** stale meta (`is_generating=true`, `status=running`) with `backend_process_active=false`.


### 5. Root cause statement

**RC1 (direct):** Playwright Chromium (`chrome`), launched by the sim’s headless visualization path, exhausted host RAM on a 3.8 GiB / no-swap VPS.

**RC2 (blast radius):** Chrome ran inside `double-api.service`’s cgroup. OOM → unit failure → API restart → **sim child not respawned** → silent freeze with stale “generating” flags.

**RC3 (config posture):** Production-ish env enables headless movement (`HEADLESS_MOVEMENT_ENABLED=true`). Long scoring runs therefore pay Chrome cost **every step**. Optional `diagnostic_mode` makes this worse (blocking headless + dumps). Deploy docs often show `diagnostic_mode:true` for VPS starts.

**RC4 (observability gap):** `status=running` + `is_generating=true` without requiring `backend_process_active` caused a long false “healthy” window.

### 6. Decisions — never vs manage

#### Never run during long sim generation (this VPS / overnight score runs)

| Item | Why |
|------|-----|
| Playwright / headless Chrome for **generation validation** | **KEEP ON** (product non-negotiable) — make affordable per §12; do not “solve OOM” by disabling the loop |
| Per-step PNG screenshots (`rendered/`) | **DISABLE or sample** on long sprints — not required for legitimacy |
| `diagnostic_mode=true` on multi-thousand-step sprints | **NEVER** — forces blocking extras on top of headless |
| Extra Chromium jobs on the same host (manual browser automation, local FE capture) | **NEVER** concurrent with long sim |
| Relying on “status: running” alone | Lies after OOM restart |

#### Required / keep running

| Item | Why |
|------|-----|
| `reverie` / temp runner | Sim generation itself |
| `double-api` (uvicorn) | Start/stop/status; keep **alive and separate from Chrome fate** |

#### Manage properly (hardening)

| Item | Action |
|------|--------|
| Headless validation | Opt-in only for **short** debug windows; default **off** on VPS score hosts |
| `ENABLE_HEADLESS_VALIDATION` default in `trigger_headless_execution` | Change default to **false** (code fix) so unset env does not spawn Chrome |
| systemd | Consider `MemoryMax` / separate slice for sim vs API; ensure Chrome OOM cannot restart API mid-run — or run reverie **outside** API cgroup |
| Swap | Add **1–2 GiB** swap as last-resort cushion (does not replace turning Chrome off) |
| Day highlights subprocess | Keep fire-and-forget; ensure it does not launch browsers; rate-limit if memory climbs |
| Ops pulse | Alert if `is_generating && !backend_process_active` or `last_generated_at` stale > N minutes |
| Sim logs | Ensure `SIM_LOG_DIR` exists and is discoverable (`./logs/sims/<sim>.log` relative to API cwd) — incident script found **no** sim log under repo root |

### 10. Design confirmation — is headless “core” or “unintended”?

**Product mental model (Ivan):**

```
BE plans movement intent for step N+1
  → FE (headless Phaser) realizes it on the real map (A*, collisions, occupancy)
  → FE reports actual_pos / corrections
  → BE plans N+2 from FE-confirmed coordinates
```

**Verdict: that model matches the Source of Truth and the implementation intent.**

| Source | What it says |
|--------|----------------|
| `sot_realism.md` §Authority + Core Runtime Loop | Backend = intention; **Frontend = spatial realization during generation**; next step plans from **FE actuals**, not BE hope |
| `sot_be-fe.md` | Contract is explicitly `reverie.py` + `headless_visualization.py` ↔ Phaser globals / movement reports |
| `.claude/skills/fe-be-contract` | Same per-step loop; `BACKEND_INTENT_ONLY_PATH=true` ⇒ BE may send empty `path[]` + `target_zone`; **FE owns wall-aware A*** |

So Playwright Chrome on the VPS is **not a random side job**. It is the **server-side way to run the FE half of the designed loop** (Phaser needs a browser runtime).

#### What failed on `20260720-1`

| Question | Answer |
|----------|--------|
| Was Chrome “unintended / should never exist”? | **No** — it is the designed FE executor when headless flags are on |
| Was it outside the core sim process? | **No** — triggered from the reverie step loop every step when `HEADLESS_*` enabled |
| Why OOM then? | **Implementation + host cost of that core path**: Chromium+Phaser (~736 MiB RSS) on a **3.8 GiB / 0 swap** box, inside **`double-api` cgroup**, so OOM restarted API and killed the sim |
| Did `diagnostic_mode` invent Chrome? | **No** — VPS `.env.local` already had `HEADLESS_MOVEMENT_ENABLED=true`, `ENABLE_HEADLESS_VALIDATION=true`, `HEADLESS_BLOCKING_MODE=true`, `HEADLESS_STRICT_MODE=true`. Diagnostic mode would force the same; it was not required for Chrome to run |

#### Inefficiency inside the core path (ops, not “wrong feature”)

- Full Chromium for map A* every step is **heavy** relative to host size.
- Screenshots (`rendered/step-*.png`, ~269 MiB accumulated) add I/O and browser work on top of movement reports.
- Persistent worker + tab reuse exist (`HEADLESS_TAB_REUSE=true` on VPS) — still not enough on 4 GiB with no swap.
- Same-cgroup coupling: Chrome death ⇒ API unit OOM ⇒ sim not respawned.

Turning headless **off** for a long score run is a **temporary ops tradeoff only if product accepts degraded FE confirmation**. **Product decision 2026-07-23: headless ON is non-negotiable** for legitimate Phaser-validated generation. Long-term posture: **keep the BE↔FE loop**, and **make Chromium affordable** (see §12).

### 12. Second look — first principles & efficiency roadmap (2026-07-23)

**Constraint (locked):** Phaser validation must remain in the generation loop. Turning headless off is not the strategy.

#### 12.1 What are we actually trying to achieve?

| Must achieve (legitimacy) | Nice-to-have (debug / marketing) |
|---------------------------|----------------------------------|
| Wall-aware path / blocked handling | PNG of every step (`rendered/step-N.png`) |
| Occupancy / soft-obstacle / claimed tiles | Full Next.js page boot aesthetics |
| Proximity observations for chats | Pixel-perfect match to viewer chrome |
| `actual_pos` writeback for next BE plan | Strict abort on every edge case |

Today we achieve the left column by booting **Chromium + Next + Phaser** every step. That conflates **“run FE spatial algorithms”** with **“run a full browser game.”**

#### 12.2 Prior attempts (already shipped — still not enough for 7k-step / 4 GB)

| When | What | Result |
|------|------|--------|
| Feb 2026 | 100× speed, Phaser.HEADLESS, timeouts | Faster steps; Chrome still heavy |
| Mar 2026 | Persistent Playwright worker (one browser) | No per-step Chromium launch |
| Apr 2026 | StrictMode off / no double-boot in headless | Less FE churn |
| Jun 2026 H0 | Prod `next start` headless build | ~1 s/step vs 10–30 s dev |
| Jun 2026 1.5 | `HEADLESS_TAB_REUSE` | 3×100 parallel soak **PASS** on 3.8 GB |
| Jun 2026 | Cap 3 concurrent sims | Protects parallel, not one long sim |
| Jul 2026 | Single sim × 6860 + PNGs | **OOM** — different failure mode than 3×100 |

Sources: `worklog.md` (2026-02→06), `TODO_mvp-release-gate.md`, `TODO_post_mvp.md` Phase 5, `audit/0.3_HEADLESS-DX-ANALYSIS.md`, this RCA.

#### 12.3 Root inefficiency (with headless ON)

1. **Per-step full-page screenshots are unconditional** in `headless_visualization.py` (~line 1363) — not required for movement legitimacy; drove ~269 MiB `rendered/` + browser paint cost.  
2. **Long-lived Chromium** can grow (tab reuse helps boot cost; does not guarantee flat RSS over thousands of steps).  
3. **Chrome shares `double-api` cgroup** — browser OOM restarts API and orphans the sim.  
4. **No swap** on 3.8 GB host — any spike is fatal.

#### 12.4 Options ranked (keep Phaser validation)

| Tier | Approach | Effort | Keeps Phaser loop? | Stops unbounded growth? |
|------|----------|--------|--------------------|-------------------------|
| **A — Now (ops + tiny code)** | Disable screenshots; add 1–2 GB swap; run **one** long sim at a time; recycle/restart Chromium every N steps (e.g. 500); isolate sim process from API cgroup; stale-gen alert + auto-resume | S–M | Yes | Mostly (ops) |
| **B — Near** | `HEADLESS_SCREENSHOT_EVERY_N=0` default for sprint; forced browser recycle API; MemoryMax; don’t stack trailer capture with sim | M | Yes | Yes on this host class |
| **C — Strategic** | **Phase 5 browser-free realization** (`TODO_post_mvp.md`): extract A*/occupancy/proximity to Node/Python service; Playwright only as **parity oracle** on sample windows | L (4–6 w) | Same *algorithms*; no Chromium in hot path | Best long-term |

**Recommendation:**  
- **Immediate:** Tier A (screenshot off/sample + swap + Chrome recycle + cgroup) so Light finish stays Phaser-validated without another OOM.  
- **Don’t** treat “disable headless” as the product answer.  
- **Plan** Tier C as the elegant end state — we only need spatial realization, not a GPU-less browser painting the village 9000 times.

#### 12.5 Explicit non-goals for efficiency work

- Removing FE authority from SOT  
- Replacing Phaser viewer playback (separate from generation)  
- Keeping every-step PNGs as a generation requirement
