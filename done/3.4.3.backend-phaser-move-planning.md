## ✅ **Backend-Phaser Movement Planning**

### *Goals*
- Restore legacy architecture where backend handles high-level AI intent (e.g., "go to garden") and target zones, while Phaser computes low-level, collision-aware paths using Arcade A* and physics.
- Eliminate backend pathfinding bugs (e.g., invalid waypoints through walls in path_finder.py) by delegating obstacle avoidance to Phaser's native collision system.
- Enable tighter frontend-backend sync via execution reports (actual positions after collisions), supporting spontaneous events and mid-step replanning.
- Maintain realism: 6 tiles/min cap, smooth interpolation, but with dynamic adjustments for interruptions (e.g., chats, obstacles).
- Reduce backend compute: No full A* per step; focus on intent/zone targeting.

### *Architecture Changes*
- **Hybrid Model**: Backend → Intent/Target Zone JSON (no full paths). Frontend Phaser → Local A* path computation + animation. Feedback Loop → Backend via WS/API reports.
- **Authority Split**: Backend owns AI decisions (when/why to move); Frontend owns how (path, collisions, visuals).
- **Data Flow**:
  ```
  Backend (reverie.py) → Intent JSON (target_zone, speed_multiplier, duration) → WS to Frontend
  Frontend (Phaser) → A* Path from current_pos to zone → Tween/Animate with Arcade Collision → Report actual_end_pos + events → WS/API to Backend
  Backend → Receive Report → Update Memory/Next Intent (e.g., replan if blocked)
  ```
- **Step Frequency**: Retain 60s/step for planning (from env `SIM_STEP_LENGTH=60`), but allow mid-step (e.g., 10s) replans on reports (via `step_length` var).

## **MOVEMENT PLANNING & EXECUTION**

*MOVEMENT LOGIC*

a. The backend AI decides where an agent should go (e.g., "head to the garden") and sends simple instructions to the frontend via WebSocket JSON, including the agent's current position, a target area (like a bounding box around the garden), a speed setting (0 for stay still, 1 for normal walk, 1.5 for run), and an estimated time. 
b.1. The frontend receives this and checks: if speed is 0 or no target, the agent idles in place and immediately reports its exact position back. 
b.2. Otherwise, frontend calculates a collision-free path using A* on the map's walls, animates the agent smoothly along the path with Phaser tweens or followers (facing the direction and scaling speed/time), and watches for obstacles:
— if one blocks the way (like a wall or another agent), it pauses, recalculates a detour every 500ms, and resumes; 
- if impossible, it stops at the nearest safe spot and flags it as blocked. 
c. At the step's end (or interruption like chat), the frontend reports the actual final position, travel time, any blocks/deviations, and events back to the backend. 
d. The backend then verifies: if the agent deviated more than 2 tiles or got blocked, it triggers an ad-hoc replan (e.g., shorten the goal or pause for chat), updates the position for continuity, and either starts a mid-step adjustment or waits for the next full 60-second cycle.

### ✅ **Frontend-headless: Coordinate format mismatches and incomplete observation queuing**

### ✅ **Backend: Step 0 Timeout & Validation Mismatches**

**Step 0 Timeout**: Changed the page load strategy from `networkidle` to `domcontentloaded` in `headless_visualization.py`. React applications make continuous background API calls (status polling, file watchers) that prevent the network from ever becoming "idle," causing a 30-second timeout on the first step. The fix loads the DOM quickly (~1s) and then waits for the explicit `window.__headlessReady` signal that the frontend already emits when AnimationManager is initialized.

**Validation Mismatches**: Fixed incorrect position comparison logic that was causing 4 mismatches per step (one per persona). The validation was comparing the `movement` field (which is actually the **start position**) against the actual rendered position. The fix now correctly uses `path[-1]` (the last waypoint) as the expected position—representing where the persona should be after completing this step's movement. Added fallback validation that also accepts positions anywhere along the path within tolerance, ensuring partial movements are validated correctly.

### ✅ **Frontend: Movement Report Position Format Fix**: 
Fixed the `["x", "y"]` string array bug in headless movement reports that was causing 422 API validation errors. The issue had two causes: (1) duplicate entries in `__headlessReports` where AnimationManager pushed properly converted `[number, number]` tile coordinates but then called `originalOnReport`, triggering MainScene to push another entry with raw `{x, y}` pixel objects—which the backend incorrectly converted using `Object.keys()`, and (2) missing format validation for edge cases. The fix adds exhaustive format handling in AnimationManager's headless callback (handles object, array, and fallback formats), adds the `location` field alongside `actual_pos` (both now guaranteed `[number, number]`), removes the `originalOnReport` call in headless mode to prevent duplicates, and updates MainScene to skip its headless handling entirely since AnimationManager now owns all headless report generation with proper pixel-to-tile conversion.
