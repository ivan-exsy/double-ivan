# Optimizing Memory and Planning Modules in the Agent Simulation Architecture

## Current Architecture & Inefficiencies

The agent simulation uses a **memory/retrieval module** and a **planning/reacting module** to create realistic behavior. In the current design, each agent maintains a *memory stream* of experiences in natural language, and a retrieval model finds relevant records by relevance, recency, and importance. The planning module generates a daily plan and detailed actions, while the reacting module handles moment-to-moment decisions and re-planning as needed. This approach succeeds in producing believable, coherent behavior over time, but it is **computationally expensive** and cumbersome:

* **Excessive API Calls:** The code invokes dozens of OpenAI model calls per simulation step – over *50 calls each step* – as it retrieves memories, plans the day, reacts to events, and carries out dialogues. Many of these calls repeat similar context, causing redundant token consumption.
* **Heavy Prompt Payloads:** Each call often includes verbose prompt content like the agent’s full profile, extensive memory snippets, and detailed plan context. This leads to very large prompts (sometimes 500–2000 tokens) for planning and conversations. The same information (e.g. agent’s identity or recent history) may be sent to the model multiple times across different function calls.
* **Memory Bloat:** Every observation, reflection, and plan step is recorded as a new memory entry. Plans are stored in the memory stream as well, which means a long day’s plan (including high-level agenda and recursively broken-down tasks) can create many memory records. Over time this yields significant memory overhead and potential duplication (e.g. routine daily activities being logged every day). Storing every detail as separate entries strains the vector database and increases retrieval workload.
* **Redundant File/Record Creation:** The current implementation logs agent state in a fragmented way – possibly writing out separate files or database records for each sub-component (plans, dialogues, reflections, etc.). This not only duplicates data (since, for example, a planned action will also appear later as an observed memory) but also complicates long-term maintenance with many small records to manage. In short, there is ample opportunity to **simplify and consolidate** how the agent’s state is represented.

The inefficiencies above result in **unnecessary token usage, slower performance, and higher API costs**, without improving the fidelity of the simulation. Below, we propose optimizations to address these issues while preserving the agents’ believable behavior.

## Reducing Prompt Verbosity & Duplication

One clear opportunity is to streamline the prompts sent to the LLM, avoiding repetition and extra verbosity. Optimizing prompt design can significantly cut down tokens and cost. Key strategies include:

* **Cache and Reuse Agent Summaries:** Rather than injecting a full character backstory and motivations into every prompt, maintain a **concise profile summary** for each agent and reuse it across calls. The original architecture already does this by synthesizing an “\[Agent’s Summary Description]” (name, traits, current goals) at intervals and caching it. We should extend this idea – for example, generate the summary once and supply it as a constant system message or prompt prefix for all that agent’s interactions. This eliminates repetitive re-transmission of identity/background text, saving tokens on every call.
* **Trim Down Repeated Context:** Analyze prompt templates to remove any duplicative information. For instance, if the environment description or current time is always provided, ensure it’s brief and provided only once. Static details (like the layout of the town or an agent’s permanent attributes) need not be re-listed in detail each time – they can be referenced abstractly or assumed. The goal is to include *just the necessary context* for the task at hand. Every sentence in the prompt should add new information; anything else can be dropped or replaced with a short placeholder.
* **Batch Related Operations in One Call:** Wherever possible, combine what are currently multiple sequential API calls into a single call. For example, **multi-turn dialogues** between agents can be generated in a joint prompt instead of alternating back-and-forth calls. The original paper suggests batching dialogue generation in a joint prompt to avoid iterative turn-by-turn calls. We can have the model produce a chunk of conversation (several exchanges) in one response, which reduces overhead and ensures consistency. Similarly, the retrieval of related memories can be combined: instead of prompting separately for “relationship with X” and “memory of X doing Y,” a single query prompt could retrieve both types of relevant info in one go. Fewer calls mean less duplicated context and better efficiency.
* **Use Structured Output to Minimize Tokens:** When the task allows, ask the LLM to return information in a compact, structured format (like JSON or a list of key–value pairs) rather than verbose prose. For instance, a daily plan could be returned as a JSON array of {time:…, action:…} entries. This avoids filler words and yields only the essential data. Newer OpenAI models support a `response_format` parameter to guarantee well-formatted JSON output, making this easier. A structured plan output can be shorter (e.g. `"8:00": "Eat breakfast"` instead of *“At 8:00 am the agent will have breakfast”*) and it saves us from lengthy natural-language descriptions that then have to be parsed. The structured approach both cuts token usage and simplifies maintenance (since we don’t need brittle text parsing logic for plans or reflections).
* **Implement Prompt Caching:** Many prompts in the system are similar or identical across time – for example, the morning planning prompt format, or reflection questions that repeat periodically. By caching the model’s outputs for common prompts, the system can reuse results when the same context appears again, instead of calling the API every time. The migration plan provided suggests introducing prompt caching to cut costs by \~75%. Concretely, if an agent’s situation hasn’t changed much since the last plan, we might reuse large parts of the previous plan (or the previous model call’s result) and only update what’s new. Even caching smaller sub-tasks (like the output of a query summarizing a recent conversation) and reusing it within the same agent’s subsequent prompts can eliminate duplicate work. Proper cache invalidation logic would be needed to ensure we update when context truly changes, but many routine computations (like daily routine generation) can likely be reused with minor tweaks.

By tightening and caching prompts in these ways, we **preserve the narrative content** but send far fewer tokens to the model. This directly lowers API costs and latency without sacrificing the quality of the agent’s behavior. Indeed, careful prompt design and reuse can dramatically reduce the runtime cost of each simulation step.

## Efficient Memory Management (Supabase + pgvector)

The agents’ memory storage and retrieval is central to long-term coherence, but it can be optimized for efficiency. The project uses **Supabase with pgvector** as the vector database for memories, which we can tune in several ways:

* **Optimize Embedding Dimensions:** The current system likely uses OpenAI’s `text-embedding-ada-002` (1536-dimensional) for memory vectors. High-dimensional embeddings improve recall, but they carry higher storage and compute costs. We should evaluate if a smaller vector size or a different model suffices, given the domain of simulation. For instance, OpenAI’s newer embedding models or fine-tuned smaller embeddings could achieve similar semantic accuracy with fewer dimensions. As Amazon’s guidelines note, using compact vectors (e.g. 256 or 768 dims) when appropriate can improve performance and memory use, and a well-tuned smaller model can sometimes outperform a larger one for a focused use case. In practice, we could experiment with down-projecting 1536-d vectors via PCA or using a 768-d embedding model and see if relevant memory retrieval remains accurate.
* **Vector Compression (Quantization):** To further reduce the memory footprint, we can store embeddings in compressed form. Vector databases like Qdrant, Milvus, etc., offer options to quantize vectors to lower precision – for example, **8 bits per dimension** instead of 32-bit floats. With product quantization (PQ) or other schemes, memory usage drops dramatically (e.g. 4× smaller) with minimal impact on semantic recall. If pgvector itself doesn’t natively support quantization, we could preprocess embeddings (storing scaled integers) or switch to a vector store that does. The trade-off (a tiny loss in embedding accuracy) is often worth the large savings in space and retrieval speed. This means we can retain a large memory corpus but at a fraction of the RAM/disk cost, which is crucial as agents accumulate memories over long simulations.
* **Deduplicate and Merge Similar Memories:** Human-like agents may experience repeated or very similar events (e.g., *“Every morning John drinks coffee”* each day). Storing each as a separate memory is wasteful. We should implement **duplicate detection** – when adding a new memory, compare its embedding to existing entries. If it’s extremely close to something already stored (cosine similarity above a threshold), we can choose not to insert a new entry, or instead update the existing memory’s metadata (like bump its recency or frequency count). This prevents cluttering the database with near-identical records. In retrieval-augmented systems, redundant text chunks are known to increase storage and even confuse retrieval by returning overlapping results. A good practice is to **avoid redundancy** or filter it out so that the same information isn’t indexed multiple times. For our agents, this might mean only logging *“John has a morning coffee routine”* once, and referencing it, rather than logging “John drank coffee at 8am” every single day. By deduplicating, we cut down the vector count and hence reduce both memory overhead and query load.
* **Intelligent Memory Chunking & Summarization:** The granularity of memory entries can be adjusted for efficiency. Very large memory entries (long paragraphs) are expensive to embed and not always necessary; extremely fine-grained entries (every minute detail) are cheap individually but produce a huge number of vectors. We should find a balance: for example, chunk long experiences (like an hour-long conversation transcript) into smaller thematic pieces before embedding, so retrieval can pull just the relevant piece. Conversely, group very frequent small events into a single summary memory. The system could periodically **summarize recent low-level events** into a higher-level memory (this is akin to the “reflection” mechanism, but we can do it more aggressively for optimization). For instance, after a lengthy conversation, store an overall summary like “Alice and Bob discussed Alice’s upcoming party” instead of dozens of back-and-forth utterances. The detailed transcript could be archived separately or removed from the active memory index after summarization. This kind of **compression of older memories** ensures that the vector index contains mostly succinct, informative items rather than a blow-by-blow log. It aligns with how the original architecture synthesizes higher-level reflections over time – we would simply push this further as a memory optimization technique.
* **Memory Pruning and Importance Filtering:** Building on the above, we can **prune the memory stream** as it grows. Since each memory has an “importance” score in the generative agents architecture, we could decide that when the total number of memories exceeds a threshold, the least important (or very old + low importance + rarely accessed) memories get dropped or archived. This prevents unbounded growth in the vector DB (which would slow down retrieval and increase cost). Importantly, because truly important memories (high score or recently relevant) stay, the agent’s behavior shouldn’t be affected – it might simply “forget” insignificant details just as humans do. Additionally, we can use **metadata filters** during retrieval: e.g., restrict searches to the last X days of memories for everyday questions, to avoid pulling in very old context unless specifically needed. By keeping the active memory set lean and relevant, we not only save on storage but also shorten the retrieved context that goes into prompts (saving tokens).
* **Efficient Indexing:** Ensure the pgvector index is tuned for our usage patterns. For example, using HNSW indexing for similarity search can drastically speed up retrieval with minimal recall loss. Supabase’s pgvector (v0.5+) supports HNSW indexes, which we should enable for the memory table. This improves query latency and reduces the need for workarounds like limiting vector searches too narrowly. Moreover, we should upgrade to the latest pgvector version (0.6+ if possible) to utilize features like parallel indexing builds and other performance improvements. While these index tweaks don’t directly reduce token usage, they **lower the overhead** of memory retrieval operations, making the system faster and more scalable. Fast retrieval also enables us to be more fine-grained (which improves fidelity) without a huge performance penalty.

By applying these memory optimizations, the agent’s long-term memory becomes **more compact, faster, and cheaper** to maintain. We essentially focus the memory store on distinct, meaningful content and leverage database techniques (like vector quantization and indexing) to handle it efficiently. This preserves the agent’s ability to remember relevant facts and events – in fact, it can **improve relevance** by removing noisy duplicates – while cutting down on wasted space and computation. The memory retrieval model will be less distracted by redundant records and can surface the truly important memories more reliably.

## Consolidating Agent State & Simplifying Plan/React Loops

Another area for improvement is the internal architecture of the agent’s planning and reacting cycle. The goal is to **consolidate state and reduce the number of moving parts** so that maintaining the system is easier and fewer resources are wasted on redundant computations.

* **Unified State Representation:** Currently, an agent’s state might be scattered across multiple constructs – e.g. a text file or string for the current plan, a list of recent observations, separate logs for dialogue, etc. This fragmentation can lead to redundant file creation and difficulty in keeping everything in sync. We recommend creating a **single structured state object** for each agent that encapsulates all key information: e.g., current intentions/plan, last known location, active conversation (if any), emotional state, and a pointer to their memory (or recent memory summary). This could be stored as a JSON in the database or an in-memory object, and updated transactionally. By having one unified state, we avoid writing dozens of little files or records – reducing I/O overhead – and it becomes simpler to inspect or reset an agent’s state. The simulation engine can still log events for debugging or analysis, but these logs can be append-only and not constantly read back into the agent loop. In short, **consolidate what can be consolidated** to minimize bookkeeping. This will reduce redundant creation of files/entries and simplify long-term maintenance (fewer components to reconcile).
* **Targeted Plan Updates (Avoid Full Replans):** The planning module should not throw out the baby with the bathwater on every react cycle. The original design allows agents to change their plans mid-stream if needed, but we can make this more efficient by **surgically updating plans** instead of regenerating the entire day’s schedule. For example, if an agent is following a plan and an interruption occurs at 3 PM, we can prompt the model with just “Given the original plan and this new event, adjust the plan from 3 PM onward” rather than re-planning the whole day from scratch. This way, the morning and early afternoon plan (unchanged) doesn’t have to be re-listed in the prompt or re-decided by the model. The architecture discussion indeed suggests re-planning could be done such that only parts that require adjustment are invalidated and updated. Implementing this means keeping the current plan in a data structure, and calling the planner only for the affected time window. It preserves coherence (the agent keeps prior intentions that were not impacted) and saves a lot of tokens. It’s also more realistic: humans don’t rewrite their entire day’s agenda if one meeting runs late; they just shuffle a few things.
* **Separate Reactive Layer for Simple Responses:** Not every observation should trigger a heavy LLM call. We can introduce a lightweight **reactive layer** for trivial or reflex-like responses. For instance, if an agent observes something extremely straightforward (“Your phone is ringing”), we might handle the immediate reaction with a simple rule or a very brief prompt (“Answer the phone”) without involving the full planning prompt with memory retrieval. This idea must be applied carefully to *preserve fidelity* – we don’t want to reduce the richness of agent behavior – but certain things can be seen as “background behaviors”. The original system already had the agent perform routine behaviors (waiting for an occupied bathroom, turning off a burning stove) as part of its logic. We can formalize that: have a set of known high-priority triggers (danger, greetings, etc.) that cause immediate action outputs via a minimal prompt or even deterministic logic. More complex situations would still invoke the full chain of memory retrieval, reflection, etc. This two-tier approach means the **plan/react loop isn’t always invoked for minor events**, reducing the number of expensive calls. The agents remain believable because for anything nuanced, the LLM is still in charge – we’re only short-circuiting truly obvious reactions to save time.
* **Batch Dialogues Between Agents:** When multiple agents converse, we can optimize by generating their dialogue in a batch. Instead of agent A calling the LLM for its line, then agent B calling for a response, and so on (which doubles token usage with repeated shared context), use a single prompt that contains both agents’ perspectives and have the model produce the next exchange or even a few exchanges. One approach: designate one LLM call to handle one round of multi-agent dialogue (possibly by instructing it with both agents’ goals and asking for the dialogue). Another approach is to use a **moderator prompt** that outputs all agents’ lines at once. The original optimization notes mention the possibility of batching dialogue generation to avoid the back-and-forth overhead. By doing this, we cut the prompt duplication (the same situational context doesn’t need to be sent twice for two agents), and we reduce latency. Practically, if two agents are talking, the system could formulate a single ChatGPT prompt like: *“Agent A says X. Agent B will respond. Continue the conversation for one exchange.”* and let the model output both Agent B’s reply and maybe Agent A’s follow-up. This would then be split and fed into the simulation as if they spoke in turns. The conversation remains coherent and dynamic, but we’ve potentially halved the number of API calls and removed redundant context.
* **Maintain Short-Term Context Summaries:** As time progresses, an agent accumulates a lot of context (recent memories, ongoing intentions). Continuously appending all recent observations into prompts will eventually blow up context size. A good practice is to maintain a rolling **summary of recent events** for the agent and use that in prompts instead of raw logs. The system could, for example, summarize the last hour of the agent’s experiences whenever a new planning cycle starts, and use that summary as part of the input (in place of listing all individual observations from that hour). The generative agents paper already did something similar by summarizing the previous day for the next day’s planning prompt. We can do this at a finer grain. This reduces prompt length significantly while preserving the important information. It also helps long-term maintenance: the agent’s state is less cluttered with hundreds of trivial recent-memory entries because they’ve been distilled. In implementation, this might tie into the reflection system – e.g., trigger an automated reflection/summarization step every N game hours to condense recent memory (store that as a memory, and potentially discard or archive the detailed ones). The agent thus carries a **compressed narrative** of its recent past, which is easier (and cheaper) for the model to digest each cycle.

Overall, these measures simplify the **plan-react cycle** and the internal state handling. We cut out redundant recomputation (only update what’s needed), avoid needless file/record churn (by unifying state and summaries), and streamline multi-agent interactions. The result is a loop that achieves the same realistic adaptation to events but with fewer steps and less overhead. This makes the architecture more **robust and easier to maintain**. Future developers can tweak one cohesive state or prompt, rather than managing many interdependent files and prompts, reducing the chance of errors. And importantly, by not overburdening the LLM with repeated or unnecessary context, we keep token usage and costs to a minimum during these cycles.

## Leveraging Modern LLM Features and Tools

Since the original architecture was conceived (circa early 2023), large language model APIs have evolved. We now have new features and patterns – like function calling and long-context models – that can be harnessed to optimize the system further. Adopting these **modern capabilities** can both simplify architecture and reduce token usage:

* **OpenAI Function Calling for Memory and Tools:** One game-changer is the ability for the LLM to call functions during its reasoning. We can expose the agent’s operations (memory retrieve/store, world-actuation functions) as callable functions to the model. For example, define a function `retrieve_memories(agent_name, query)` that, when called, triggers a vector DB lookup and returns relevant memory content. The agent’s prompt can then be much lighter – we don’t manually stuff it with numerous memory records. Instead, the model will **decide when it needs to fetch from memory** and call the function with a query (e.g. “retrieve\_memories(‘John’, ‘relationship with Eddy’)”), at which point our code supplies the answer. This means the model only sees memory information **on demand**, rather than in every prompt. It reduces clutter and ensures the model’s context is focused on what it deems relevant. The same applies to world interactions: e.g., a `move_agent(location)` function or `get_world_state(query)` function could replace verbose descriptions of the environment – the model calls them if needed. Using function calling in this way turns the architecture into more of an *agent with tools* setup. It preserves behavioral fidelity (the model is still driving decisions) but offloads memory searching and state queries to functions. By not pre-loading all possible info, we expect token counts per prompt to drop. This also centralizes certain logic (memory retrieval code resides in one function, rather than being implicitly duplicated in many prompts). Early experiments have shown it’s feasible to give GPT-4 a vector store memory via function calls and have it autonomously store or retrieve memories as needed, which validates this approach.
* **Context-Aware Compression:** We can employ **LLM-based compression** techniques to dynamically shorten context while preserving important content. For instance, before sending an agent’s long memory list to the model, we could prompt a smaller model or use a function to summarize or compress those memory entries *with awareness of the current situation*. Unlike a generic summary, context-aware compression would emphasize details relevant to the agent’s current goal or query. In practice, this might mean having the agent’s LLM (or a helper model) generate a brief synopsis of how recent events relate to the agent’s objectives, and using that synopsis in the prompt. Research on long-context handling suggests using “smart preprocessing” where only the critical parts of a knowledge base or context are kept in detail, and the rest are truncated or abstracted. We can integrate such a pipeline: whenever the context length is about to exceed a threshold, trigger a compression routine that *ranks* information by relevance and compresses less relevant parts (perhaps by converting them into a higher-level statement). For example, if an agent has 30 memories retrieved but we can only fit 10, we might compress clusters of related memories into one sentence each. The model (especially GPT-4) is capable of doing summary with instructions to focus on certain themes. This **compression on the fly** will minimize token usage and avoid prompt overload, especially as simulations scale to longer runs. The key is that it’s *context-aware* – meaning we don’t compress blindly, but guided by what matters now (using either retrieval scores or an importance heuristic). This way, the agent doesn’t lose the thread of important events, and realism is preserved.
* **Retrieval-Aware Memory Writing:** We can also flip things around and make the **memory storage process** aware of future retrieval. When an agent experiences something, instead of always writing a verbose entry, we can tailor the memory entry to be maximally useful for later queries. This could involve tagging it with keywords or metadata (who was involved, what topics, etc.), which pgvector can store alongside the embedding. It could also mean the agent occasionally **writes a summary of an experience for itself**. For example, after a complex event, the agent could produce a reflection like “This event was important because X” and store that, so that future queries surface the reflection rather than a flood of raw observations. Essentially, we encourage the agent to store *knowledge* distilled from experiences, not just raw logs. Modern patterns like this blur the line between memory and knowledge base – the agent builds its own knowledge over time which is easier to retrieve. Additionally, a retrieval-aware strategy might decide **not to store ephemeral data** at all. If something is unlikely to ever be needed (say, the agent looked at a random billboard on the street), we can choose not to record it to conserve space. This requires a heuristic or a learned model of “importance” – which we already have in the form of the importance score from the architecture and could refine further. In summary, by making memory writing smarter, every piece of memory stored has a clear purpose and isn’t just clutter. That improves retrieval quality (less noise) and reduces overhead (fewer total memories). The agent still “remembers” what it needs to, but it forgets or abstracts the rest in a purposeful way (much like human forgetting).
* **Structured Plan and Action Outputs via Functions:** Another use of function calling is to structure how the agent’s actions are produced. We can define functions for actions like `schedule_plan(agent, planJSON)` or `speak(agent, utterance)` that the model can call. Instead of outputting a block of text that we parse into an action, the model would directly invoke the relevant function with structured data. For example, when it’s time to create a daily plan, the model might call `schedule_plan("John", {"8:00":"breakfast", "9:00":"go to work", ...})`. This approach ensures the output is already machine-readable (no parsing needed) and can be shorter because the model isn’t narrating the plan, just providing the key data. OpenAI’s function calling allows the model to autonomously choose these function calls mid-response. By designing our plan-making prompts to encourage function outputs, we both reduce tokens and eliminate a lot of error-handling code. It simplifies maintenance – adding a new type of action is as easy as adding a new function – and it keeps the simulation loop tight (less time spent interpreting the model’s text outputs). This idea is compatible with the *frontend unchanged* requirement, because we’re not altering what the agent does in the world, only how the instructions to do so are generated. The frontend would receive actions in a structured form and execute them just the same.
* **Multiple Model Routing (Cognitive Economy):** To minimize OpenAI API costs, we should use the **right model for each task**. The analysis in the plan suggests using cheaper models for lightweight tasks and reserving GPT-4 only for truly complex reasoning. Concretely, we could use GPT-3.5 or a fine-tuned smaller model for routine tasks like extracting a location name from an observation, simple classification (“is this event surprising?”), or summarizing a short memory. These tasks don’t require the full power (or expense) of GPT-4. Meanwhile, high-level planning, nuanced social dialogue, or intricate reflection might still go to GPT-4 (or a top-tier model) because we want maximum coherence and creativity there. By **routing tasks based on complexity**, we potentially slash token costs without affecting agent realism – the heavy intellectual lifting gets high-quality output, and the grunt work is done cheaply. We can implement this via a dispatcher in code: e.g., if expected tokens < 50 and it’s a straightforward transform, use the 3.5-turbo; if >500 or requires world knowledge, use GPT-4. The project’s cost analysis already moves in this direction by suggesting `gpt-3.5-turbo-instruct` for replacing davinci, a mini GPT-4 for many tasks, etc.. We should continue that trend and keep evaluating new models (including open-source ones) for specific roles. This architectural pattern (sometimes called a “model cascade” or “mixture of experts” approach) ensures we’re not **over-provisioning** intelligence (and cost) where it isn’t needed. As long as the cheaper models are tuned well, the overall agent behavior remains consistent.
* **Utilize Larger Context Windows Judiciously:** Modern GPT-4 versions and other models offer much larger context windows (16k, 32k, even up to 100k tokens). While we don’t want to stuff the prompt with irrelevant info, a larger context window can relieve pressure to prune aggressively. It opens up possibilities like keeping *all* high-relevance memories in context (instead of only the top 5) or including an agent’s entire plan plus relevant memories together. This can preserve fidelity by providing the model a more complete picture of the agent’s state each time it responds, potentially improving coherence over long interactions. For example, we might fit an agent’s multi-day memory summary and today’s detailed plan in one 16k prompt, which ensures the model sees the broader narrative continuity. However, we must balance this with cost – longer context means more tokens per call. A **hybrid approach** is best: use retrieval to narrow down context *and* take advantage of a larger window to avoid dropping borderline-useful info. As one article notes, the future likely lies in combining retrieval augmentation with long-context models. In our case, that might mean we retrieve as normal, but if we have a 32k window, we allow say 20 retrieved memories instead of 10, covering more context for safety. The simulation environment and frontend don’t change; we’re just leveraging a bigger “working memory” for the agent’s brain. This makes the agent less likely to lose track of earlier context, further boosting realism. The bottom line: **where available and affordable, use bigger context models to simplify context management**, but do so in a controlled way that doesn’t re-introduce a token cost problem.

By integrating these modern features, we **future-proof the architecture** and make it more efficient. Function calling and structured outputs modularize the agent’s skills (memory search, action execution) and cut down prompt size. Advanced context management and model routing ensure we’re economical with tokens while still using the best tool for each job. These changes do not alter the visible behavior of agents – they will still remember, plan, react, and converse in a human-like way – but they radically improve the *engine under the hood*. The system will be easier to extend (thanks to function-based design), cheaper to run (fewer and shorter prompts, optimized memory store), and ready to incorporate even newer advancements (like specialized long-term memory modules or knowledge graphs) as they arise.

## Conclusion

In this technical architecture update, we identified the pain points of the current generative agent simulation – namely verbose prompts, redundant context across calls, an ever-growing memory store, and repetitive plan/react cycles leading to excessive token usage and maintenance complexity. We then proposed a series of concrete optimizations to resolve these inefficiencies while *preserving the agents’ behavioral fidelity*. By reducing prompt verbosity and avoiding duplicate information, we immediately cut down the tokens consumed in each interaction (for example, caching the agent’s summary and using joint dialogue prompts removes a lot of repetition). Improving memory management with pgvector (through vector dimension tuning, 8-bit compression, deduplication of entries, and smart chunking) keeps the long-term memory both effective and lightweight. We also restructured parts of the architecture: consolidating agent state into single records and updating plans incrementally yields a cleaner, more maintainable system that avoids constantly reinventing the wheel. Finally, we leveraged modern LLM features like function calling – allowing the model to fetch or store memories when needed – and larger context windows, which together simplify prompt design and cut out unnecessary calls.

Importantly, **the simulation environment and frontend remain unchanged** throughout these optimizations. Agents will still behave in the sandbox world as they always did; all improvements occur behind the scenes in how the AI’s “mind” is implemented. An agent will continue to remember past interactions, reflect on them, plan its day, and react dynamically – but it will now do so with a far leaner use of API calls and tokens. The net effect is a more **efficient and robust architecture**: one that achieves the same groundbreaking realism of the original generative agents, but at a fraction of the runtime cost and with a design that is easier to maintain and extend going forward. By adopting these strategies, developers can sustain long-running agent simulations (or scale up to more agents) without the previous concerns of runaway token budgets or unmanageable complexity, ensuring the project’s longevity and adaptability to future advancements.

These changes align with suggestions from the original authors on caching summaries and partial re-planning, and take advantage of new OpenAI API capabilities introduced after the initial project. The result is a technically sound, cost-efficient evolution of the agent architecture that maintains the rich, emergent behavior that makes these agents compelling.
