## Verification: Phaser Headless Mode

### Official Phaser `HEADLESS` Mode

**Key finding from Phaser API docs:**

> "A Headless Renderer doesn't create either a Canvas or WebGL Renderer. However, it still **absolutely relies on the DOM being present and available**. This mode is **meant for unit testing, not for running Phaser on the server**, which is something you really shouldn't do."
> — Source: Phaser 3 API Documentation (`src/const.js#L73`)

**What it provides:**
- Skips Canvas/WebGL rendering (no visual output)
- Game loop runs via `game.headlessStep(time, delta)`
- Physics (Arcade/Matter) still works
- Tweens still work
- Emits `prerender`/`postrender` events

**Limitation:** Still requires a browser/DOM environment. Cannot run in pure Node.js without polyfills.

---

### Third-Party Solution: `@geckos.io/phaser-on-nodejs`

This package **does provide** true server-side execution:

```javascript
require('@geckos.io/phaser-on-nodejs');
const Phaser = require('phaser');

const config = {
  type: Phaser.HEADLESS,
  width: 800,
  height: 600,
  physics: {
    default: 'arcade',
    arcade: { gravity: { y: 0 } }  // 2D top-down, no gravity
  },
  scene: [SimulationScene]
};

const game = new Phaser.Game(config);
```

**Features supported:**
- ✅ Arcade Physics (collisions, overlap detection)
- ✅ Matter Physics
- ✅ Tweens (position animations)
- ✅ Multiple scenes
- ✅ Adjustable frame rate
- ✅ Pathfinding (via easystar.js or custom A*)

**How it works:**
- Polyfills DOM APIs using `jsdom`
- Polyfills Canvas using `node-canvas` or `@napi-rs/canvas`
- Runs Phaser in headless mode within Node.js

### Comparison: Current vs. Alternative Approach

| Aspect | Current (Playwright + Browser) | `phaser-on-nodejs` |
|--------|--------------------------------|-------------------|
| **Setup complexity** | High (Chromium, page navigation, wait loops) | Low (npm install, require) |
| **Execution time/step** | ~60-70s (real-time animation) | <1s (can skip to final position) |
| **DOM dependency** | Full browser | jsdom polyfill |
| **Race conditions** | Many (browser load, React mount, etc.) | Few (synchronous control) |
| **Memory footprint** | ~200MB+ (Chromium) | ~50MB (Node.js) |
| **A* Pathfinding** | Your existing code works | Same code works |
| **Collision detection** | Arcade Physics | Arcade Physics |
| **Coordinate conversion** | Still needed | Still needed |

---

### Verdict

**Yes, there is a straightforward solution**, but with caveats:

1. **`Phaser.HEADLESS`** alone is **not** enough — it still needs a browser/DOM
2. **`@geckos.io/phaser-on-nodejs`** enables true server-side execution and would eliminate:
   - All Playwright coordination
   - Browser launch/navigation overhead
   - Most race conditions

3. **However**, you would still need:
   - The A* pathfinding code (already written in `AnimationManager.ts`)
   - Coordinate conversion (tiles ↔ pixels)
   - JSON schema alignment between backend/frontend

### Recommendation

If considering a refactor, the `phaser-on-nodejs` approach would simplify architecture significantly. The key change would be:

```
Before: Backend → Playwright → Browser → Phaser → Window globals → Backend
After:  Backend → Node.js Phaser instance → Direct function calls → Backend
```

This eliminates the entire browser coordination layer while keeping your existing A* and physics logic intact.

## Risk Assessment

### High Risks

1. **Tilemap/Collision Layer Loading**
   - Current code uses Phaser's `map.createLayer()` and `getTileAt()`
   - In Node.js, no WebGL/Canvas context — may need to parse JSON directly
   - **Mitigation:** POC Phase 1 must verify collision detection works

2. **Position Drift Between Server and Frontend**
   - Server calculates position; frontend animates visually
   - Risk of mismatch if frontend tweens differ from server calculations
   - **Mitigation:** Use server positions as source of truth; frontend interpolates

3. **Library Maintenance/Support**
   - `@geckos.io/phaser-on-nodejs` is community-maintained
   - Breaking changes in Phaser updates could cause issues
   - **Mitigation:** Pin versions; maintain fork if needed

### Medium Risks

4. **Testing Completeness**
   - Need to verify all edge cases work identically
   - Blocked paths, speed=0 stationary, interruptions
   - **Mitigation:** Port existing test cases; add new ones

5. **Deployment Complexity**
   - New service means new container, port, health checks
   - **Mitigation:** Containerize early; use existing infrastructure patterns

### Low Risks

6. **A* Pathfinding Logic**
   - Already implemented in `AnimationManager.ts`
   - Pure TypeScript, no DOM dependencies
   - Should port with minimal changes

- ✅ Memory constraints matter (removing Chromium saves 200MB+)
- ✅ Debugging headless issues has consumed significant time
- ✅ Team has Node.js deployment experience

### Keep Current If:

- ✅ Current implementation is "good enough" and stable
- ✅ Short-term deadlines preclude multi-week refactor
- ✅ Visual validation in headless (screenshots) is important
- ✅ No confidence in `phaser-on-nodejs` stability
- ✅ Limited bandwidth to maintain additional service
