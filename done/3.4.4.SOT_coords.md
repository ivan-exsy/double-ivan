# <OPUS 4.5 Analysis: Reality-Grid as Single Source of Truth>

After analyzing your architecture, I'll assess the "reality-grid" concept against your stated goals. **The core insight: a pixel-level unified grid is architecturally sound but introduces unnecessary complexity. A tile-level sparse object registry achieves the same goals with 90% less storage and better LLM token efficiency.**

---

## Current State Analysis

Your system already has a fragmented but functional approach:

| Component | Storage | Format | Used By |
|-----------|---------|--------|---------|
| Static map | CSVs (`collision_maze.csv`, `sector_maze.csv`) | 140×100 tile IDs | Backend pathfinding, Frontend Easystar |
| Movable objects | Memory events (`add_event_from_tile`) | Sparse events in `a_mem` | AI planning (retrieved via RIR) |
| Sprite positions | `movement/{n}.json` | Per-step tile coords | Frontend rendering, Backend continuity |
| Visual assets | Tiled JSON + PNGs | Layered tilemap | Frontend Phaser only |

**Key Problem**: Object relocations (teapot example) exist as memory events, not as queryable spatial state. AI must *retrieve* memories to know "what's at this tile"—expensive and unreliable for dense scenes.

---

## Reality-Grid Assessment

### Option A: Pixel-Level Dense Grid (Your Initial Thought)

```
140×100 tiles × 32×32 pixels = 4480×3200 = 14.3M cells
```

**Problems**:
1. **Storage bloat**: Even with sparse encoding, tracking pixel positions for ~50 objects = negligible benefit over tile-level
2. **AI irrelevance**: LLMs don't reason about pixels—they reason about "teapot on bedroom table"
3. **Sync complexity**: Sub-tile precision creates rounding drift between backend/frontend
4. **No Phaser benefit**: Phaser already handles pixel interpolation from tile coords

**Verdict**: ❌ Over-engineered for your use case

### Option B: Tile-Level Sparse Object Registry (Recommended)

A single authoritative data structure tracking **what exists at each tile**:

```typescript
// Conceptual schema (stored as JSON or Supabase table)
interface RealityGrid {
  static_layer: TileID[][];           // 140×100 immutable (buildings, walls)
  objects: Map<TileCoord, ObjectRef[]>; // Sparse: only tiles with objects
  sprites: Map<PersonaName, TileCoord>; // Current positions
  version: number;                      // For optimistic locking
}

interface ObjectRef {
  id: string;           // "teapot_001"
  type: "portable" | "fixed";
  owner?: string;       // "Ivan" if carried
  placed_at?: string;   // "bedroom:table" semantic address
}
```

**Benefits**:
1. **Token efficiency**: AI prompt includes `objects_at_location: ["teapot_001"]` instead of retrieving memories
2. **Deterministic sync**: Backend writes, frontend reads—no reconciliation
3. **Playback-ready**: Each step stores delta (object moves), reconstructible for any step
4. **Supabase-native**: Single `reality_state` table with JSONB column, RLS-secured

## Feasibility Analysis

### Goal 1: Backend Scenario Generation
**Current**: AI retrieves object locations via memory queries (expensive, ~500 tokens/query)
**With Reality-Grid**: Direct lookup `grid.objects.get(curr_tile)` → inject into prompt as structured data

```python
# execute.py enhancement
def get_tile_context(tile: Tuple[int, int]) -> dict:
    """Returns all objects/agents at or near tile for AI context."""
    return {
        "objects_here": reality_grid.objects.get(tile, []),
        "nearby_agents": [p for p in reality_grid.sprites if distance(p, tile) < 5],
        "zone": reality_grid.static_layer[tile[1]][tile[0]]  # sector name
    }
```

**Token savings**: ~40% reduction in perceive/retrieve by replacing memory queries with structured context.

### Goal 2: Frontend Change Reporting
**Current**: Frontend detects collisions/proximity → POST to `/observations`
**With Reality-Grid**: Frontend reports object interactions as grid mutations

```typescript
// Frontend mutation report
POST /api/simulations/{sim}/grid/mutations
{
  "step": 15,
  "mutations": [
    { "type": "object_move", "id": "teapot_001", "from": [50,12], "to": [73,16] },
    { "type": "sprite_pos", "persona": "Ivan", "tile": [73,16] }
  ]
}
```

Backend applies mutations atomically, broadcasts via WebSocket.

### Goal 3: Playback Reference
**Current**: Reconstruct from `movement/{n}.json` + memory events (lossy for objects)
**With Reality-Grid**: Store deltas per step, reconstruct any state:

```json
// storage/{sim}/grid_deltas/{step}.json
{
  "step": 15,
  "mutations": [...],
  "snapshot_hash": "abc123"  // For validation
}
```

Playback: Load base grid → apply deltas 0..N → exact state at step N.

## Implementation Recommendation

### Phase 1: Tile-Level Object Registry (MVP)
1. **New file**: `storage/{sim}/reality_grid.json` (single source)
2. **Backend**: `maze.py` loads/saves grid; `execute.py` injects into AI context
3. **Frontend**: Fetches grid on load; reports mutations via existing observation endpoint

### Phase 2: Supabase Migration (Production)
```sql
CREATE TABLE reality_grid (
  sim_code TEXT PRIMARY KEY,
  static_layer JSONB NOT NULL,      -- Immutable base map
  objects JSONB DEFAULT '{}',       -- Sparse object positions
  sprites JSONB DEFAULT '{}',       -- Current persona positions
  version INT DEFAULT 0,
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Per-step deltas for playback
CREATE TABLE grid_deltas (
  sim_code TEXT,
  step INT,
  mutations JSONB NOT NULL,
  PRIMARY KEY (sim_code, step)
);
```

### Phase 3: Real-time Sync
- Backend writes to Supabase on step completion
- Frontend subscribes to `reality_grid` changes via Supabase Realtime
- Eliminates polling; sub-100ms sync

## **1. Maze as a single source of truth**

### *1. Unified Maze/Tile Map Format (CSV vs. JSON)*

**Context**: Backend AI prefers CSV for precise, computable grids (e.g., collision_maze.csv for pathfinding arrays). Frontend Phaser prefers JSON for rich, layered tilemaps (Tiled exports with visuals, collision properties). Unification needed to avoid duplication/sync issues in Supabase migration.

#### **Key Differences**
- **CSV (AI/Backend Preferred)**:
  - Format: Flat 2D arrays (e.g., collision_maze.csv: 140x100 rows of IDs/0s for walls; sector_maze.csv: IDs mapping to names like "Hobbs Cafe").
  - Pros: Simple, fast NumPy loads; exact for backend pathfinding (path_finder.py uses arrays); no hierarchy overhead.
  - Cons: No built-in layers (visuals/physics separate); manual ID→name mapping (special_blocks.csv); harder for Phaser rendering.
  - Usage: Backend (maze.py ~135-149: loads CSVs → address_tiles dict); AI prompts reference textual names (e.g., "dorm table").

- **JSON (Phaser/Frontend Preferred)**:
  - Format: Hierarchical Tiled export (e.g., the_ville.json: layers for collision {collide: true}, objects, tilesets like interiors.png).
  - Pros: Rich metadata (tilesets, properties for Arcade physics); direct Phaser load (TilemapParser); supports dynamic objects/layers.
  - Cons: Larger, slower parse; backend must flatten to arrays (no native NumPy grid); version sync issues (e.g., .tmx → JSON conversion).
  - Usage: Frontend (main_script.html: Phaser.Tilemaps.Parsers.Tiled); loads full map for A* (Easystar on JSON collision layer).

#### *Trade-offs & Challenges*
- **Sync Issues**: CSV lacks visuals (separate PNGs); JSON lacks direct arrays (requires parsing to grid). Current hybrid: Backend CSVs from Tiled (static export); Phaser JSON (visuals). Mismatches cause stalls (e.g., backend valid path → frontend collision reject).
- **Performance**: CSV faster for backend (NumPy arrays); JSON better for Phaser (native layers). Unification adds conversion overhead (~100ms load).
- **Dynamic Updates**: Movables (e.g., teapot relocation) are event-based (memory/events, not map-altering); neither format stores runtime state—JSON could add "events" layer, but CSV simpler for static base.
- **Supabase Fit**: JSON easier (single file upload); CSV suits bulk (e.g., collision_maze.csv as blob). Both storable; derive one from other via script.

#### *Recommendation: Unified JSON (Phaser as Master) - <VALIDATE>*
- **Why JSON?**: Single source (Tiled export → shared Supabase "simulation_maps" bucket); Phaser loads directly (no CSV parse); backend converts JSON layers to arrays (add to maze.py: json_to_grid parser, ~50 lines).
- **How**: Export Tiled map as JSON (visuals/collision/objects); backend: Load JSON → extract collision layer to NumPy array (e.g., [y][x] from data/width). Store one JSON per sim variant (e.g., the_ville.json); no full dup (static base + runtime overlays).

#### *Current: Static vs. Dynamic Assets (Movable Objects)*
Yes, possible. Maze is static (fixed buildings/roads in CSVs—no updates). Movable objects (e.g., teapot) are dynamic but **not altering the tile map**:
- **Static**: Immutable (collision/sector/arena CSVs define fixed layout; e.g., kitchen tiles always collide as "kitchen").
- **Dynamic (Movables)**: Handled as runtime events, not physical map changes. AI tracks via:
  - **Persona Memory**: Spatial memory (s_mem in persona.py) stores object positions as events (e.g., "teapot at [x,y]" via add_event_from_tile in maze.py ~509).   - **Runtime State**: Per-step in movement/{n}.json (partial_state tracks positions; no CSV updates). Frontend sprites may visualize (e.g., teapot sprite moves via Phaser), but backend maze remains fixed—AI uses memory/events for "where is teapot?" queries (e.g., in _should_react for interactions).
  - **AI Handling**: GPT prompts include memory (curr_event in plan.py), so agents "know" via retrieved events (e.g., "Ivan recalls teapot in bedroom"). No tile map mutation—events overlay static grid (e.g., teapot event at bedroom tile triggers "pick up" in perceive/retrieve).

## **4. Unified Coord System for back and front: tiles vs. pixels**

- **Primary**: Tiles (discrete integers, e.g., [50,12] on 140x100 grid). Backend AI/planning uses natively (pathfinding, events, proximity in maze.py/execute.py). Frontend state/reports use tiles exclusively (JSON/WS payloads).
- **Rendering Layer**: Pixels derived on-the-fly (tile * 32 + 16 for Phaser sprites/tweens). No storage/sync in pixels—convert once per render (e.g., CoordinateAdapter.ts: tileToPixelCenter).
- **Rationale**: Eliminates conversion errors (floor/ceil drifts); simplifies sync (exact tile matches in reports); backend-native for grids/A*. Frontend handles pixel visuals without altering SOT.

### *Maze as Single Source of Truth*
- **Centralized**: maze.py (backend) loads CSVs (collision/sector/arena/game_object_maze.csv) and JSON (Tiled exports) from shared Supabase bucket ("simulation_maps"). Builds authoritative `address_tiles` dict (tile coords → addresses) and `zones` bbox (for intents).
- **Shared Access**: Frontend fetches same assets (Supabase public read); parses for Phaser Tilemaps (JSON) and Easystar grid (CSV collision_maze). Backend exposes via API (e.g., /maze/{name}/tiles endpoint for coords).
- **Dynamic Overlays**: Static maze fixed (no per-sim dup); movables/events tracked runtime (memory/JSON, not grids—e.g., teapot relocation via add_event_from_tile, no CSV mutation).
- **Rationale**: One authoritative map per sim type (e.g., "the_ville"); avoids dup (shared bucket); ensures consistency (backend validates, frontend renders). Fallback: Local files if Supabase down.
