## 1) Problem Statement

Current simulation steps process personas mostly sequentially. With 4 sprites, step time can exceed 70s and LLM time alone can exceed 40s. This does not scale linearly for larger simulations.

Goal: parallelize LLM-heavy per-persona work within a step while preserving:
- context integrity,
- social realism/naturalness,
- deterministic replay behavior,
- Supabase SOT guarantees.

---

## 2) Non-Negotiable Invariants

1. **Supabase remains SOT** for coordinates/memory/scratch contracts.
2. **Step determinism** is preserved:
   - same seed + same inputs -> same step output.
3. **Observation-first chat behavior** remains intact.
4. **No silent fallback**:
   - any degraded mode logs explicit reason.
5. **Commit order stays deterministic** even if compute is parallel.
6. **Easy rollback** by feature flag to current sequential flow.

---

## 3) Current Bottlenecks (Observed)

1. Persona loop in `reverie.py` is sequential.
2. Each persona executes synchronous cognitive chain in `persona.move()`.
3. Reflection and chat generation can trigger high LLM call fan-out.
4. Router/global cache/metrics objects currently rely on shared mutable state.
5. Headless validation is a separate large fixed cost.

---

## 4) Target Execution Model

Adopt a **3-stage step model**:

1. **Stage A: Serial Pre-Step Gate (authoritative)**
   - Process observations
   - Apply chat/proximity gates/cooldowns
   - Freeze snapshot for step planning

2. **Stage B: Parallel Intent Compute (read-only world snapshot)**
   - Per-persona LLM-heavy cognition runs concurrently
   - No direct mutation of shared world maps/tables
   - Produce candidate intent/movement/action package

3. **Stage C: Serial Deterministic Commit**
   - Resolve conflicts and apply to canonical step state in stable order
   - Write Supabase + movement payloads once
   - Preserve current replay/headless contract

This model gives speedup without losing causality control.

## 5) Implementation Phases (Step-by-Step)

### v0.2 P1 Delta (Backlog Alignment)

Add the following P1 scope before enabling `active` mode rollout.

1. **Low-risk LLM batching (strict-contract paths only)**
   - Scope: batch only deterministic, schema-strict evaluations (poignancy/insight families).
   - Input policy: build batches from a stable sorted key `(persona_id, step, eval_type, item_hash)`.
   - Output policy: validate each batched item against existing response schema before commit.
   - Fallback: if batch-level or item-level validation fails, retry only failed items with current single-call path and log `BATCH_FALLBACK_REASON`.

2. **Task decomposition gate (boundary/context-change only)**
   - Run decomposition only when one of these is true:
     - current action reaches a real boundary (`completed`, `blocked`, `invalidated`);
     - meaningful context delta appears (new social interaction, priority event, or goal-location mismatch).
   - Skip decomposition when current action remains coherent and context is materially unchanged.
   - Emit deterministic diagnostics per persona-step:
     - `DECOMP_GATE=RUN|SKIP`
     - `DECOMP_REASON=<stable reason code>`.

3. **Async reflection write queue (bounded lag)**
   - Move non-blocking reflection persistence to an async queue keyed by `(simulation_id, persona_id, source_step, reflection_hash)`.
   - Keep lag bounded to 1-2 steps:
     - drain queued writes each step before final commit closeout,
     - if queue lag exceeds 2 steps, force synchronous flush and raise `REFLECTION_LAG_GUARD`.
   - Guarantee idempotent writes and explicit degraded-mode logging on flush failure.

4. **P1 Delta release gates**
   - Heavy-window A/B run shows additional reduction in LLM-heavy step time with no determinism regressions.
   - Decomposition invocation rate drops on stationary/routine windows without schedule-coherence regression.
   - Reflection queue lag p95 stays <= 2 steps with no missing persisted reflections.

5. **Approved execution defaults (2026-02-23)**
   - Rollout mode: `shadow` first; do not start in `active`.
   - Worker cap policy: high parallelism per step (per-sprite target worker allocation).
   - Determinism gate: zero-tolerance for output drift in shadow compare runs.
   - Batch fallback: retry failed items singly; do not fail entire step for partial batch errors.
   - Reflection lag guard: if lag exceeds 2 steps, force synchronous flush (`REFLECTION_LAG_GUARD`).
   - Go/No-Go priority: correctness first (determinism + data integrity), then performance.

## Phase 1 - Step Snapshot Contract

1. Introduce an immutable `StepSnapshot` object built once per step:
   - persona states (time, current pos, action summary),
   - relevant world tiles/occupancy,
   - chat/cooldown state,
   - observation outcomes.
2. Ensure Stage B workers read only `StepSnapshot`.
3. Remove hidden reads from mutable globals in parallel path.

Deliverable: deterministic, serializable snapshot structure.

---

## Phase 2 - Worker Result Contract

1. Define `PersonaIntentResult` schema:
   - persona name/id,
   - chosen action/address,
   - candidate movement/path,
   - chat intent metadata (if any),
   - diagnostics (llm calls, latency, retries),
   - conflict hints.
2. Ensure result has enough detail for serial Stage C conflict resolution.
3. Add strict validation before commit.

Deliverable: stable interface between parallel compute and serial commit.

---

## Phase 3 - Concurrency-Safe LLM/Router Layer

1. Audit shared mutable state in model routing/logging/caching.
2. Refactor to one of:
   - worker-local accumulators + end-step merge (preferred),
   - or lock-protected shared state where unavoidable.
3. Enforce per-step quota decisions (Tier C etc.) in deterministic fashion:
   - reserve budget in serial pre-allocation, or
   - centralized atomic allocator with deterministic tie-break.
4. Preserve current compact metrics logs.

Deliverable: thread-safe, reproducible routing and telemetry.

---

## Phase 4 - Parallel Compute Engine

1. Add bounded worker pool (thread/process depending on profiling).
2. Submit per-persona Stage B tasks from a stable sorted persona list.
3. Add global step timeout + per-task timeout.
4. Add cancellation/fallback policy:
   - timed-out persona -> safe sequential retry or failsafe action.
5. Keep `shadow` mode first:
   - run parallel compute but do not commit,
   - compare with sequential output for divergence tracking.

Deliverable: controlled parallel engine with observability and safe fallback.

---

## Phase 5 - Serial Deterministic Commit and Conflict Resolver

1. Commit order: sorted stable key (persona_name).
2. Resolve conflicts deterministically:
   - tile contention,
   - object/action contention,
   - simultaneous chat intent collisions.
3. Preserve chat system invariants:
   - pair cooldown,
   - active conversation constraints,
   - first-daily-encounter behavior.
4. Write one authoritative movement state per persona per step.

Deliverable: deterministic outcomes regardless of worker completion order.

---

## Phase 6 - Supabase Safety Hardening

1. Add explicit write strategy for step commit:
   - staged in-memory commit list -> controlled Supabase write batch.
2. Add idempotency keys:
   - `(simulation_id, step, persona_id, write_type)`.
3. Add duplicate-write protection and upsert semantics where applicable.
4. Add strict error classes:
   - transient (retry with backoff),
   - permanent (mark step degraded and halt/rollback policy).
5. Add read-after-write verification sample checks:
   - coordinates and critical scratch fields.
6. Add write queue depth and latency metrics.

Deliverable: Supabase-safe parallel architecture with controlled commit path.

## 6) Risk Register (Including Supabase)

| Risk | Impact | Probability | Mitigation |
|---|---|---|---|
| Shared mutable router/cache state causes race | High | High | Worker-local state + deterministic merge; lock minimal shared paths |
| Nondeterministic commits from unordered futures | High | Medium | Stable sort commit order + deterministic conflict rules |
| Chat realism degrades (too many/too few chats) | High | Medium | Keep observation-first gates serial; run behavior A/B validation |
| Supabase connection pool saturation | High | Medium | Bounded commit concurrency, pooled client config, backpressure |
| Supabase write contention/row lock conflicts | High | Medium | Single serial commit stage for SOT rows; retry transient errors |
| Duplicate writes for same persona-step | Medium | Medium | Idempotency keys + upsert guards + post-write checks |
| Partial step persistence (some personas missing) | High | Medium | Transaction-like step commit policy + degraded-step marker + retry |
| Read-after-write stale data | Medium | Medium | Sample verification reads + delayed consistency handling |
| RLS/policy regressions under new write paths | High | Low-Med | Validate service-role path, explicit policy tests in staging |
| Latency improves but total cost spikes | Medium | Medium | Keep tier quotas and token guardrails; monitor per-step token usage |

## 9) Production Rollout Configuration (Approved)

Use the following for production rollout unless a targeted experiment requires overrides.

### Required P1 rollout envs

- `LLM_STEP_PARALLEL_ENABLED=true`
- `LLM_STEP_PARALLEL_MODE=active`
- `LLM_STEP_PARALLEL_WORKERS=0` (auto-high capped by persona count)
- `LLM_STEP_PARALLEL_STRICT_DETERMINISM=true`
- `LLM_STEP_PARALLEL_CORRECTNESS_FIRST=false` (must be false for active mode to run)

### Keep strict headless gate enabled

- `HEADLESS_STRICT_MODE=true`
- `HEADLESS_STRICT_MIN_ACCEPTED_RATIO=1.0`
- `HEADLESS_STRICT_MIN_ACCEPTED_COUNT=4`
- `HEADLESS_STRICT_ABORT=true`
- `HEADLESS_STRICT_MAX_REPORT_JUMP_TILES=25`

### Keep P1 guardrail envs enabled

- `TASK_DECOMP_BOUNDARY_GATE_ENABLED=true`
- `POIGNANCY_BATCH_ENABLED=true`
- `REFLECTION_ASYNC_QUEUE_ENABLED=true`
- `REFLECTION_ASYNC_MAX_LAG_STEPS=2`

### Instant rollback

If production behavior degrades, set:

- `LLM_STEP_PARALLEL_ENABLED=false`

Then restart backend. This returns runtime to sequential step execution without code rollback.
