# **Safety analysis and recommendations**

## *What I found*

  I compared Dependabot's findings against the actual code that runs. Three important facts:

  1. The Django alerts are all dead code. About half of your alerts are Django-related (SQL injection, path traversal, account hijack, etc.). These look terrifying — but you don't        
  actually run Django anywhere. The environment/frontend_server/ folder is the original research-paper frontend from the Stanford repo. Your real frontend is the separate double-front    
  Next.js project. No Python file in your codebase imports Django. It's just a requirements.txt sitting in a folder, and Dependabot scans it blindly.

  2. Many "high severity" packages aren't actually imported either. I searched your code and found that these packages are pinned but never directly used by your project:
  - nltk, Pillow, joblib, scikit-learn, sqlparse, gunicorn, tqdm

  Some of these may still be pulled in as dependencies of things you DO use (e.g. gensim may need some of them), but gunicorn is definitively not used — your production startup script
  (start.sh) runs uvicorn, not gunicorn.

  3. aiohttp is used, but only as an HTTP client, not as a server. This matters because most aiohttp alerts are about server vulnerabilities (request smuggling, multipart parsing, HTTP   
  parser issues on the receiving side). Your code calls aiohttp.ClientSession() to fetch URLs — it never runs aiohttp.web.Application. So about 80% of the aiohttp alerts don't apply to   
  your attack surface. A few still do — the client-side ones (cookie leak on redirect, CRLF injection, credential leak).

  What IS actively used and exposed: aiohttp (client only), requests, urllib3, certifi, idna, h11, python-multipart (via FastAPI).

## *Why this matters for risk*

  Your actual attack surface is the API Gateway (FastAPI + uvicorn) deployed on Railway. That's the only internet-facing thing you ship. Dependabot doesn't know that — it treats every    
  dependency in every requirements.txt as equally scary, even if the code never runs.

  The real risks that warrant attention:
  - python-multipart vulnerabilities (High) — this one IS in your production path because FastAPI uses it to parse uploads
  - urllib3 + requests issues — used for outbound HTTP calls; mostly client-side DoS risks with limited impact on a backend that talks to trusted APIs (OpenAI, Supabase)
  - aiohttp client-side issues — similar — only matters if you fetch untrusted URLs (you don't)

  The Critical-labeled Django/Pillow/joblib/NLTK alerts do not apply to your running system because that code is never executed in production.

## *My recommended plan (three waves)*

  I haven't touched any code yet — I want approval before making changes. Here's what I propose:

  Wave 1 — Delete the dead code (biggest impact, near-zero risk).
  - Delete environment/frontend_server/requirements.txt entirely, since the Django frontend isn't used.
  - Remove the Django/gunicorn lines from railway-requirements.txt (lines 48-51 explicitly say "Legacy frontend - optional, can remove if not needed").
  - This alone should close roughly 100+ of your 160+ alerts.
  - Risk: very low. Nothing imports Django.

  Wave 2 — Bump the packages you actually use (real fixes).
  - Update python-multipart, requests, urllib3, certifi, idna, h11, aiohttp to current patched versions in both requirements.txt and railway-requirements.txt.
  - Run the simulation (reverie.py) once and the API gateway (uvicorn) once to confirm nothing broke.
  - Risk: low-medium. Modern versions of these libraries are generally backward-compatible, but pinning jumps from 2021-era versions to 2024+ may surface minor issues.

  Wave 3 — Clean up the "probably transitive" packages.
  - For nltk, Pillow, joblib, scikit-learn, sqlparse, tqdm: test whether they can simply be removed from requirements.txt. If something breaks, bump them to current versions instead.     
  - Risk: medium. Requires actually running the system to see if gensim or another package silently depends on them.

## *What I'd start with*

  Do Wave 1 now. It's the highest-value, lowest-risk step — deleting dead code closes the majority of alerts without touching anything your system actually runs. You'll see your
  Dependabot count drop dramatically, and then you can look at the remaining ~30 alerts with a clear head.

  Then do Wave 2 in a separate pass, because bumping active dependencies carries a small chance of breakage and deserves its own test run.

  Wave 3 is optional and can wait until you have time for a proper cleanup — it's mostly hygiene, not security-critical.
