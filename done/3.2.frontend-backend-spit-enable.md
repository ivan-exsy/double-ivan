# Frontend-Backend Decoupling: Source of Truth

## **Overview**

This document serves as the comprehensive source of truth for the frontend-backend integration in the generative agents simulation system using a turn-based architecture. The system enables coordinated operation where the backend generates simulation steps with partial movements and agent decisions, the frontend renders these steps, collects user interactions, and triggers the next backend step, ensuring immutability and natural time flow without blocking dependencies.

### **Core Architecture Principles**

**Backend (Scenario Writer)**:
- Generates simulation steps independently with partial movements (max 6 tiles/minute) and cognitive updates
- Processes user interactions from frontend before each step
- Maintains immutable step files with embedded partial states (no modifications to existing steps)
- Provides structured data with waypoints, progress tracking, and render status for frontend consumption

**Frontend (Movie Production)**:
- Triggers backend steps via API and renders partial movements with animations
- Collects user interactions (goal modifications, events) and passes them to the next step
- Supports real-time playback, rewinding, scrubbing, and hybrid modes (live vs. pre-rendered)
- Provides non-blocking feedback and enables headless rendering for automated visualization

## **Backend Implementation**

### **1. Turn-Based Coordination Infrastructure**

**Immutable Step Operations**:
- Implemented write-once pattern: Each step creates a new numbered JSON file (`movement/step-{n}.json`) with embedded partial states
- Windows-compatible atomic operations ensure no partial reads during writes
- Guarantees immutability: No existing step files are ever modified or overwritten

**Simulation Metadata System**:
- Updates `storage/{sim_code}/meta.json` after each step with `current_step`, `timestamp`, `status`, `total_steps`, and render status
- Enables frontend coordination without affecting backend internal state (`reverie/meta.json`)

**Turn-Based API Endpoints**:
- `POST /api/simulations/{sim_code}/step/next` - Executes next immutable step with user interactions
- `GET /api/simulations/{sim_code}/step/{step}` - Read-only access for replay (never modifies)
- `POST /api/simulations/{sim_code}/feedback/notes` - Logs frontend issues (desyncs, performance)
- `GET /api/simulations/{sim_code}/rendered/{step}` - Serves pre-rendered PNG images

### **2. Position Reconciliation System**

**Turn-Based Position Management**:
```
Backend: Generates partial movement → Validates reachability (6 tiles/step) → Embeds remaining path in step
Frontend: Animates partial movement → Validates final position → Collects interactions
Backend: Processes interactions → Continues from embedded state in next step
```

**Backend Position Reconciliation** (`position_reconciliation.py` + `reverie.py`):
- Validates movement every step with 6-tile limit and action duration constraints
- Processes frontend feedback with 3-tile tolerance during planning phase
- Generates alternative targets for unreachable movements using progressive fallbacks
- Embeds partial states (remaining_path, action_progress) in each step file for seamless continuation

**Key Bug Fixes**:
- Fixed reconciliation timing to occur before movement calculations in each step
- Batch processing of feedback (last 20 entries) integrated into user interaction handling
- Comprehensive logging with immutability guarantees
- Ensures all personas' states are consistently tracked across steps

### **3. Address Mapping System**

**Intelligent Address Resolution** (`address_mapper.py`):
- Maps AI-generated addresses to valid maze addresses with character-specific and location-specific rules
- Handles special cases (e.g., Hobbs Cafe) and fuzzy matching fallbacks
- Integrated into turn-based planning to resolve addresses before path generation

**Bidirectional Mapping** (`maze.py`):
- Consistent coordinate-to-address mapping in both directions
- Updated to support partial movements and embedded states

### **4. Action Lifecycle Management**

**Turn-Based Action Progression**:
- Actions span multiple steps naturally based on duration (e.g., 60-min action over 60 steps)
- Progress tracked immutably via embedded `action_progress` in step files (steps_elapsed, percentage)
- Completion triggers new action generation during next step's planning phase
- Progressive fallback system (arena → sector → living area → Johnson Park) applied per step

**Solution Applied**:
- Simulations run indefinitely or until user stops, allowing full action cycles
- Verified cognitive pipeline (`act_check_finished`, `plan`, `_determine_action`) works across steps
- Ensures dynamic behavior with social interactions and schedule adherence

### **5. Hybrid Route Planning System**

**Structured Path Generation**:
- `path_finder.py`: Returns `{full_path, waypoints, path_length, validated}` considering obstacles and other agents
- `execute.py`: Plans partial paths (max 6 tiles/step) and embeds remaining path in state
- `reverie.py`: Stores partial paths and progress in movement JSON as `"path"` and `"partial_state"`

**Movement JSON Structure** (Immutable Step File):

```json
      "completed": false

```

**Stationary Enhancement**:
- Short paths (≤1 tile) include micro-movements for visual interest
- Integrated with activity detection for natural idle animations

### **6. Collision Prevention System**

**Coordinate Assignment** (`execute.py`):
- Tile claiming prevents simultaneous targeting with persona priority and distance preferences
- Validates activity-position alignment and triggers re-planning if conflicts arise
- Considers partial movements and embedded states for ongoing paths

**Dynamic Pathing** (`path_finder.py`):
- Treats other characters' positions as dynamic obstacles
- Real-time collision avoidance in partial path planning
- Smart shared-location assignment with turn-based resolution

### **7. Headless Visualization Service**

**Automated Rendering & Observation Generation** (`headless_visualization.py`):
- Triggers background rendering after each step using Playwright (Chromium headless)
- **Generates observations automatically** (proximity, collisions) from headless render
- **Submits observations to API Gateway** via HTTP for backend processing
- Validates sprite positions against step JSON (configurable tolerance)
- Generates PNG images (`rendered/step-{n}.png`) and MP4 videos
- Non-blocking: Runs asynchronously without delaying step execution
- Supports batch rendering for entire simulations

**Observation Integration**:
- Extracts observations from `window.__headlessObservations` during render
- Enriches observations with step number and timestamp metadata
- Posts to `POST /api/simulations/{sim_code}/observations` endpoint
- Enables fully automated simulations without active browser window
- Emergent behaviors (conversations, reactions) work in unattended mode

**Position Validation**:
- Extracts positions from `window.__currentPersonaPositions`
- Compares against step JSON with tolerance threshold (default 2 tiles)
- Captures debug screenshots for mismatch analysis
- Appends validation results to `meta.json`

**Integration**:
- Step metadata includes `render_status` (queued, completed, path)
- Controlled by `ENABLE_HEADLESS_VALIDATION` environment variable
- Fallback to on-demand rendering if image not ready
- Ensures visual assets for hybrid playback modes

## **Frontend Implementation**

### **1. Turn-Based Architecture**

**Step Coordination System**:
- Replaces polling with explicit step triggering via `POST /step/next`
- Collects user interactions during rendering and passes to next step
- Supports immutable replay with `GET /step/{n}` for historical access
- Event-based issue detection with feedback API integration

### **2. Position Feedback System**

**Error Observability Integration** (`lib/errorObservability.ts`):
- `PositionValidator` class validates partial movements (5px tolerance, 6-tile limit)
- Buffers feedback with 10-second batches, adapted for turn-based flow
- Unified tracking with `errorObserver` for desyncs and constraint violations

**Phaser Integration** (`components/GameCanvas.tsx`):
- Animates partial paths (150ms/tile) with walking animations
- Verifies positions on animation completion and during user interactions
- Detects path conflicts and reports via feedback

**Redux State Integration** (`hooks/useRealtime.ts`):
- Tracks partial states (remaining_path, action_progress) from step data
- Validates movement realism per step (max 6 tiles)
- Handles teleportation detection with turn-based thresholds

### **3. Animation System**

**Atlas Animation System**:
- Directional walking (`{name}_{direction}_walk`) and idle frames (`{name}_{direction}`)
- Character-specific animations with activity-based overlays
- Supports partial movement animations spanning multiple steps

**Activity Detection & Visualization**:
- `isStationaryActivity()` for keywords (reading, sleeping, etc.)
- Subtle effects (bobbing, facing direction) for stationary phases
- Progress bars for long actions using embedded `action_progress`

**Phase-Based Animation Logic**:
```typescript
// Partial movement with walking animations
if (persona.isMoving && persona.direction && persona.partial_state.remaining_path.length > 0) {
  const walkAnimKey = `${persona.name}_${persona.direction}_walk`
  sprite.play(walkAnimKey, true)
  // Animate to next waypoint in partial path
} else {
  // Stationary: idle + activity animation
  sprite.setTexture(persona.name, idleDirection)
  if (isStationaryActivity(persona.action)) {
    sprite.y += Math.sin(time) * 0.2
  }
  // Show action progress bar if applicable
}
```

### **4. Movement System**

**Partial Movement Implementation**:
- Pixel-by-pixel animation toward partial targets (X then Y axis)
- `requestAnimationFrame` for 60fps, synchronized with step timing
- Handles continuing movements from embedded remaining_path

**Timeline Integration**:
- `useSmoothTimeline` for continuous progression in live mode
- Scrubbing snaps to step boundaries with partial state reconstruction
- Eliminates jumping by respecting embedded progress

### **5. Collision System**

**Character-to-Character Collision**:
- Separation vectors and sliding for smooth resolution during partial movements
- Client-side prediction using step data and other agents' paths

**Dynamic Collision State**:
- Handles blocked paths and occupied tiles from backend validation
- Visualizes conflicts (red lines, X marks, orange circles) with debug toggle
- Integrates with turn-based re-planning triggers

### **6. User Interaction System**

**Interaction Collection** (`components/UserInteractionPanel.tsx`):
- Click agents to modify goals, add events (weather, obstacles), inject social scenarios
- Queues interactions for transmission in next step request
- Logged immutably in step files under `user_interactions`

### **7. Hybrid Playback System**

**Simulation Player** (`components/SimulationPlayer.tsx`):
- Toggle between 'live' (Phaser rendering) and 'rendered' (pre-rendered images)
- Fast playback using PNG sequence (500ms/step) for completed simulations
- Timeline controls with step jumping and play/pause
- Replay uses read-only API to reconstruct states from embedded data

**Rendered Playback** (`components/RenderedPlayback.tsx`):
- Loads images from `/rendered/{step}` with loading indicators
- Navigation buttons and range slider for precise control
- Falls back to live mode if renders unavailable

### **8. System Health Improvements**

**Animation System**:
- Tween tracking prevents overlaps in partial animations

**Coordinate Pipeline**:
- Unified pixel coordinates with tile-to-pixel mapping

### Known Issue: Position Validation Warnings ⚠️

**Status**: FIXED (October 23, 2025)

**What Was Happening**:
```
❌ Step 1 validation: FAILED (3 mismatches)
❌ Step 2 validation: FAILED (3 mismatches)
```

**Root Cause**: Coordinate System Mismatch
- **Expected positions** (from `movement/N.json`): Stored as **TILES** (game grid coordinates)
  - Example: `[130, 50]` = tile coordinates
- **Actual positions** (from Phaser render): Extracted as **PIXELS** (screen coordinates)
  - Example: `[4160, 1600]` = pixel coordinates (130×32 ≈ 4160)
- **Validation logic** was comparing tiles directly to pixels (32x scale difference!)

**Solution Implemented**:
1. Added `TILE_SIZE = 32` constant
2. Convert extracted pixel coordinates to tiles: `actual_tiles = pixels / 32`
3. Compare in same units (tiles) with tolerance
4. Updated mismatch output to show both tiles and pixels for debugging
5. Added detailed docstring explaining the coordinate systems

**Files Modified**:
- ✅ `reverie/backend_server/headless_visualization.py` → `_validate_positions()` method

**Impact**: Validation warnings should now be accurate. If mismatches still appear, they represent genuine position discrepancies rather than scale conversion errors.
