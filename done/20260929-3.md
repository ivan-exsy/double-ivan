## RCA

Nicolás is one Double in this sim and two names in the data. The map, the step feed, and the survival roster call him Nicolás. The promise file calls him `Nicolasdemaria123`. That string is the login written into his scratch row when the row was created, and it was still there at the stop. The ballot joins people on the name string. His own promises never attached to him, and the other voters saw a promise to a person who is not on the roster.

That split is why his promises and his takeaway memories never landed on him. The takeaway call itself ran. The save did not keep his side. The rest of this section is why the two names diverged, where else the same split lands, and the change that lets a user rename a Double without breaking a season. No product code was changed for this assessment. The stopped sim's files were left as the run wrote them.

The map and the promise file are reading two different columns for the same Double. Only Nicolás is split. The other five match.

| Roster key, from `personas.name` | Scratch name, from `persona_scratch.name` |
| --- | --- |
| Nicolás | Nicolasdemaria123 |
| Gosha Carnegie, Ivan Pitts, Katya Fox, Luba Istomina, Yevgenia Pritchard | same as the roster |

His scratch `first_name` is also `Nicolasdemaria123`, and `last_name` is empty. The same scratch name is in `base_pit` and in the 29 September forks. The login was written once, when the scratch row was created, and it was never updated when the Double was named Nicolás.

`personas.id` is already the real key. Scratch rows, coordinates, and memories are stored on that id. The running sim ignores it for names. At bootstrap it builds the roster from `personas.name`, then copies `persona_scratch.name` into the scratch file even when the two disagree. From `reverie/backend_server/reverie.py`:

```python
"name": (scratch_row or {}).get("name") or persona_name,
"first_name": (scratch_row or {}).get("first_name") or first_name,
"last_name": (scratch_row or {}).get("last_name") or last_name,
```

Join writes the current name into the scratch row. When Join must rename someone to avoid a clash, it writes that new name to the roster and to the new sim's scratch row. That path does not cause this split. The onboarding rename does. It writes only `personas.name` (`pgh_compile._rename_persona`). A second Join by someone already on the roster returns `already_on_roster` and does not touch the scratch row, so it never repairs the split. The next fork copies both columns, and the split arrives in the sim intact.

Inside the run those two strings are used as if they were the same person:

- The map, the step file, survival state, vote targets, and who is in a conversation use the roster name, Nicolás.
- The identity block, the conversation prompt, and the takeaway prompt use the scratch name, `Nicolasdemaria123`. The vote prompt's "you are …" line uses `first_name`, which is the login too.
- A promise is kept only when both sides match the scratch names. It is then stored with `states.get` on that scratch name (`reverie/backend_server/survival/controller.py`, `_merge_talk_promise`). The state table is keyed Nicolás, so his side is dropped. The other person's ballot keeps a promise labeled with the login. The takeaway sentence is saved with `takeaways.get(speaker.name)`, and `speaker.name` is the roster name, so his sentence is dropped too. He has 0 takeaway memories in this run. The others have between 10 and 20.

That is why his own ballot was empty, his talk memories are empty, and everyone else's ballot mentioned `Nicolasdemaria123`. On day 2, Luba's promise block said `Nicolasdemaria123` and the people she could vote for included `Nicolás`. The reason had to guess they were one person. His day-2 vote against Katya recorded no betrayal: "We stick together, vote steady" is stored only on her side.

The same split misses anywhere a relation is stored under one string and read under the other.

- Promises and takeaway memories. Proven on this run.
- Relationship affinity. A talk records affinity under `scratch.name`. Later lookups use the roster name, so Nicolás's affinity never attaches.
- Chat lines and memory of the chat. The conversation prompt names the speaker from scratch. The cleanup keeps whatever name the model writes back, so one sit can contain both strings. The saved memory then uses the scratch name as subject and object.
- Ally checks. Both look up the roster name. `_survival_ally_or_trust` (`social_will.py`) decides whether a meeting becomes a full talk. `pick_social_seek_target` picks who they should try to find that day, preferring an active ally. Neither ever counts Nicolás as an ally.

Survival state, alliance keys, vote targets, who eliminated whom, and `chatting_with` are stored as the name string. They match the map today, and a later rename breaks them for the same reason. `simulations.persona_names` is the same kind of copy. Free-text memories will keep the old wording either way. That part is history, not a key.

Cost and trace labels already prefer the roster name (`persona.name`, then the scratch name only if that is missing). His usage is counted under Nicolás. Those labels are not part of this fix.

The fix is one identity and one label.

`personas.id` stays the only id. It does not change when the user renames. `personas.name` is the only name the world uses: map, chat, ballots, prompts. `persona_scratch.name` and `first_name` are a cache of that label for the identity paragraph, not a second name.

Three ways to get there:

1. Heal the string at load, and make rename write both rows. If scratch disagrees with `personas.name`, the roster name wins and the scratch row is corrected. Takeaway, affinity, and chat then see one string. A rename updates `personas.name` and every scratch row for that id. A sim already running keeps the name it booted with. The next start uses the new one. This fixes Nicolás's class of bug. A rename after promises exist still leaves those promises under the old string.
2. Keep the heal, and store relations by `personas.id`. Promises, votes, affinity, and `chatting_with` save the id. The prompt fills in the current `personas.name` when it is built. A nickname change cannot orphan a promise. Memory sentences stay as they were written. This is the version that matches "a rename must not break the system."
3. Make the scratch name the source of truth and push it back onto the roster. That fights the rename, which already writes `personas.name`, and it would rename the map key under a live sim. This one should not be done.

The recommendation is 2, built in that order. The load-time heal and the rename write come first. They are safe to ship without touching this stopped run. The id-keyed relations are the core, and they include promises, takeaway saves, votes, affinity, `chatting_with`, and the two ally lookups. They should land before anyone can rename a Double who is already inside a season. The build list is at the end of this paper.

## Promises that are still live

The name fix puts Nicolás's own pledges on his ballot under Nicolás. It does not fix a pledge that stays live after that person has left, a broken pledge that comes back, or a favor scored as a betrayal. No code has been changed for this.

A pledge stays active until that voter themselves votes the other person out. A betrayal then closes only the voter's own side. Gosha left on day 1 because other people voted him out, so Ivan's pledge to him was still active on day 2. The ballot prints every active pledge. It never asks whether that person is still in the game. The same active flag feeds the "active alliances" line in other prompts. Hiding the name on the ballot alone would leave that leak.

The save makes this worse. `_merge_talk_promise` sets `active` back to true on every new line, including a pledge already marked broken. It happened twice. Katya broke her pledge to Yevgenia on day 1. Yevgenia's new words on day 2 marked Katya's old line active again, and it came back on Katya's ballot as a live pledge. Yevgenia's pledge to Katya was marked broken on day 2 and also active: the vote is counted at 20:00, elimination runs at 21:00, and a talk in that hour reopened it.

The vote instruction already says to state whether a pledge is being kept. Another sentence in the prompt will not hold this. Luba already had the instruction and her own quote. Forcing keep or break on every stored line would also be wrong. Gosha's robotics-notes favor would become "I promised to look at his notes, and I am breaking that."

## Build

Two pieces. Pledge rules first, then the id key, so a revived pledge is not copied onto the new key. The name heal can ship before either. Do not patch the stopped sim. Still-body captions, pool speech, the unopened Watch page, Downtown Join, and cost labels are out of this work.

### 1. One name

- At load, if scratch `name`, `first_name`, or `last_name` disagrees with `personas.name`, the roster name wins and the scratch row is corrected. The block is in `reverie/backend_server/reverie.py`.
- The onboarding rename writes `personas.name` and every `persona_scratch` row for that id. Today `_rename_persona` writes only `personas.name`.
- Leave Join's first write as it is. A clash rename already writes both columns. A second Join returns `already_on_roster` and does not repair scratch. The load heal covers that.
- Then store promises, takeaway saves, votes, affinity, `chatting_with`, and the ally lookups by `personas.id`. The prompt fills in the current `personas.name`. The lookups are `_merge_talk_promise`, `takeaways.get(speaker.name)`, `_survival_ally_or_trust`, and `pick_social_seek_target`.
- Cost and trace labels already prefer `persona.name`. Leave them.
- Memory sentences stay as they were written.
- A sim already running keeps the name it booted with.

### 2. Live pledges

Record only a vote pledge or a protection pledge. Change `survival_talk_takeaway_v1.txt`. The current line counts anything the speaker will do "in a vote or later," which stored Gosha's favor. A favor, a hint, or an errand is not a pledge. Store a kind on the row: `spare` (keep your name out, protect you) or `vote_with` (vote together). Betrayal counts only those two kinds. A row with no kind does not count.

Close every pledge with the person voted out when the votes are counted, at 20:00, before the 21:00 elimination phase. The words stay on the record. Closing them records no betrayal. A betrayal stays what it is now, and only for a `spare` or `vote_with` row: voting out someone you pledged. Do not record a new pledge with anyone who already has a pending elimination. That covers the talk between 20:00 and 21:00.

A broken pledge stays broken until the promiser says a fresh pledge of their own. The other person's new words must not set `active` back to true on the broken side. Today both sides of `_merge_talk_promise` set `active = True`.

The ballot lists only active pledges with people still in. The same active flag is what the other alliance lines read. For each live pledge, the vote returns keep or break, and one sentence of why. The ballot line is built from the stored words plus that choice. Luba's line would read: I promised Gosha "I'll back you if you back me," and I am breaking that. Her reason follows. If a field is missing, retry. If it is still missing, the server fills a stance only when the kind makes the choice plain:

- `spare`: break when they voted that person. Keep when they voted someone else.
- `vote_with`: break when they voted that ally out. Break when the tallied votes show they did not vote the same person as that ally. If the ally's vote is not known yet, print the stored words and do not invent keep or break.

"Break when they voted that person, otherwise keep" is the wrong default for a vote-with pledge.

Survivors already receive one memory that the person was eliminated (`_broadcast_elimination`). Add to that sentence that the pledge with them ended. Do not write a second memory.

Two approaches stay rejected. Dropping eliminated names from the ballot text and sharpening the instruction leaves the stored pledge active, so it still feeds the other alliance lines. A second model pass to rewrite the reason adds a call on every ballot, and the rewrite can still deny the stored quote.
