## **Natural Approach to Realistic, Fluctuating Action Durations**

**Current Reality**: The simulation currently uses accelerated progression for testing (1-min steps via `sim_step_length=60` in `.env.local`, and a hardcoded 5-min action override in `plan.py` line ~954: `act_dura = 5`). This compresses days unrealistically (e.g., morning routine in 5-10 min). The implementation below removes this temporary acceleration and introduces natural, fluctuating durations via LLM context and modifiers. Switch involves 2 file changes + env vars.

### Core Principles
- **LLM-Driven Base**: Let the LLM generate initial durations in `generate_task_decomp` prompts, informed by context (e.g., "Estimate time for brushing teeth on a busy morning").
- **Dynamic Modifiers**: Apply soft, factor-based adjustments post-LLM (e.g., +random(5-15%) for variety; extend if interrupted). Use existing memory (e.g., "tired" keyword → +20%).
- **Adaptive Feedback**: During execution, monitor interruptions (e.g., proximity chat) and adjust remaining time (e.g., pause routine, resume later).
- **Variance for Realism**: Add 10-30% random fluctuation per action, scaled by type (e.g., high for creative tasks like "painting", low for routines like "sleeping").
- **No Overrides**: Avoid testing hardcodes; let factors compound naturally (e.g., social → longer; fatigue → shorter bursts but more rests).

This keeps sims spontaneous (external events influence pacing) while realistic (no instant actions, but no rigid mins).

##### **Rubber-band sprite movements**

*Problem*
Frontend sprites exhibit rubber-band/jittery motion during path-following tweens, caused by backend-generated waypoints (`movement/N.json`) overshooting the authoritative end-of-step coordinates from `environment/N.json`. This leads to the sprite moving past the target, then snapping back (e.g., Luba step 6: end at (116,46), but path extends to x=111).

*Frontend Adjustments*
- Switched to linear tweens with snapping to final coordinates.
- Cleared velocity/acceleration post-tween to prevent physics drag.
- Reset physics states around tweens; added softened timeouts for long paths.
- Result: Reduced elastic effects, but snaps persist due to backend mismatch.

*Backend Root Cause & Fix*
**Cause**: Incomplete clamping in `reverie.py` (movement loop, ~lines 1046–1150) allows `full_path` slicing to include future waypoints, creating non-monotonic paths longer than net distance +1–2 tiles.

**Implementation in `reverie.py`** (15–20 lines; test with `run_test_sim.py` and `validate_continuity.py`):
1. **Net Distance Pre-Compute** (~line 1079): Calculate `net_dist = manhattan(current_tile, next_tile)`. For ≤1, use single-point path `[next_tile]`. Target slice length: `min(net_dist + 2, 6)` for smooth visuals.
2. **Conditional Path Generation** (~lines 1081–1096): If `full_path` exceeds slice or carryover detected (e.g., `full_path[-1]` ≠ `next_tile`), regenerate short path via `path_finder` (start=`current_tile`, end=`next_tile`; ignore obstacles for visuals, fallback to linear). Else, slice `full_path[:slice_len]` and prepend start.
3. **Clamping & Smoothing** (~lines 1097–1109): Ensure `output_path[0] = current_tile`, `[-1] = next_tile`. Interpolate non-monotonic segments (check perpendicular deviation >1; replace with linear steps: `current + i * (next - current) / net_dist`). Update `remaining_path_for_write = full_path[net_dist:]`.
4. **Validation** (~line 1112): Assert `len(output_path) ≤ net_dist + 2` and max excursion ≤ `net_dist + 1`. Log path details; fallback to linear if violated.

**Additional Prep in `path_finder.py`**:
- Ensure `full_path` includes start and ends at `end` for consistent slicing.

**Outcomes**:
- Paths are monotonic, short (net_dist +1–2 points), and exactly end at authoritative coords—no overshoots or snaps.
- Preserves continuation logic; no new deps/files.
- Validates: No excursions > net distance; all tests pass.

*Overview*
Extend movement paths to realistic human speeds (~1 m/s, 30 tiles/min at 32px/tile) for immersive simulations, capping at 30 tiles/step to avoid perf issues. Backend enforces slicing/multipliers; frontend scales tweens/velocity. Total: ~3-4 hours backend + 1-2 hours frontend/testing; no new deps.

*Research Findings (Phaser Feasibility)*
- **Viability**: Fully feasible; Arcade Physics uncapped (>>16px/s needs), tweens handle 30+ waypoints at 60 FPS on mid-range devices. Use fixed timestep (`physics: { fps: 60 }`), `PathFollower` for subdivision (<50 points/step), and linear velocity for efficiency.
- **Best Practices**: `moveTo()` for straight paths; `Curves.Path` + easeInOut for curves. Mitigate jitter via slicing (no GC spikes); collisions via tilemap layers. Edge: Interrupt with `tween.stop()`; cull off-screen sprites.
