# **Turn-Based Architecture**

## *Vision
The turn-based architecture transforms the generative agents simulation into an interactive, emergent system where:
- the backend generates immutable JSON "scripts" for each step (agent decisions, partial movements, actions), 
- the frontend visualizes these in real-time using Phaser for realistic sprite behaviors, and reports back observations (e.g., unplanned collisions or serendipitous encounters) to influence future steps. 

This enables natural social interactions, spontaneous events, and personalized user experiences—users can focus on specific agents, adjust camera angles, and witness emergent storytelling. 
Headless rendering serves only for initial synchronization and validation, ensuring backend plans render correctly without glitches, while the core experience is live, re-renderable simulations that feel dynamic and agent-driven rather than pre-recorded movies.

## *Schema & Benefits*
### Turn-Based Flow
```
Backend: Generate Script (JSON: paths, actions, partial states)
    ↓ (POST /step/next)
Frontend: Render & Observe (Phaser: animations, collisions, emergence)
    ↓ (POST /observations: e.g., {type: "meeting", agents: ["Maria", "Klaus"]})
Backend: Adjust & Next Step (Incorporate feedback, maintain immutability)
```

**Key Benefits**:
1. Natural time flow with actions spanning steps.
2. Realistic 6 tiles/minute movement constraints.
3. Emergent social interactions and user-injected events.
4. Simplified state via single source of truth (immutable JSONs).
5. Personalized, live re-rendering for dynamic experiences.

## **Coordinate Conversion System**

 **Purpose**
The Coordinate Conversion System enables seamless integration between the backend's tile-based coordinate system (used for efficient AI planning, pathfinding, and memory management) and the frontend's pixel-based system (optimized for Phaser.js rendering, animations, and user input). This bidirectional translation preserves sub-tile precision, ensures round-trip accuracy, and requires no changes to existing backend or frontend logic.

### **📊 System Architecture**

```
┌─────────────────┐    ┌───────────────────────┐    ┌─────────────────┐
│   Backend       │    │   API Gateway         │    │   Frontend      │
│   (Tiles)       │────│   (Converter)         │────│   (Pixels)      │
│                 │    │                       │    │                 │
│ • AI Planning   │    │ • /step/next          │    │ • Phaser.js     │
│   [78, 21]      │    │   tiles→pixels        │    │   [2512, 688]   │
│ • Pathfinding   │    │ • /observations       │    │ • Direct Use    │
│ • Memory        │    │   pixels→tiles        │    │ • No Conversion │
│ • Constraints   │    │ • Validation          │    │ • Rendering     │
└─────────────────┘    └───────────────────────┘    └─────────────────┘
     Native Tiles         Transparent Bridge           Native Pixels
```

### **Key Implementation Details**
- **Location**: `api_gateway/app/core/coordinate_converter.py`
- **Core Functions**:
  - `to_pixels(tiles: list[int]) -> list[float]`: Converts tile coordinates to pixel coordinates (e.g., [78, 21] → [2512, 688]).
  - `to_tiles(pixels: list[float]) -> list[int]`: Converts pixel coordinates to nearest tile (e.g., [2495, 685] → [77, 21]).
  - `convert_step_data(data: dict, direction: str) -> dict`: Handles full step structures, paths, and partial states ("to_frontend" or "to_backend").
  - `convert_observation(obs: dict, direction: str) -> dict`: Processes observation locations with precision offsets.
- **Integrations**:
  - **API Endpoints**: `/step/next` applies "to_frontend" conversion before response; `/observations` uses "to_backend" on incoming data.
  - **Storage**: Backend stores raw tiles; API delivers pixels with metadata (`"coordinate_system": "pixels"`).
  - **Validation**: Headless service (`headless_visualization.py`) converts for DOM comparisons; new endpoint `GET /simulations/{sim_code}/validation/{step}/coordinates` for round-trip tests.
- **Features**: Error-resilient (graceful degradation), path array support, metadata for debugging, frontend direct use (no re-conversion).

### **Import & Basic Use**

  ```python
  from app.core.coordinate_converter import coordinate_converter

  # Backend to Frontend
  tiles = [78, 21]
  pixels = coordinate_converter.to_pixels(tiles)  # [2512, 688]

  # Frontend to Backend
  pixels = [2495, 685]
  tiles = coordinate_converter.to_tiles(pixels)  # [77, 21]

  # Step Data
  frontend_step = coordinate_converter.convert_step_data(backend_step, "to_frontend")
  ```

#### **Phase 4: Animation Architecture Fix ✅ COMPLETE**
**COMPLETED** (October 2, 2025 - Post Root Cause Analysis)

**Critical Issue:** Backend provides discrete snapshots (final positions per step), not movement instructions. Previous tween-based animations (150ms/tile, up to 17-27s) caused multi-step spans, post-playback movement, jitter, incomplete paths, and wall clipping (frontend path recreation bypassed backend collision).

**Solution: Instant Positioning (True Turn-Based)**
- Replaced `MultiStepAnimationManager` tweens with direct `sprite.setPosition()`.
- Each step shows backend's final state immediately (no interpolation/delays).
- Direction from position delta for idle frame orientation.
- Removed all time-based logic (no 1000ms activity timers, no distance durations).

**Key Changes**
**File:** `components/GameCanvas.tsx` lines 55-151
- **Before:** `animatePersonaStep()` used tweens with `duration = tilesToMove * 150ms`.
- **After:** `positionPersonaInstantly()` calls `sprite.setPosition(x, y)` directly.
- Class retains `MultiStepAnimationManager` name for API compatibility.

**Code Comparison:**
```typescript
// OLD (Time-Based - INCORRECT)
const moveDuration = tilesToMove * 150; // Up to 17s+!
this.scene.tweens.add({
  targets: sprite,
  x: targetPos.x, y: targetPos.y,
  duration: moveDuration, // Spans steps
  onComplete: () => startActivityAnimation(1000ms)
});

// NEW (Instant - CORRECT)
sprite.setPosition(targetPos.x, targetPos.y); // Immediate
onComplete(); // No delays
```

**Why It Works**
1. **Backend:** Handles pathfinding, collision, timing.
2. **Frontend:** Displays computed state per timestep.
3. **Turn-Based:** Discrete transitions, no continuous animation.
4. **Performance:** No tween overhead; instant scrubbing/seeking.

#### **Phase 5: Implementation Strategy to Fix Visualization Issues**

##### *Context Review*

**Two Visualization Systems**:
- **Legacy Movement System** (`hooks/useLegacyMovement.ts` + `components/GameCanvas.tsx` lines ~1775-2069): Active during playback. Uses backend waypoints for interpolated `smoothPath` (50+ points for 6-tile moves). Phaser tween chains with `totalDuration = pathLength × 100ms` (5-6s max). Issues: Overruns, interruptions, jitter, clipping, truncation.
- **MultiStepAnimationManager** (`components/GameCanvas.tsx` lines ~60-151): Primary renderer, step-bounded. Discrete per-step updates; short linear tweens for >1 tile moves; instant for ≤1 tile. Strengths: No overruns/jitter, backend sync. Weaknesses: Instant small moves feel robotic.

**Playback Per-Step Timing**:
- Backend: 60s simulated/step.
- Frontend: Accelerated (2-5s/step) causes interruptions; x1 (60s/step) leads to frozen sprites.
- Natural Viz: 5-6s max for 6 tiles (brisk walk); add idle animations for waits.

These cause all issues: Legacy flexibility breaks under rushing; MultiStep precision lacks smoothness.

##### *Alignment with Priorities*
- **Smooth Execution**: Hybrid for progressive paths + fidelity.
- **No Jitter/Teleport**: Isolate steps, bound tweens.
- **No Delays/Frozen**: Dynamic 1-6s timing + idle loops.
- **Hybrid Approach**: MultiStep base for reliability + short tweens for polish.

##### *Recommended Strategy: Hybrid MultiStep with Short Progressive Tweens*
- **Core Flow**: On step advance, compute path → instant position → short linear tween from current to final (if >1 tile).
- **Timing**: Dynamic `T = min(6000, max(1000, distance * 50))` ms (1-6s). User slider override.
- **Why Fixes**:
  - Smooth: Natural progression (5s for 6 tiles).
  - No Jitter/Teleport: Step-bounded tweens, start from prior pos.
  - No Delays/Frozen: Caps avoids 60s holds; idle bobbing post-tween.
  - MVP Fit: Supabase Realtime sync; Expo portable; 6 tiles/min validation.
- **Fallback**: Cap >6 tiles at 6s + warning.
- **Risks**: Minor perf (test mobile); toggle for over-smoothing.
