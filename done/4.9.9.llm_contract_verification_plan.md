- evidence-backed status for each function,
- clear production-vs-test parity rules,
- ongoing governance so the doc stays accurate.

## Exit Criteria (Promotion To True SOT)

`docs/sot/sot_prompts.md` can be promoted to **SOT v1.0** only when all are true:

1. 100% of active functions have:
   - explicit expected raw output shape,
   - explicit cleanup/parsing expectation (or "none"),
   - current pass/partial/fail status with timestamp and artifact link.
2. No active function row is marked "pending verification."
3. For each function, transport behavior is classified:
   - native chat success,
   - native responses success,
   - chat recovered via responses fallback,
   - total failure.
4. Production-vs-test parity fields are captured in each run manifest.
5. README + SOT index reference `docs/sot/sot_prompts.md` as prompt-usage SOT.
6. PR governance rule is documented: prompt-flow code changes must update SOT in same PR.

- SOT-grade evidence requires production-shaped prompt payload.

Done when:

### WS4) Function Verification Campaign

**Objective:** close pending verification for every active function.

Manual web replay gate (any true):
- both modes fail raw contract,
- large chat vs responses discrepancy,
- repeated off-format despite non-empty output.

Done when:
- function status is set to `pass`, `partial`, or `fail` with evidence links.

## Standard Function Cycle (Execution Runbook)

Assume `<FN>` is the function under test.

### Step 0 - Freeze test posture
- Fix env posture and model config for this cycle.
- Capture manifest before first call.

### Step 1 - Automated probe
Use:
- `tests/llm_output_function.py` for targeted dual-mode comparison, or
- `tests/llm_output.py` for broader matrix runs.

Record both requested and actual transport fields.

### Step 2 - Assess against contract
Classify:
- non-empty vs empty
- raw contract pass/fail
- cleanup contract pass/fail
- tier promotion behavior
- transport fallback behavior

### Step 3 - Report and hold
- publish function result summary
- wait for sign-off before next function

### Step 4 - Conditional web replay
- run only when gate criteria are met
- attach results to run folder

### Step 5 - Update SOT row
- update status + timestamp + artifact links
- keep rationale concise

## Transport Interpretation Rules (Mandatory)

When `api_style_requested=chat_completions`:
- if `api_style_used=chat_completions` and output passes => **native chat pass**
- if `api_style_used=responses` and fallback counter increments => **chat recovered via fallback**
- if both blank/fail => **chat fail**

Do not count "chat recovered via fallback" as native chat reliability.

## Web Replay Setup (Production-Aligned)

Use Prompt Editor as **secondary confirmation** after API verification for a function.

Prompt Editor URL:
- `https://platform.openai.com/chat/edit`

### When To Run Web Replay
- Run after Step 3 (report/hold), before final sign-off for that function.
- Required when:
  - both API modes fail raw contract, or
  - chat vs responses behavior diverges, or
  - output is non-empty but repeatedly off-format.

### Inputs You Must Reuse From API Artifacts
For function `<FN>`, reuse values from:
- `test-results/<run-id>/<FN>/chat.json`
- `test-results/<run-id>/<FN>/responses.json`
- `test-results/<run-id>/<FN>/assessment.json`

Carry over exactly:
1. `prompt` (user message content)
2. model target (`final_producing_model` from assessment context)
3. any format-critical constraints already present in prompt

Do not rewrite or "improve" the prompt during replay unless you are explicitly testing a prompt fix.

### Developer Message Selection (Must Match Function Family)
Use the function-specific system prompt family from `reverie/backend_server/persona/prompt_template/prompt_fragments.py`:
- `planning_agent`
- `action_decision`
- `conversation_agent`
- `memory_agent`
- `persona_base` (fallback/explicit mapped cases)

Important:
- Do not use one universal dev message for all functions.
- Use the same family the runtime uses for `<FN>`.

### Exact Replay Procedure (Per Function)
1. Open `https://platform.openai.com/chat/edit`.
2. Model: select the same model used in API evidence (typically `gpt-5-mini`; optionally also run `gpt-5-nano` for comparison).
3. Settings:
   - output format: text
   - reasoning: lowest / minimal
   - tools: off
4. Developer message: paste the exact system prompt text for `<FN>` family from `prompt_fragments.py`.
5. User message: paste exact `prompt` string from API artifact JSON (no edits).
6. Run at least 3 times per model to detect instability.
7. For each run, classify:
   - non-empty: `yes/no`
   - raw contract pass: `yes/no`
   - failure type (if fail): `empty | off-format | wrong type | partial`
   - notes (short)

### Recording Format
Write rows to:
- `test-results/<run-id>/openai_web_results.csv`

Required columns:
- `function,model,run_id,attempt,non_empty,raw_contract_pass,failure_type,notes`

Example row:
- `run_gpt_prompt_daily_plan,gpt-5-mini,20260217_x,2,yes,no,off-format,"Narrative schedule; not parser-shaped numbered continuation"`

### Interpretation Rules
- Web replay checks model behavior and prompt contract adherence only.
- Web replay does **not** validate API transport behavior (`chat_completions` vs `responses`) because Prompt Editor transport is not controlled the same way.
- Final function status still comes from API artifacts plus contract scoring; web replay is corroborating evidence.
