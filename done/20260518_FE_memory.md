## 1. What's wrong

Running two sims back-to-back on the same machine **without restarting the dev environment** between them, the Node frontend's RAM footprint nearly doubled. The growth is large in absolute terms, and the concern is that on a 24/7 production server this trend would either degrade performance or eventually crash the process.

Headline numbers from Windows Task Manager:

| Process | After run 1 | After run 2 | Δ |
|---|---:|---:|---:|
| **Node.js JavaScript Runtime** | 5,700 MB | **8,352 MB** | **+2,652 MB** |
| **VmmemWSL** (WSL2 VM) | 1,139 MB | 2,843 MB | +1,704 MB |
| Chromium (headless, lingering) | 262 MB | — | persistent |
| Python (backend) | ~306 MB | ~320 MB | +14 MB |

Machine memory at the end of run 2: **96% used**. One more run and the OS would have started swapping or OOM-killing.

During an active sim, CPU also leans heavily on the Node side (43% Node + 18% Chromium), so this isn't a "frontend is idle, memory just slowly drifts up" pattern — the frontend is doing real work each step and not releasing it cleanly afterward.

## 2. Why this matters

Production will run sims **continuously**, not one-at-a-time with manual restarts. Any per-run residual that survives the end of a sim is a leak in the production sense — it compounds across runs and over time forces a process restart.

Even if a single sim's footprint is acceptable, **between-sim cleanup** has to bring memory back to roughly the baseline. The Task Manager snapshots strongly suggest it currently doesn't.

## 3. Plausible suspects (FE side)

Ivan doesn't have visibility into the `double-front` internals, so this list is just to anchor the investigation — not a diagnosis. Worth checking each:

1. **Phaser scenes not destroyed between sims.** When the user navigates from one sim to another, are old scene objects, textures, tilemaps, and sprite pools fully released, or do they linger in memory and accumulate?
2. **Per-step JSON blobs retained.** Every step the FE receives a `movement/N.json` and ships an `environment/N.json`. If those payloads are kept in an array/object indexed by step (e.g. for "rewind"), the structure grows linearly with sim length. Verify whether old steps are evicted.
3. **WebSocket / SSE subscription leaks.** Subscriptions to Supabase realtime channels or the API gateway's websocket that aren't unsubscribed on sim teardown will keep callbacks (and their closure context) alive.
4. **Headless browser orchestration not closing pages/contexts.** A lingering Chromium process at 262 MB after run 1 suggests at least one Playwright page or context wasn't closed. If the orchestration script opens a fresh context per sim and doesn't close the old one, every run leaks one.
5. **Next.js dev-mode HMR retention.** Dev server holds compiled module graphs and HMR state; this is normal in dev but exaggerates the apparent leak. Worth confirming whether **prod-build (`next build && next start`) shows the same growth pattern** before treating it as a code bug — if prod-build is flat across runs, the dev-only piece is cosmetic.
6. **Phaser texture / atlas cache.** Phaser's texture manager caches by key; reloading the same tilemap with a different key each run can accumulate textures in GPU memory and (via the JS-side reference) in the heap.
7. **Console / log buffers in dev.** Browser devtools console buffering (if a headless instance is being run with devtools attached) can hold every step's logs for the lifetime of the page.
8. **WSL VM growth.** The +1.7 GB on `VmmemWSL` likely reflects the FE/Docker side living inside WSL — worth checking whether anything FE-related runs inside WSL (Docker containers, Supabase local stack) and whether those processes also leak.

## 7. Investigation — 2026-05-18 (Nicolas, FE side, static audit pass)

Static audit of `double-front`'s teardown path against §3 suspects. **Verdict so far: the obvious cleanup hooks are mostly in place — Ivan's "scenes not destroyed / channels not unsubscribed / contexts not closed" hypotheses don't fit the code.** Likely contributors below.

### What's actually wired up (refutes §3 suspects 1, 3)

| Suspect (§3) | Hypothesis | Code reality |
|---|---|---|
| 1. Phaser scenes not destroyed | "old scene objects, textures, sprite pools linger" | `MainScene.shutdown()` (`scenes/MainScene.ts:2853`) removes input + scene listeners, deletes window globals (`__mainScene`, `__playbackController`, `__cameraController`, ...), calls `animationManager.shutdown()`, resets camera, nulls callbacks, destroys popover + debug panel. `AnimationManager.shutdown()` (`scenes/managers/AnimationManager.ts:5677`) destroys all activeTweens, clears `claimedTiles` + `computedPathsTiles` + `headlessDynamicOccupiedTiles`, cancels `jsSafetyTimeoutId`, deletes window globals. `usePhaserSetup` (`hooks/usePhaserSetup.ts:152`) calls `game.destroy(true)` on unmount with `simCode` in deps, so it re-runs on sim change. |
| 3. WebSocket / SSE subscription leaks | "subscriptions not unsubscribed on teardown" | All four Supabase Realtime channels call `removeChannel` in cleanup: `hooks/useCarriedObjects.ts:146`, `hooks/useSimulationStep.ts:143`, `hooks/useMazeChunks.ts:246`, `hooks/useSupabaseCoords.ts:280`. `useRealtime` force-closes the entire `window.__webSocketRegistry` and `__webSocketLocks` when `simCode` changes (`hooks/useRealtime.ts:1027-1044`). |
| (route teardown) | "stores not reset on sim navigation" | `dispatch(resetSession())` + `PlaybackController.resetInstance()` + `CameraController.resetInstance()` all invoked in page cleanup at `app/sim/[sim_code]/play/page.tsx:763-767` and `app/simulations/[sim_code]/page.tsx:1345-1349`. |

The "an old scene leaks because nothing unmounts it" theory doesn't survive contact with the code.

### Likely actual contributors

**A. `stepBufferRef` accumulates ~one entry per step within a sim (likely #1 contributor on the Node side)**
- `hooks/useSimulation.ts:70`: `const stepBufferRef = useRef<Map<number, any>>(new Map())`
- Writes (`stepBufferRef.current.set(step, stepData)`) at line 569; **no in-run eviction**.
- The only `.clear()` is in a cleanup effect keyed on `simCode` (line 90) — i.e. it only purges when the **sim** changes, not within a sim.
- For a 1000-step sim where each `stepData` carries full persona array + timestamp + per-step payload, the Map ends a run with ~1000 entries. The exact size depends on payload weight; even at 0.5 MB/entry that's ~500 MB sitting in one Map at end-of-sim.
- This explains the **shape** of the growth: a single sim peaks high; V8 doesn't return that arena to the OS once allocated, so run 2 starts on top of run 1's high-water mark even though the buffer logically clears between sims.
- **Suggested fix:** evict entries with `step < currentStep - N` (N≈20–50 covers catch-up). Two-line change.

**B. No explicit texture eviction**
- `grep -rn 'textures.remove' scenes/ hooks/ lib/ components/` returns zero matches.
- `MainScene` preload (`scenes/MainScene.ts:247-359`) loads ~20 static tilesets + one atlas per persona (`load.atlas(personaName, ...)`).
- `game.destroy(true)` does clear Phaser's texture cache, but the underlying ArrayBuffers don't free immediately — they sit in the JS heap until the next major GC, and V8 won't shrink the heap. If sim 2 starts before that GC fires, both sets are resident briefly.
- Not the primary leak, but a non-trivial peak contributor (especially with roster turnover between sims).
- **Suggested fix (optional):** in `MainScene.shutdown` (before the implicit destroy), iterate `this.textures.list` and `this.textures.remove(key)` for the persona atlases specifically.

**C. Lingering Chromium (§3 suspect 4) — out of scope for FE**
- The "262 MB Chromium after run 1, persistent" almost certainly comes from the BE orchestration opening a Playwright page per step and not closing the previous one. WORKLOG `2026-05-15 — Frontend` already noted "the backend opens `new_page()` per step" — that's the same surface. **This needs a BE-side audit of `new_page()` lifecycle**, not an FE fix.

**D. Next.js dev mode HMR (§3 suspect 5) — likely the largest tax**
- HMR retains module graphs, source maps, server-side bundles across recompilations. In `next dev` this is normal and large.
- This is exactly why §4 question 1 ("dev vs `next build && next start`") is the most discriminating test we can run before touching code.

### Recommendation

Run §4 question 1 **before** any code change:

1. `next build && next start`, two back-to-back sims, Task Manager screenshots at the same checkpoints (after run 1 teardown / after run 2 teardown).
2. Heap snapshots in Chrome DevTools at the same three checkpoints §4 asks for, comparing the JS heap retainers — specifically watch for `Map` instances retaining `stepBufferRef` payloads.

**Expected outcomes:**
- If prod build flattens the curve (e.g. 5.7 GB → 6.0 GB instead of 5.7 → 8.3): the bulk is dev-mode HMR + V8 high-water mark. We deprioritize, document, and move on — production server won't run in dev mode anyway.
- If prod build still shows multi-GB growth: `stepBufferRef` eviction (A) is the next move; texture eviction (B) is the followup.

### What we already know without running the test

Two fixes are worth doing regardless of the dev-vs-prod result, because they're cheap and improve the worst case:
- **A. `stepBufferRef` rolling-window eviction** — two-line change, no behavior impact (catch-up path still works for the last N steps).
- Verify `useSupabaseCoords.ts` cleanup runs on early-return paths.

**Status:** investigation phase 1 done (static audit). Phase 2 is the dev-vs-prod runtime comparison.

## 8. Phase 2 — runtime comparison (2026-05-18, Nicolas, macOS)

### Setup

Repro on macOS 14 (M1, arm64). Same stack as Ivan's bug report: `double-front` FE serving `next-server` on :3000, `api_gateway` uvicorn on :8001, BE reverie loop driving Playwright headless against the FE.

- **Baseline sim:** `base_family_sim` (4 personas: Pistsov family). Ivan's reported sim was a `base_the_ville_*` variant which isn't present locally on this machine — `base_family_sim` was the next-closest baseline that was both available and viable (4 personas vs 0).
- **Steps per sim:** 200 (Ivan's lower bound).
- **Two sims back-to-back, same FE process** — sim B starts immediately after sim A's `COMPLETED.json` is written, no restart of `next-server` between them.
- **Memory metric:** `vmmap -summary` *Physical footprint* (RAM + compressed). Plain `ps rss` is unreliable on macOS because the kernel compresses idle pages aggressively, deflating RSS without the process actually releasing memory. Footprint counts the compressed pages, so it's the right thing to compare against Ivan's Windows Task Manager numbers.
- **Process measured:** `next-server` (the only Node process serving FE; the `next dev` wrapper that spawns it is a thin <100 MB shim and is excluded).

A trivial pre-existing TS error (`DebugAddressPanel.tsx:79`, `as Record<string, unknown>` cast without `unknown` intermediate) blocked the prod build and was fixed in place to unblock — that file is the only repo change from this investigation.

### Results

| Phase | Checkpoint | Footprint (actual) | Footprint (peak) | Δ vs pre-sim |
|---|---|---:|---:|---:|
| **dev** (`next dev`) | pre-sim (post-route-compile) | 1.6 GB | 2.1 GB | — |
| | post sim 1 (200 steps) | 1.7 GB | 2.1 GB | **+0.1 GB / peak flat** |
| | post sim 2 (200 steps) | 1.8 GB | 2.1 GB | **+0.2 GB / peak flat** |
| **prod** (`next build && next start`) | pre-sim (post-warmup) | 112 MB | 133 MB | — |
| | post sim 1 (200 steps) | 136 MB | 139 MB | **+24 MB / peak +6 MB** |
| | post sim 2 (200 steps) | 119 MB | 141 MB | **+7 MB net / peak +8 MB** |

Notes on the prod numbers: between sim 1 and sim 2 the actual footprint *dropped* from 136 MB → 119 MB while peak edged up only 141 MB — a GC clearly ran between runs and reclaimed memory, with peak essentially stable across both sims. That is the textbook shape of "no leak."

LLM cost across all 4 sims: ~$0.20 (1 548 LLM calls, `gpt-4o-mini`).

### Verdict

**Prod build flattens the curve. Hard.**

- Dev start-up alone is ~14× heavier than prod start-up (1.6 GB vs 112 MB) — that gap is the Next.js dev-mode HMR + module-graph + source-map state §3 suspect 5 called out, and it accounts for the majority of the absolute number Ivan saw on Windows.
- Prod growth across two back-to-back 200-step sims is **+8 MB peak / net negative on actual** — indistinguishable from noise. There is no residual per-sim accumulation in the FE Node process when run under `next start`.
- Dev growth across the same two sims on this machine was **+200 MB / peak unchanged**. Not zero, but ~13× smaller than what Ivan reported (+2 652 MB). The most likely cause for the macOS-Windows gap is the **dev-environment stack itself**, not a difference in OS memory accounting:
  - **Cursor IDE renderer / extension-host process leaks.** Cursor itself has publicly documented "slow-and-steady OOMs" where memory creeps up across a session because manually managed state isn't disposed of cleanly ([Cursor blog: app stability](https://cursor.com/blog/app-stability)). User reports of the renderer process hitting the ~4 GB Electron-on-Windows ceiling are common ([forum thread](https://forum.cursor.com/t/cursor-crashes-frequently-on-windows-renderer-process-exceeds-4gb-memory-possible-memory-leak/147231), [another](https://forum.cursor.com/t/cursor-memory-leak-7gb-ram-usage-makes-it-unusable-crashes-constantly/60625)).
  - **`ELECTRON_RUN_AS_NODE` in the integrated terminal.** Cursor sets `ELECTRON_RUN_AS_NODE=1` on terminals it spawns ([analysis](https://dredyson.com/the-hidden-truth-about-terminal-script-failures-in-cursor-ide-a-complete-insiders-guide-to-diagnosing-and-fixing-electron_run_as_node-issues/), [report](https://forum.cursor.com/t/major-issue-agent-terminal-set-electron-run-as-node/133805)). A `node` child started under that environment inherits Electron-side characteristics and is documented to grow several GB on its own, independent of the workload.
  - **Task Manager groups all `node.exe` into one line.** Windows Task Manager aggregates by executable name, not PID. So the "Node.js JavaScript Runtime 5,700 → 8,352 MB" line on Ivan's machine is the *sum* of every `node.exe` running: `next dev`, the TypeScript language server inside Cursor, ESLint, the `ELECTRON_RUN_AS_NODE` child(ren), plus anything else. The dev-server-only delta is almost certainly smaller; some of the growth is attributable to other Node processes that have nothing to do with the sim.
  - **WSL2 overhead.** Ivan's `VmmemWSL` growing +1.7 GB confirms the WSL2 VM is doing real work above and beyond the dev server — file watchers indexing the cross-OS-mounted project, internal WSL state, etc. This piece is *not* a reporting artefact, it is real allocation.
  - **Playwright / headless Chromium retention.** A well-documented bug: repeated `chromium.launch()` / `close()` does not fully release memory between runs ([Playwright issue 21079](https://github.com/microsoft/playwright/issues/21079), [Playwright issue 15400](https://github.com/microsoft/playwright/issues/15400)). This affects macOS too, but the absolute residual is smaller because macOS compresses idle pages and there's no Cursor / WSL2 stack stacked on top.

  Net: the Windows number is the **sum** of dev-server growth + IDE leak + WSL2 overhead + Chromium-headless residual, all of which collapse to zero impact on a production deploy that runs `next start` with no IDE in the loop.

### Heap snapshots — not captured

§7's recommendation included Chrome DevTools heap snapshots at three checkpoints to identify the top retainers (specifically to confirm or refute `stepBufferRef` as the #1 retainer). They were **not** taken in this run for two reasons:

1. The headless visualization is driven by Playwright's `chromium_headless_shell`, not a full Chrome with DevTools attached. Attaching DevTools to a Playwright-launched headless context per step isn't a 60-second tweak and would have substantially extended the run.
2. With prod showing flat growth, the urgency to identify a top retainer dropped — there's no leak in prod to chase down.

If the team still wants the heap-retainer breakdown for the dev case (to satisfy the original §4 question 2), the cheapest path is a small standalone repro that loads `/simulations/<code>?headless=true` in a regular Chrome with DevTools, drives Playwright-like step injection via a script, and snapshots at the three points. A few hours of work, not blocked by anything found here.

### Recommendation

**Deprioritize the FE memory work for production.** The bug as filed is a dev-environment artefact (HMR + IDE + WSL2 + headless Chromium retention), not a production leak. Concretely:

- **Production deployment is unaffected.** A long-running Railway/equivalent server will not run `next dev`, no IDE is in the loop, and there is no WSL2 layer. Prod start-up is ~120 MB, and back-to-back sims add a handful of MB at most. No process-restart cadence is needed for this reason.
- **The two §7 "do it anyway" fixes can stay on the regular backlog, not the critical path.** `stepBufferRef` rolling-window eviction is still cheap and correct for huge sims (5 000+ steps), but it is not preventing a prod incident.
- **For Ivan's dev ergonomics**, two workarounds will measurably lower the apparent footprint on Windows: (a) run `next build && next start` locally during long generation sessions, (b) launch the dev stack from a PowerShell or cmd shell *outside* Cursor so the dev-server `node.exe` isn't co-mingled with Cursor's own Node processes in Task Manager and isn't started under `ELECTRON_RUN_AS_NODE=1`. Worth offering as workarounds, not features.
- **Two tests on Ivan's side to formally close this out.** Both are cheap (~10 min each):
  1. Re-run the same `run_sim.sh <baseline> <new_name> 200` two-sims-back-to-back script under `next start` on Windows. Expected: flat growth, mirroring §8's macOS prod numbers.
  2. Re-run *once* under `next dev` but from a PowerShell or cmd shell *with Cursor fully closed*. Expected: the apparent "Node.js Runtime" delta in Task Manager drops by a large fraction relative to Ivan's original measurement — that drop is the IDE component being subtracted out. Confirms (or rules out) Cursor as the dominant amplifier.

**Status:** investigation phase 2 done. Recommend closing the bug as "dev-mode only / not a production leak" pending optional Windows re-run.

## 9. Follow-up — `stepBufferRef` rolling-window eviction (2026-05-18)

### Why we're landing this anyway

The §8 verdict ruled out a production leak, but the §7 audit had flagged `stepBufferRef` (`hooks/useSimulation.ts:70`) as growing without in-run eviction — a `Map<number, stepData>` that only purges when `simCode` changes. The reason §8's runtime measurements *didn't* surface this as a leak is that the experiment ran in **headless mode**, and in headless mode the FE bypasses `stepBufferRef` entirely (BE pushes step data through `window.__executeMovementsForStep`, never through the API fetch that populates the buffer). The buffer therefore stayed empty across the entire 4-sim run, hiding both the limitation and any potential fix.

The headless path being clean is the right answer for the prod server (which is headless-only). But the buffer is the active code path for a *human watching playback in a browser tab*, and for a long sim (5 000+ steps with the full persona payload at each step), an unbounded `Map` is the wrong default. So we're landing a cheap, behavior-preserving fix as a preventive maintenance item — **not** because it's blocking anything.

### Survival mode match

Ivan confirmed he runs his repros with Survival mode ON; §8's runs also had Survival on (the BE logged `SURVIVAL WAKE OVERRIDE` during both phases). Apples-to-apples confirmed; the macOS-vs-Windows gap in §8 is not explained by a workload difference.

### Fix

`hooks/useSimulation.ts`: added rolling-window eviction after each `stepBufferRef.current.set(step, stepData)`. Retains a ±50-step window around `currentStepRef.current` plus `lastGoodStepRef.current` (which is needed for the fallback path at line 617). Eviction only fires when the buffer exceeds a hard ceiling of 100 entries, so normal-play inserts stay O(1); only when the buffer overflows does it pay an O(N) sweep, and only on that single step.

No behavior change for:
- Catch-up loop (which only ever looks at recent steps).
- Rewind (`rewindToStep`, line 677) — if a target step is outside the window, the existing `pollingApi.isStepAvailable` + refetch path handles it.
- Fallback path (line 617) — `lastGoodStepRef.current` is explicitly retained.

### Test plan

Manual: open browser playback on a sim, scrub to step 500, then to step 1000, then back to step 500 — playback continues smoothly, no console errors. Buffer size never exceeds 100 entries.

No new automated test added: the existing fetch/cache behavior is unchanged; only the upper bound on size is. A test that exercises the ceiling would have to drive 100+ unique step fetches, which is out of scale for the unit-test surface here.

**Status:** fix landed in working tree, ready for review.
