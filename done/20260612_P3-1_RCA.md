## Verdict in one paragraph (plain language)

The double's "brain" stores the user's message correctly, but the double has no senses pointed at its own memory. The engine only notices things that physically appear on the map around the agent — and a chat from the user never appears on the map. On top of that, even if the message *were* noticed, the one mechanism that lets an agent change its plans mid-day (the "reaction" path) is switched off in our production configuration and, even when on, is built exclusively for agent-meets-agent encounters — a message from a human user doesn't fit its shape at any point. So the message sits in memory, perfectly stored, with no road from there to behavior. This is a missing design piece, not a broken one: nothing malfunctioned; the path simply was never built.

## Hypothesis verdicts (vs. the brief's ranked list)

### H1 — no trigger: **CONFIRMED, primary — and stronger than stated**

There is no code that converts a fresh `gwchat_` memory into a perceived event or reaction candidate (`grep gwchat reverie/` = 0 matches, re-confirmed). Perception reads *only* the spatial tile map:

- `perceive.py:129-180` — perceived events come exclusively from `maze.get_nearby_tiles(...)` → `tile_details["events"]`. No path reads `a_mem`.
- Worse, the chain has a **second independent break**: even a perceived event cannot trigger a reaction in production config. `plan.py:4497-4498` — `_should_react` returns `False` unconditionally when `OBSERVATION_PRIMARY=true` (our default; conversations were moved to the spatial-proximity ConversationManager, which is equally blind to non-spatial input). The brief's H1 ("never perceived") and this hard-disable are two breaks **in series**.
- Three further shape mismatches would silently drop a naively-surfaced chat event:
  - `plan.py:4384-4385` — `_choose_retrieved` deletes events whose subject is the persona itself; the injected row has `subject = persona_name`.
  - `plan.py:4506` — reaction requires `curr_event.subject in personas`; "User" is not a sim persona.
  - `plan.py:4480-4482` — the "chat" reaction mode is dead code (`return False` before `return "do other things"`); only `wait` survives.

### H2 — routine fast-path suppression: **CONFIRMED as latent; never actually reached in this run**

The `P2_ROUTINE_SKIP_REACTION_EVAL` gate (`plan.py:4455`) sits *behind* the `OBSERVATION_PRIMARY` return inside `lets_react`, so it never executed on 2026-06-12. It becomes load-bearing the moment a fix surfaces chats as percepts: the novelty scorer (`plan.py:2264-2318`) gives a mundane user message ≈ 0.50 (base 0.50; subject-self → no +0.20; no urgent keywords) — below the 0.60 threshold → `routine_light` → suppressed. The bomb message would score ≈ 0.85+ (urgent-keyword +0.35) and pass. **Fix implication: fresh external memories need a novelty floor ≥ threshold** — justified, since by construction they can never be in `latest_events`.

### H3 — retrieval scoping: **REFUTED as a cause** (one latent non-causal bug noted)

`gwchat_*` rows load cleanly at resume: node IDs are treated as opaque strings (no numeric parsing, no sort dependency); rows land in `seq_chat`, `id_to_node`, `kw_to_chat` with keywords and embedding intact (`associative_memory.py:141-237, 373-402`); RIR scoring would make a poignancy-7 same-day chat highly competitive (`retrieve_double.py:267-280`). The problem is that **no retrieval that could surface them ever runs mid-day**:

- The per-step perception retrieval (`retrieve.py:47-58`) fetches only relevant *events* and *thoughts* — chats are structurally excluded.
- Embedding retrieval (which *does* include `'chat'`, `retrieve_double.py:631`) runs only with focal points: conversation context, reflection insights, day-boundary planning (`plan.py:3275`) — none reachable from routine desk work.
- Latent bug (non-causal, fix-adjacent): `_try_load_from_supabase` does not carry the DB `node_id` onto the loaded node — `add_chat` renumbers it `node_N`. Harmless today; matters if the fix tracks processed rows by node ID.

### H4 — structurally no other route: **CONFIRMED**

- Exactly three things mutate `f_daily_schedule` after wake-up: task decomposition (`plan.py:3655` — refines, never redirects), `_create_react`/`_wait_react` schedule injection (`plan.py:4551` — unreachable per H1), and end-of-day sleep padding (`plan.py:3692`). Full replanning happens only at the day boundary (`plan.py:3329-3412`, gated on `new_day`).
- Reflection is also verified closed (beyond the brief): (a) the trigger only moves when *perceive()* adds events (`perceive.py:301`); Supabase-loaded rows never decrement it (`associative_memory.py` load mutates no scratch state); (b) focal-point generation draws from `seq_event + seq_thought` only — `seq_chat` is excluded (`reflect.py:449-463`); (c) post-chat reflection requires an in-engine conversation in progress (`reflect.py:712-786`).
- The engine has zero awareness of `last_generated_at` / `chat_dirty` / memory freshness — confirmed absent from `reverie/`.

## Proposed core fix (per binding constraints — for approval, not yet implemented)

**Concept: an "external inbox" pass — fresh externally-sourced memories become first-class percepts with a guaranteed reaction evaluation.** Generic over `meta.source` (today `gateway_chat`; any future injected type inherits it). No sim-code special cases, no new env flags, no new plumbing.

1. **Freshness, data-derived.** At persona load (and as a near-free in-RAM existence check per step), select associative-memory rows with an external `meta.source` newer than a `last_processed_external` cursor persisted in scratch (scratch already round-trips through Supabase, so the cursor survives chunk boundaries → idempotent across wakes).
2. **Surface as a perceived event.** Inject each fresh row into the `perceive()` output as an event node — `subject = "User"` (the *sender*, not the persona — this survives `_choose_retrieved`'s self-subject filter and reads correctly downstream), description from the chat content, real poignancy. It then flows through retrieve → plan like any sensory input, decrements the reflection trigger, and leaves a proper event-memory trail.
3. **A reaction branch that fits the type.** The existing react path is persona-vs-persona (wait/chat); a user message needs a **replan** reaction. Add an external-origin branch ahead of the `OBSERVATION_PRIMARY` return in `_should_react` (that flag's comment-documented purpose — suppressing the *persona-chat* fallback — is preserved): one LLM call — "given this message, does {persona} change their plans? → {no-change | insert activity, duration, location}" — and on change, reuse the existing `_create_react` machinery (`generate_new_decomp_schedule`) to splice the task into today's schedule. Novelty floor ≥ `P2_NOVELTY_THRESHOLD` for external fresh events by construction; `routine_light` semantics for spatial events untouched.
4. **Cost envelope.** Chat-free chunks: an in-memory check per persona-step ≈ zero LLM cost (telemetry-verifiable per acceptance criterion 4). Chunks with N fresh messages: N reaction-eval calls + one decomposition call on change — the same cost class as one native reaction.

**Test-first plan:** failing test reproducing P3-1 minimally (persona mid-routine; inject a `gwchat_` row; run the cognitive step; assert the schedule/action changes and an event node referencing the message exists) → implement → acceptance re-run per the brief (mundane + urgent message on a fresh `base_family_sim` fork, Naturalness Gate green vs `20260611-2`, suites green, no LLM inflation on chat-free chunks).

**Known design risks to watch:** (a) the dinner-style message must change *future* schedule slots, not just the current action — the replan splice must target the message's referenced time window; (b) duplicate triggering if the cursor write ever races a crash — cursor must be written through the same scratch-persist path as the step itself; (c) the H3 latent node-id bug should be fixed in passing **only if** the cursor design keys on node IDs (otherwise leave it — surgical-changes rule).
