# Backend Movement and Grounding Troubleshooting Report

## Purpose

This document summarizes the current backend troubleshooting findings for movement and location grounding in the `generative_agents-local` codebase.

This report is intentionally focused on:

- action-to-location grounding
- backend planning/runtime behavior
- spatial consistency between semantic destination and actual sprite position

It does **not** currently cover:

- conversation quality
- chat triggering
- utterance generation

Those are deferred on purpose to keep the investigation focused.

---

## Executive Summary

The backend is not failing primarily because the frontend pathfinding is broken.

The main weakness is earlier in the pipeline:

- the backend often grounds an action to a semantically weak or wrong location
- that bad grounding is then validated mechanically rather than semantically
- the runtime then executes it faithfully

The most important conclusions from code + artifacts are:

1. `spatial_memory` currently behaves like a hard planner constraint.
   If a sector/arena/object is missing there, the planner usually cannot choose it.

2. The active location-grounding implementation still uses a split prompt chain:
   - `sector`
   - `arena`
   - `object`

3. That split design has real costs:
   - 3 roundtrips instead of 1
   - context decreases across steps
   - errors accumulate
   - once `arena` is wrong, `object` is trapped downstream
   - the whole flow depends on fragile string matching

4. The monitoring output can be misleading.
   At least in Ivan's case, monitoring suggested the LLM saw multiple arena options, but the real prompt input had already been filtered to a single bad option.

5. The runtime allows a persona to be geometrically "in the right zone" while semantically standing on a tile with weak or degraded address meaning.
   This is especially visible in Luba's run.

6. Task-decomposition anchors exist, but today they behave more like semantic hints than hard spatial constraints.
   They are stored and propagated through the plan, but they do not strongly drive tile resolution or final grounding.

7. Some personas are clear failure cases, some are control cases.
   The system is not uniformly broken.
   - Ivan is the strongest repeated grounding failure
   - Luba is a mixed case with data/runtime issues
   - Katya is the healthiest control
   - Gosha is mostly coherent

8. The automated run report overstates semantic health.
   The movement pipeline can be stable while action/location coherence is still weak.

Bottom line:

- the core issue is mostly `Stage 2 / location grounding`
- not mainly FE pathfinding
- not mainly pure LLM randomness
- not mainly one isolated bug

It is a layered problem involving:

- poor or restricted option sets
- weak semantic validation
- implicit tree-based spatial memory
- degraded world-only address states
- and a prompt chain that loses context between steps

## What the Backend Actually Does

At a high level, the movement pipeline works like this:

1. The backend generates or continues an action.
2. The backend grounds that action to a semantic destination.
3. The backend converts that destination into a geometric `target_zone`.
4. The frontend/headless runtime performs the actual movement.
5. The backend records the actual resulting position.
6. The next step starts from the actual position, not just the planned one.

That distinction matters because the system has both:

- a semantic layer
- a geometric layer

Those layers are only partially aligned today.

---

## Critical Vocabulary

### `spatial_memory`

This is the persona's textual map of accessible places.

In the active path, the planner uses it to build the choice sets for:

- accessible sectors
- accessible arenas
- accessible objects

It is not just decorative context.
It materially controls what the LLM can choose.

### `address`

This is the semantic destination label, for example:

`the Ville:Dorm for Oak Hill College:kitchen:toaster`

It is the planner's intended destination.

### `target_zone`

This is a geometric bounding box derived from the validated address.

It is not a semantic address.
It is the area the runtime considers "close enough / in zone."

### `authoritative address`

This is the semantic address derived from the persona's **actual tile coordinates**.

It answers:

"Where is the sprite really standing right now, according to the map?"

### `anchor`

An anchor is a semantic hint attached to a task-decomposition subactivity.

Examples:

- `bedroom`
- `counter`
- `refrigerator`

Today this is mostly planning metadata, not a hard runtime constraint.

### `zone_anchor`

This is not the same as the textual anchor above.

`zone_anchor` is a real tile inside the chosen `target_zone`.
It is what the runtime actually uses to stabilize or guide in-zone behavior.

## The Current Spatial Memory Schema Is Weak

The real `spatial_memory.json` files are nested by depth, not by explicit typed keys.

Real shape:

```json
{
  "the Ville": {
    "Dorm for Oak Hill College": {
      "kitchen": [
        "toaster",
        "kitchen sink",
        "refrigerator",
        "cooking area"
      ],
      "common room": [
        "common room table"
      ]
    }
  }
}
```

This means:

- top level = world
- second level = sector
- third level = arena
- terminal list = objects

What it does **not** do:

- it does not explicitly label nodes as `sector`, `arena`, `object`
- it does not separate machine IDs from display labels
- it does not carry strong metadata like ownership, permissions, role semantics, confidence, or canonical identity

Why this matters:

- meaning is inferred from depth in the tree
- logic depends on human-readable strings
- renaming is dangerous
- filtering becomes string-fragile
- prompt generation inherits the schema's weakness

This is not a cosmetic issue.
It is a structural weakness in the grounding layer.

## How Action Grounding Works Today

The backend does **not** ask the LLM for one full structured destination object.

Instead, it uses three prompts:

1. `run_gpt_prompt_action_sector(...)`
2. `run_gpt_prompt_action_arena(...)`
3. `run_gpt_prompt_action_game_object(...)`

This chain is executed when a new action is grounded.

Important clarification:

These are **not** called progressively as the agent arrives.
The system does **not** do:

- choose sector
- travel there
- then choose arena
- then choose object

Instead, it usually resolves all three at grounding time, then the runtime tries to realize that destination.

The likely motivation visible in code is:

- strict short outputs
- easier parsing
- local fallbacks
- better format control

Evidence in code:

- `max_tokens = 15`
- schema-sensitive routing
- formatting-sensitive flags
- simple `_extract_braced_token(...)` parsing

This makes sense as a robustness strategy.

However, the operational downsides are now visible:

- 3 roundtrips instead of 1
- context decreases across steps
- errors accumulate
- if `arena` is wrong, `object` is trapped downstream
- string matching becomes a central failure point

Latency is almost certainly worse with 3 calls.
Token cost is not provably better or worse without measurement.

## Confirmed Code-Level Clarifications

### 1. `spatial_memory` behaves as a hard planner constraint

Confirmed:

- the active persona path loads `MemoryTree` from `bootstrap_memory/spatial_memory.json`
- I do not find an active call site switching personas into `GridBackedMemoryTree`
- sector, arena, and object prompts all draw from `persona.s_mem`

Practical meaning:

- if `Hobbs Cafe` is absent from Luba's `spatial_memory.json` in this run
- the planner usually cannot choose it

What is still not fully proven:

- whether that absence is intentional scenario design
- or incomplete/bad data for the run

But the implementation fact is clear:

the active planner is constrained by what the bootstrap `spatial_memory` exposes.

### 2. Luba's world-only `the Ville` states are not just JSON export noise

Confirmed:

- the problematic tiles are genuinely unlabeled in the map matrices
- they are walkable
- `maze.py` builds hierarchical addresses and always includes world-level address

Practical meaning:

- a walkable tile with no sector/arena/object naturally resolves to `the Ville`
- this is allowed by the current map/runtime combination

This does **not** prove the map was intentionally designed that way.
But it does prove the problem is deeper than export formatting.

### 3. There is no strong invariant between `target_zone` and real address

Confirmed:

- `target_zone` is built from a validated address and expanded `±2`
- action completion checks mainly whether the persona is inside the zone
- runtime validity checks also accept zone membership
- environment files log the actual address from actual coordinates

Practical meaning:

the system currently allows:

- "the persona is operationally in the correct zone"

while also allowing:

- "the exact semantic address of the current tile is degraded or weak"

This is a real design behavior, not just a logging issue.

### 4. Task-decomposition anchors are not hard spatial constraints

Confirmed:

- anchors are generated and validated
- they are stored in `subactivity_anchor`
- they propagate across subactivity runtime

Not found:

- an active `_resolve_anchor_to_tiles()` implementation
- a strong runtime path where textual anchors force address grounding or tile resolution

Practical meaning:

- the planner can know the semantic anchor is `bedroom`
- but the movement runtime will still operate on `target_zone` and `zone_anchor`
- not on a resolved tile set derived from the textual anchor

This is why anchors currently behave more like hints than true constraints.

## Case Study: Ivan Step 5

This is the cleanest single example of the current grounding failure.

### Action

The action is:

`turn off alarm and sit up in bed`

That action itself is not the problem.
It comes from task decomposition and semantically points to `bedroom`.

### Grounding result

The backend grounds it to:

`the Ville:Dorm for Oak Hill College:woman's bathroom:bathroom sink`

### Why this matters

This is not a frontend pathfinding mistake.
The wrong semantic branch is already chosen before FE execution.

### What actually happened

Sector:

- `Dorm for Oak Hill College`

Arena:

- monitoring suggests the broader accessible list contained:
  - `Klaus Mueller's room`
  - `Maria Lopez's room`
  - `woman's bathroom`

But the real prompt input was filtered before LLM call:

- room entries containing `"'s room"` were kept only if they matched the persona's last name
- Ivan is `Pistsov`
- `Klaus Mueller's room` and `Maria Lopez's room` were removed
- only `woman's bathroom` remained

So the real situation was:

- the monitor suggested optionality
- the real prompt was already effectively forced into bathroom

Then the object prompt only saw bathroom objects:

- `toilet`
- `bathroom sink`
- `shower`

At that point, `bed` was already unreachable.

### Why this is a strong diagnostic case

This proves the failure is not just:

- "the LLM chose something dumb"

It is also:

- observability mismatch
- backend option filtering bug
- semantically bad branch chosen before object resolution
- no semantic guard downstream to reject the absurd result

## Confirmed Bugs and Inconsistencies

These are the clearest backend issues supported by code and artifacts.

### 1. Prompt/monitor option mismatch

The monitor does not always show the exact filtered option set the prompt actually received.

Impact:

- corrupts troubleshooting
- makes the LLM look freer than it really was

### 2. Surname-based room filtering

The arena prompt filters `"'s room"` choices by last-name substring.

Impact:

- semantically wrong
- removes potentially relevant rooms
- relies on display-string matching instead of real identity/access metadata

### 3. Missing semantic guard for absurd action/place/object combinations

Today, if the final address exists in `maze.address_tiles`, it is usually allowed.

Impact:

- `sit up in bed` can validate as `bathroom sink`
- existence check is stronger than semantic plausibility

### 4. Anchor information is not enforced downstream

Task decomposition can provide useful anchors like `bedroom`, but grounding can ignore them.

Impact:

- semantically rich upstream data is wasted
- repeated collapse into semantically incompatible branches

### 5. World-only current address states erase prompt context

When a persona is on an unlabeled walkable tile, current semantic context degrades sharply.

Impact:

- later prompts may run with weak current-location context
- compounding downstream quality loss

### 6. Sector fallback can silently rewrite model intent

The planner sometimes replaces the model's sector choice with a fallback sector.

Impact:

- observability confusion
- harder debugging
- implicit hidden corrections

## Structural Weaknesses

These are not necessarily one-line bugs, but they materially weaken the system.

### 1. Split prompt chain with decreasing context

Sector sees more context than arena.
Object sees the least.

This is exactly the wrong direction if downstream choices depend on upstream semantics.

### 2. Human-readable strings are used as logical keys

Examples:

- `Klaus Mueller's room`
- `Dorm for Oak Hill College`
- `woman's bathroom`

This is fragile.

The system needs stronger separation between:

- canonical identity
- display label

### 3. `spatial_memory.json` is implicit rather than self-describing

The tree shape itself carries meaning.
There are no explicit typed node wrappers.

### 4. Geometric validity is allowed to dominate semantic validity

If a persona is in the right `target_zone`, the runtime may treat the state as valid even when the exact semantic tile meaning is weak.

### 5. Task decomposition and grounding are weakly connected

The system can generate semantically useful anchors upstream, then largely ignore them during actual grounding.

## Data / Map Modeling Gaps

Some issues are not purely prompt or runtime issues.

### 1. Missing semantically required sectors for certain personas

Example:

- Luba's run data lacks `Hobbs Cafe` in `spatial_memory`

This may be:

- a deliberate access restriction
- or a bad/incomplete bootstrap dataset

Code alone cannot decide the intended behavior.

### 2. Missing personal-room-like options for Ivan

Ivan's available dorm arenas are already poor for many bedroom-oriented actions.

If the option tree itself is semantically weak, prompt quality alone will not save the system.

### 3. Unlabeled walkable map fringe

Some walkable tiles have no sector/arena/object labels.

That creates legitimate semantic degradation in a system that later exports current address from exact coordinates.

## Important Difference Between Pipeline Stability and Semantic Correctness

The run report is directionally correct about one thing:

- the pipeline is stable

But that does **not** mean:

- the semantic grounding is healthy

The run can be:

- stable
- crash-free
- replayable
- FE-consistent

and still fail at:

- action/location coherence
- current location plausibility
- semantic consistency across steps

That distinction is essential.

This run should not be summarized as "movement is solved."
It should be summarized as:

- movement transport is relatively stable
- grounding semantics remain materially weak

## Recommended Priority Order Before Any Major Refactor

If the goal is safe progress, this is the recommended order:

1. Fix observability integrity.
   Make sure monitoring reflects the real prompt inputs and filtered option sets.

2. Remove or replace surname-based room filtering.
   This is fragile and semantically wrong.

3. Add obvious semantic guards.
   Example: bed-oriented actions should not validate to `bathroom sink` if better alternatives or replan paths exist.

4. Audit persona spatial memory and access data.
   Especially Ivan and Luba.

5. Audit map semantics near repeated degraded address coordinates.
   Especially Luba's world-only fringe tiles.

6. Decide the intended behavior for anchors.
   - hints only
   - or enforceable grounding constraints

7. Only after that, consider prompt-architecture changes.

## Recommendation on Prompt Architecture

I would not replace the split prompt chain unilaterally before confirming the intended grounding contract.

However, this is now a valid and serious design question.

A more robust direction would be a unified structured response, something like:

```json
{
  "sector": "...",
  "arena": "...",
  "object": "...",
  "movement_mode": "...",
  "reason": "optional"
}
```

Benefits:

- one coherent decision instead of three fragile chained ones
- easier consistency checking
- less error accumulation
- less dependence on inter-step context loss

This would not magically solve all issues by itself.
It would still need:

- better option sets
- canonical IDs
- semantic validation

But it would remove one important source of compounding error.

## Why Deterministic Replay Still Matters

Even without changing architecture yet, the investigation supports adding a backend LLM cassette / replay mode.

Reason:

- right now many backend experiments would also change LLM outputs
- that makes movement/grounding debugging noisy and expensive

The correct tool is:

- record all LLM responses once
- replay the backend against the same fixed responses

That allows:

- safe iteration on planning/runtime fixes
- apples-to-apples comparisons
- faster debugging without rerunning a fresh LLM-driven sim every time

This is especially useful before any prompt or grounding refactor.

## Final Technical Assessment

The strongest current diagnosis is:

### Primary issue

`Action -> location grounding` is the main weak point.

### Secondary issue

`In-zone geometric permissiveness` can hide or compound semantic degradation.

### Tertiary issue

The current representation layers are too weak:

- weak `spatial_memory` schema
- display strings as logical keys
- no strong semantic guardrails
- anchors not enforced as spatial constraints

This means the current failures are not best described as:

- "frontend bug"
- "movement engine bug"
- or "the LLM is just making random bad choices"

They are better described as:

- a grounding architecture problem
- amplified by weak data/modeling in specific personas/runs
- and masked by a pipeline that can still look operationally stable

---

## Practical Bottom Line

If the goal is to move safely and professionally:

- do **not** start with a broad movement-engine rewrite
- do **not** trust the optimistic report at face value
- do **not** reduce this to "prompts are bad"

Instead:

- treat Ivan and Luba as the primary forensic personas
- fix observability and obvious semantic bugs first
- clarify the intended contract for access rules, anchors, and zone/address invariants
- then decide whether to stay with the current split design or move to a unified structured grounding prompt

The investigation is already strong enough to justify small, surgical backend fixes.

It is **not** yet a good moment for a blind architectural rewrite without first deciding:

- what should be hard constraints
- what should be soft hints
- and what data/modeling assumptions are actually intended by the system design
