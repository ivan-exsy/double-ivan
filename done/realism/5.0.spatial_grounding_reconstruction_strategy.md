# Spatial Grounding Reconstruction Plan

**Author:** Nicolas Demaria  
**Date:** 2026-03-26  
**Status:** Draft for review

## Context

This plan is based on:

- the `20260325-3` system review
- the confirmed failure of the latest `20260326-1` patch
- the agreement with Ivan on 2026-03-26 that, if the patch does not hold, the next step should be a compact reconstruction plan for spatial grounding

The purpose of this document is to describe that reconstruction in a way that is simple, concrete, and implementation-oriented.

## Problem Summary

The current backend grounding path is still structurally weak.

The main issue is not just model quality. The larger issue is that semantic planning and spatial grounding are still not tied together through one canonical contract.

Today, the backend still allows this loop:

1. contextual decomposition produces structured information
2. that structure is degraded into tagged text
3. `_determine_action()` strips those tags back out
4. `generate_action_location()` makes a second semantic location decision from cleaned prose
5. runtime then derives movement state from that second result

That creates the exact failure we have been observing:

- the semantic plan is often reasonable
- the spatial grounding is often not
- the system can look more stable while still behaving semantically wrong

## Current State: What Is Broken

### 1. The absurd loop is still real

The current planner path still does semantic decomposition and then re-inferrs location from text again.

That is the core loop this plan is meant to remove.

### 2. Multiple sources of truth still exist

The same current action is effectively represented in several places:

- decomposition output
- tagged schedule rows
- `scratch.act_description`
- `scratch.act_address`
- `partial_state.action_progress`
- decorated transport strings such as `description = action @ address`
- runtime geometric state derived later from address strings

That means the system can disagree with itself in several different ways:

- planner text says one thing
- address string says another
- geometric target says another
- API returns a partially normalized version
- FE renders whichever representation reaches it first

### 3. The latest anchor short-circuit patch was directionally right, but still fragile

The patch improved the flow by trying to use the decomposition anchor before calling the location LLM again.

That was the right direction.

But it still failed for structural reasons:

- it resolves anchors mainly at `sector + arena` level
- many useful anchors are object-level anchors
- examples:
  - `home desk`
  - `library table`
  - `kitchen counter`
  - `file shelf`
- if arena-level resolution succeeds, object selection can still be semantically wrong

So the patch improved direction, but it did not establish a strong enough contract.

## Reconstruction Goal

Remove the prose-and-re-inference loop and replace it with one canonical backend contract for the current action.

The goal is **not**:

- to rewrite the entire cognition stack
- to replace the movement/runtime state machine with the LLM
- to build a giant action taxonomy

The goal **is**:

- one semantic planner decision
- one canonical current-action contract
- deterministic runtime derivation after that

## Core Proposal

Introduce one canonical planner contract for the current action.

The LLM should produce the semantic action and the intended resolved destination once.

The backend should then:

- validate the destination
- canonicalize it
- derive runtime execution state deterministically
- expose the same action contract consistently to API and FE

## Proposed Contract

Use an `ActionContractV1` as the canonical current-action record.

```json
{
  "action_id": "luba_2025-11-01_slot-03_sub-01",
  "action_description": "Review discovery documents at home desk",
  "duration_min": 15,
  "subactivity_mode": "in_place",
  "anchor_text": "home desk",
  "resolved_address": "the Ville:Dorm for Oak Hill College:Dorm Room 2:desk",
  "resolution_source": "llm_contract_v1",
  "action_family": "desk_work"
}
```

## Contract Notes

### `action_id`

This should be the stable lifecycle identity for the action.

It should be generated by the backend, not by the LLM.

It should come from stable planning context such as:

- persona
- date
- schedule slot index
- subactivity row index

The purpose of `action_id` is to prevent false lifecycle resets when wording changes but the logical action is still the same.

### `action_family`

This is optional but useful.

It should be a small controlled family label for heuristics, validation, and debugging.

Examples:

- `sleep`
- `desk_work`
- `study`
- `exercise`
- `meal_prep`
- `hygiene`
- `social`

This should **not** become a giant catalog of every possible action.

### `resolved_address`

This should be the canonical spatial identity for runtime and API.

It is more important than using separate `sector`, `arena`, and `object` as the primary contract fields.

Those can still be derived when needed.

## BE-First Scope

The first pass should stay backend-only.

That means:

- introduce the contract in planner/runtime code
- validate it through sim runs, replay, and API responses
- avoid adding new persistence coupling until behavior is confirmed stable

### Supabase Later

Once the contract is validated, selected fields can be persisted to Supabase if useful.

Likely later candidates:

- `action_id`
- `action_family`
- `resolved_address`
- `resolution_source`
- optional contract snapshot for replay/debugging

For now, Supabase should not be a prerequisite for the reconstruction.

## Analysis From Three Perspectives

## 1. Systems Architect

### What is good about this design

This is the right direction if the contract becomes the **canonical planner artifact**.

That means:

- semantic intent is decided once
- resolved destination is decided once
- runtime derives execution-specific fields afterward

This improves separation of concerns because:

- planning owns semantics
- runtime owns execution
- API/FE consume one consistent current-action record

### Key architectural constraint

The contract should **not** try to replace downstream runtime logic.

Fields like these should still be derived deterministically after the planner contract exists:

- `target_zone`
- `zone_anchor`
- `movement_mode`
- `stationary_intent`
- `authoritative_target_tile`

If those are pushed into the LLM contract, the design becomes more fragile, not cleaner.

### Main architectural risk

The main architectural risk is treating one LLM JSON response as if it were the entire runtime state.

That would collapse distinct responsibilities into one object and create a larger failure blast radius than necessary.

### Architectural conclusion

The proposed direction is correct **if** the single structured response becomes the canonical planner contract and runtime derivation remains deterministic.

It is **not** correct if the intention is to replace the runtime state machine with one prompt output.

## 2. Product Engineer

### What improves

The biggest win is contract clarity.

Right now, current-action state is scattered across too many representations.

This redesign would reduce developer tax by collapsing the action identity and destination into one planner-side contract instead of forcing fixes across:

- planner text
- runtime scratch fields
- API normalization
- FE cleanup

### Why this helps MVP work

This is strongly aligned with MVP because the main user-visible issue is still:

- action and location not matching

Solving that at the contract boundary gives more value than continuing to patch movement symptoms alone.

### Main DX risk

This only improves developer experience if it **replaces** the current multi-representation contract.

If it is added as one more layer on top of:

- tagged text
- legacy `act_*` fields
- decorated strings
- FE/API fallback cleanup

then DX gets worse, not better.

### Product conclusion

This is a good product-engineering move if scoped tightly to the current-action grounding boundary.

It should not be expanded into a whole-cognition refactor.

## 3. Failure Engineer

### Main likely breakpoints

#### A. False action resets

If lifecycle identity still depends on wording instead of `action_id`, harmless wording drift will reset:

- action timing
- progress tracking
- switch counters

That is why `action_id` is mandatory.

#### B. Partial migration drift

If the new contract is introduced but legacy mirrors keep being reconstructed differently, planner/runtime/API/FE will diverge again.

That is why compatibility mirrors must be explicitly kept in sync during the migration.

#### C. Monolithic failure blast radius

If one structured planner call is trusted blindly, one bad response can poison:

- action description
- duration
- mode
- destination
- lifecycle

That is why this plan still requires deterministic validation after the LLM response.

#### D. Under-specified runtime execution

If the new contract stops too early and runtime derivation is not rebuilt cleanly downstream, the most likely regressions are:

- false action switches
- frozen or jittery movement
- mismatched textual vs geometric state
- replay/API drift

### Failure conclusion

The design is viable, but only if:

- action identity is stable
- legacy mirrors stay aligned during migration
- deterministic validation remains in place

Without those safeguards, the likely failures will be subtle and hard to debug.

## Recommended Implementation Phases

## Phase A — Introduce the canonical action contract

- define `ActionContractV1`
- generate stable `action_id`
- keep contextual decomp rows structured
- stop using tagged text as the primary transport for current-action grounding

## Phase B — Integrate contract generation into `_determine_action()`

- generate the current action contract once
- use `resolved_address` as the canonical destination
- remove the second semantic location inference from the planner path

## Phase C — Derive runtime state deterministically

- derive `target_zone`
- derive `zone_anchor`
- derive `movement_mode`
- derive stationary/movement execution state

These remain backend runtime responsibilities.

## Phase D — Keep compatibility mirrors and validate

- backfill legacy fields from the canonical contract
- keep FE/API/replay stable during transition
- validate behavior in full sims before removing old mirrors

## Validation Criteria

The reconstruction should be considered successful only if all of these are true:

1. `resolved_address` always maps to a valid runtime address
2. if `action_id` is unchanged, `act_start_time` does not reset
3. non-sleep actions do not end up on `bed` unless explicitly justified
4. `/step` and `/details` expose the same action/address pair
5. textual action state and geometric execution state do not silently drift apart

## Debugging Requirements

For each persona/step, log:

- raw `ActionContractV1`
- validated `resolved_address`
- `action_id`
- `action_family`
- `resolution_source`
- derived `target_zone`
- derived `zone_anchor`
- whether a lifecycle reset happened

Without that, the migration will be much harder to validate safely.

## Main Risks

### 1. Overscoping

Trying to rewrite daily planning, movement, and transport layers all at once would create too much blast radius.

This should stay focused on the current-action grounding boundary.

### 2. Overtrusting one LLM response

One structured planner call is the right boundary.

Blind trust in its output is not.

Per-field validation is still required.

### 3. Underestimating current contract sprawl

Current-action state already leaks across planner, runtime, API, replay, and FE.

That means migration discipline matters as much as the planner redesign itself.

## Bottom Line

The reconstruction is viable.

The clean version is not:

- “one LLM call replaces the whole runtime”

It is:

- “one structured planner contract becomes canonical, and the backend derives runtime execution state deterministically from it”

That is the smallest clean architecture that fixes the root problem without pretending the rest of the runtime does not exist.
