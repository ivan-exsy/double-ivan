## 1. Problem Statement

### What the data shows

Sim 20260327-2 ran 180 steps with zero analyzer issues and strong improvements in chat density (2x) and activity variety (2x). But manual review found **96 persona-steps with wrong locations** — personas placed at nonsensical addresses for their current action.

| Cluster | Persona | Action | Anchor | Resolved to | Steps |
|---------|---------|--------|--------|-------------|-------|
| 1 | Gosha | Timed math section | `Oak Hill study carrel` | woman's bathroom | 60-94 (35) |
| 2 | Ivan | Prep breakfast | `dorm_kitchenette` | woman's bathroom | 107-119 (8) |
| 3 | Ivan | Dynamic warm-up | `dorm hallway` | woman's bathroom | 127-133 (7) |
| 4 | Ivan | Run loop around campus | `campus loop` | Dorm Room 1:desk | 134-169 (36) |
| 5 | Katya | Walk back toward dorm | `college quad path` | woman's bathroom | 170-179 (10) |

**96 / 720 total persona-steps = 13.3% error rate**, spanning 53% of unique steps.

### Where the breaks happen

The initial assessment attributed these to "LLM location suggestion quality." The RCA proves this is wrong. **The LLM location prompt is not being called for any of the 96 broken steps.** The contract-first path from Phase 5.1 short-circuits the LLM entirely via `_resolve_anchor_to_address()` — a deterministic keyword-scoring function that resolves anchor text to map addresses.

The resolution flow for broken steps:

```
Decomp LLM produces anchor "Oak Hill study carrel"
  -> _resolve_anchor_to_address() scores all addresses by keyword overlap
  -> "oak" and "hill" match in BOTH "Oak Hill College" and "Dorm for Oak Hill College"
  -> Tie broken by string length (longer = higher rank)
  -> "Dorm for Oak Hill College:woman's bathroom:bathroom sink" (66 chars) beats
     "Oak Hill College:library:library table" (48 chars)
  -> Contract locked with bathroom address for 35 steps
  -> LLM location prompt never fires
```

### Three bugs in the anchor scorer

**Bug 1 — Sector name collision.** "Dorm for Oak Hill College" contains the same tokens as "Oak Hill College." Any anchor mentioning "Oak Hill" scores both sectors equally. Tie-break by `len(address)` descending means the longer dorm-sector addresses always win. The correct answer (`library:library table`) ranks LAST because it has the shortest address string.

**Bug 2 — Exact token matching.** The scorer requires literal string equality. "kitchenette" does not match "kitchen." "carrel" does not match "library table." "hallway" matches no arena. When the meaningful tokens fail, only generic tokens like "dorm" contribute, and Bug 1 sends everything to bathroom.

**Bug 3 — Zero-match fallback.** For `"campus loop"` — neither token matches any address. The resolver returns `None`. The planner contract builder falls back to the persona's home desk instead of invoking the LLM.

## 2. Why Deterministic String Matching Cannot Win Here

The anchor text comes from an LLM decomposition call (`task_decomp_contextual_v1.txt`). The prompt asks for *"short anchor string (place/workstation/area/persona)"* — intentionally open-ended to produce natural, varied location hints.

The LLM will always be more creative than any keyword dictionary:

| Anchor the LLM produces | What it means | What the map calls it |
|--------------------------|---------------|----------------------|
| `Oak Hill study carrel` | library | `Oak Hill College:library:library table` |
| `dorm_kitchenette` | kitchen | `Dorm for Oak Hill College:kitchen:cooking area` |
| `campus loop` | park | `Johnson Park:park:park bench` |
| `college quad path` | outdoor area | `Johnson Park:park:park bench` |
| `reading nook` | library | `Oak Hill College:library:library table` |
| `breakfast counter` | kitchen | `Dorm for Oak Hill College:kitchen:cooking area` |

The bottom two haven't appeared yet but will. Every new persona, career type, or action style produces anchor text the string matcher has never seen. Fixes like fuzzy matching, stemming, or synonym tables make the matcher more complex without ever reaching semantic understanding. The problem is structural: **a keyword scorer cannot understand that "study carrel" means "library."**

Confidence gating (rejecting low-match results) would help these 5 cases but is whack-a-mole. Next run produces "writing desk" or "snack bar" and we're back here.

## 3. The Combined Approach: LLM + Contract

### Core insight

The simulation needs:
- **Non-deterministic action descriptions** — LLM generates varied, natural prose
- **Non-deterministic location selection** — LLM understands semantics ("study carrel" = library)
- **Deterministic asset constraint** — output must be a real map address
- **Deterministic persistence** — address locked for the action's duration

These are not in conflict. The LLM selects from a fixed menu; the contract locks the selection.

### Architecture

```
[1] Decomp LLM produces subtasks with natural-language anchors
      action: "Timed math section"
      anchor: "Oak Hill study carrel"
         |
[2] Location LLM receives anchor as PRIMARY signal + action as context,
    plus the FULL location tree as a menu
      "The agent planned to be at: Oak Hill study carrel.
       Activity: Timed math section.
       Available locations: [tree]. Pick sector | arena | object."
    Task is SEMANTIC MATCHING (anchor → closest location), not action→location inference.
         |
[3] Validation gate rejects any response not in valid_locations dict
      If LLM says "Oak Hill College | library | library table" -> valid, accept
      If LLM says "some hallucinated place" -> reject, retry (up to 3x)
      If all retries fail -> failsafe: persona home + bed
         |
[4] Contract locks the validated address for the action's duration
      ActionContractV1(resolved_address="the Ville:Oak Hill College:library:library table",
                       resolution_source="llm_location_v1", ...)
         |
[5] Monitoring logs the LLM input, output, and contract for traceability
```

### What changes vs. current system

| Component | Current (contract-first) | New (LLM + contract) |
|-----------|--------------------------|----------------------|
| Primary resolution | `_resolve_anchor_to_address()` keyword scorer | `generate_action_location()` LLM call |
| Anchor text | Input to string matcher | Primary signal to LLM prompt (semantic matching task) |
| Contract system | Locks string-matcher result | Locks LLM result (unchanged mechanism) |
| Validation | `build_action_contract` checks `address_tiles` | Same + LLM `__func_validate` checks `valid_locations` |
| Sleep guard | Deterministic, bypasses LLM | Unchanged — kept as-is |
| Park roaming | Post-resolution keyword fix | Unchanged — kept as-is |
| Monitoring | Logs anchor resolution | Logs LLM I/O + contract |
| Failsafe | Home:bed when scorer returns None | Home:bed when LLM retries exhausted (same) |

- **`_candidate_address_score()` and scoring infrastructure** — no longer on the critical path. Kept for potential diagnostic use but not called during normal resolution.

## 8. Long-Term Direction

The LLM + contract combination is the natural architecture for this system:

- **Actions** are generated by LLMs — non-deterministic, creative, varied
- **Locations** are resolved by LLMs via semantic matching — the decomp LLM says WHERE in natural language, the location LLM maps it to a real address from the fixed menu
- **Contracts** lock the selection for the action's duration — deterministic persistence
- **Validation** ensures the selection exists on the map — deterministic gate

The key architectural insight is the **two-stage LLM pipeline**:

```
Stage 1 (Decomp LLM, Tier B):  "What should the persona do, and where?"
  → produces creative action text + natural-language anchor
  → high context, high reasoning — understands persona goals

Stage 2 (Location LLM, Tier A):  "Match this place name to the menu"
  → anchor-primary semantic lookup against fixed location tree
  → low context, simple task — even nano handles it
  → validated against real addresses
```

This division of labor plays to each model tier's strength. The harder question (what+where) goes to the smarter model. The easier question (match to menu) goes to the cheaper model. Neither stage does open-ended action→location inference, which is where gpt-5-nano fails.

As the simulation adds new maps, personas, or location types, the only change needed is updating the location tree (spatial memory). The LLM handles the semantic mapping automatically. No keyword dictionaries, no scoring functions, no synonym tables.

The decomp anchors are the critical bridge — they carry the planning LLM's spatial intent forward to the location LLM in a form it can act on. The contract system locks the result. Both pieces contribute; neither is the sole resolver.

### Future optimization: single-call decomp+location

The two-stage pipeline (5B) calls the decomp LLM (Tier B) to produce anchors, then the location LLM (Tier A) to resolve each anchor to a map address. This is the right starting point — isolated retries, simple per-stage prompts, and clear traceability between anchor production and address resolution.

Once the two-call approach is validated, a natural follow-up is collapsing both stages into a single decomp call. The decomp prompt already receives the persona's spatial memory; it could also receive the full location tree and return validated `sector | arena | object` triples directly instead of free-form anchor strings. The location LLM stage would be eliminated entirely.

**Tradeoffs:**

| | Two calls (initial) | Single call (optimization) |
|--|---------------------|---------------------------|
| Tier A calls saved | — | ~60-100 per sim |
| Prompt complexity | Simple per stage | Decomp prompt grows by ~200 tokens (location tree) |
| Retry cost | Stage 2 retries are cheap (Tier A, 30 tokens) | Retry replays the full decomp (Tier B, ~300 tokens) |
| Validation | Stage 2 validates against `valid_locations` in isolation | Validation embedded in decomp output parsing — more fields to check per row |
| Debuggability | Anchor visible as intermediate artifact | No intermediate — harder to diagnose bad resolutions |

**Recommendation:** Implement the two-call approach first to establish the anchor-primary pattern and gather validation data. If anchor→address resolution shows >95% first-try success rate across 3+ sims, collapse to a single call. The architecture doesn't change — only the prompt boundary moves.

### Error 1: Ivan in Woman's Bathroom (Steps 85-90)

The chain of events, traced through artifacts:

**Step N (before 85):** Ivan walks through the dorm hallway. His `vision_r` covers nearby tiles.

`perceive()` at step N+1 (`perceive.py:60-77`): Scans all tiles within `vision_r` of Ivan's `actual_pos`. The woman's bathroom tiles are physically adjacent to the dorm hallway. `perceive()` has zero access control — it adds every visible tile to `persona.s_mem.tree`:
```
if i["arena"]:
    if i["arena"] not in persona.s_mem.tree[i["world"]][i["sector"]]:
        persona.s_mem.tree[i["world"]][i["sector"]][i["arena"]] = []
```
Ivan's `s_mem.tree` now contains `"woman's bathroom": ["toilet", "shower", "bathroom sink"]`.

**Decomp (Stage 1) at step 85:** `_build_location_tree_for_prompt(persona)` reads `persona.s_mem.tree` directly with no filtering. Ivan's decomp prompt now shows:
```
Dorm for Oak Hill College > man's bathroom: toilet, shower, bathroom sink
Dorm for Oak Hill College > woman's bathroom: toilet, shower, bathroom sink
```
The decomp LLM produces anchor `"bathroom sink"` — object-level, no arena qualifier.

**Location resolution (Stage 2) at step 85:** `generate_action_location()` builds its own tree with privacy filtering — but the filter only covers Dorm Room, 's room, Bedroom, etc. Bathrooms are not in the filter:
```
is_private_room = ("'s room" in arena or "Dorm Room" in arena
                   or "Studio Room" in arena or arena.startswith("Room ")
                   or "Bedroom" in arena)
```
Both bathrooms pass through. The location LLM receives `"Planned place: bathroom sink"` and a tree with both `man's bathroom: bathroom sink` and `woman's bathroom: bathroom sink`. It picks the wrong one.

**Contract locks it in:** `ActionContractV1` locks `resolved_address = "the Ville:Dorm for Oak Hill College:woman's bathroom:bathroom sink"` for 6 steps (85-90). No re-resolution possible.

`perceive()` confirms contamination: Ivan now physically walks to woman's bathroom. `perceive()` at step 86+ confirms it in his tree permanently.

**Root cause (3 factors, ordered by causal priority):**

1. `perceive()` has no access boundary — walking past a location permanently adds it to spatial memory, even locations the persona shouldn't "use" (other gender's bathroom, other people's rooms)
2. `_build_location_tree_for_prompt` has no filtering — it dumps raw `s_mem.tree` to the decomp prompt. Once `perceive()` contaminates the tree, the decomp LLM sees the wrong locations as "available"
3. Anchors lose arena context at the stage boundary — decomp says `"bathroom sink"` (object), but the disambiguation requires arena context (`"man's bathroom > bathroom sink"`). The location LLM can't distinguish because both arenas have the same object.

**Why a validation-layer fix fails:** A "gender guardrail" in the resolution layer would catch this specific case but not the underlying pattern. The next sim could have Ivan perceive Katya's "Dorm Room 3" (not filtered by privacy rules if `perceive` adds it early enough), or any other location that `perceive()` leaks into the tree.

### Error 2: Luba Stranded En Route to Cafe (Steps ~155-160)

The chain of events:

**Decomp:** Produces action `"call and text firms to propose meeting times"` with anchor `"Hobbs Cafe"`, mode `"social_touch"`, duration 6.

**Location resolution:** LLM resolves to `"the Ville:Hobbs Cafe:cafe:behind the cafe counter"`. The target zone is (76-83, 17-21).

**Contract start (step ~155):** Luba's `actual_pos` is (119, 49) — deep in the dorm area. Distance to cafe target zone: ~43 tiles in x, ~28 tiles in y.

**Movement over 6 steps (MAX_TILES_PER_STEP=6):**

| Step | Start pos | Actual pos | Distance to target |
|------|-----------|------------|--------------------|
| 155  | (119,49)  | (116,46)   | ~40 tiles          |
| 157  | (115,41)  | (109,41)   | ~33 tiles          |
| 159  | (103,41)  | (98,40)    | ~25 tiles          |

She's walking toward the cafe at ~5-6 tiles/step, but needs ~10 steps to arrive. The contract only lasts 6 steps. She never reaches the cafe. Every step triggers `emit_start_tile_fallback_outside_zone`.

**Root cause:**

The decomp/contract system is distance-blind. When assigning a location, it has no awareness of:
- The persona's current physical position
- The distance to the target location
- How many steps it takes to travel there vs. the contract duration

The decomp decides `"make phone calls at Hobbs Cafe"` without knowing Luba is 55 tiles away. The contract locks a 6-step duration, but travel alone requires 10+ steps. The activity never actually starts.

**Why a validation-layer fix fails:** You can't fix this by checking the resolved address — the address **IS** correct. The problem is structural: the planning stage doesn't account for physical distance.

---

### Systemic Pattern

Both errors share one structural theme: stages of the pipeline operate with incomplete context about each other.

| Stage              | What it knows                  | What it's missing                                      |
|--------------------|--------------------------------|--------------------------------------------------------|
| `perceive()`       | Visible tiles                  | Access boundaries (gender, ownership)                  |
| Decomp (Stage 1)   | Full unfiltered `s_mem.tree`   | Arena-level disambiguation; no current position       |
| Location LLM (Stage 2) | Filtered tree + object-level anchor | Arena context from decomp; distance to target          |
| Contract           | Locked address + duration      | Travel time to destination                             |

**Fix directions (root cause, not validation):**

**Fix A — Filtered decomp tree:** Replace `_build_location_tree_for_prompt(persona)` with a call to the SAME tree-building code used by `generate_action_location()` (lines 3048-3097 of `plan.py`). This ensures both stages see identical filtered locations. Extract the tree-building into a shared helper.

**Fix B — Arena-qualified anchors:** Update the decomp prompt to require `"arena > object"` format (e.g., `"man's bathroom > bathroom sink"` instead of `"bathroom sink"`). The location LLM then receives unambiguous arena context. This is the most impactful single change — it closes the information loss at the stage boundary.

**Fix C — Distance-aware contracts:** Before locking a contract, compute approximate travel distance from current position to target zone. Either: (a) add travel time to contract duration, (b) reject destinations beyond a distance threshold, or (c) add a "travel" phase prefix to the contract.

**Fix D — Perception access boundaries:** Add filtering to `perceive()` so it doesn't add gendered/private spaces to `s_mem.tree` that the persona shouldn't use. This is the deepest fix — it prevents the contamination feedback loop — but also the most complex, since `perceive()` currently has no concept of "should vs. shouldn't access."

**Recommended priority:**
1. **Fix A + B together** (same PR, same stage boundary) — closes both the tree inconsistency and anchor ambiguity. Highest impact, moderate complexity.
2. **Fix C** — addresses the distance-blind planning. Independent from A+B.
3. **Fix D** — hardens `perceive()` against contamination. Can be deferred if A+B eliminate the downstream symptoms.
