# Playback State Desync Troubleshooting Report

## Scope

This report documents a specific simulation playback issue observed in the UI:

- the selected persona card shows an action and logical location that do not match the sprite position currently visible on the map for the same playback step.

The main reproduced example is from simulation `20260319-5-anon-a-b-c`, using the browser URL:

- `/simulations/20260319-5-anon-a-b-c?step=25`

and the visible mismatch:

- `Katya Pistsova`
- card action: `Arrange materials and set up prototypes on library table`
- card location: `Oak Hill College, library, library table`
- visible sprite: still in a room/bathroom area on the other side of the map

This report focuses on understanding whether that mismatch comes from:

1. backend step data,
2. frontend playback logic,
3. persona-details API,
4. or a combination of the above.


## Executive Summary

The mismatch shown in the screenshot is real, but it is **not** supported by the raw backend artifacts for `step 25`.

The root cause is a **frontend/API state-source mismatch**:

- the map/canvas playback uses **step-specific movement data**
- the persona popover uses **persona details data**
- the persona details endpoint is **not step-aware**
- it returns a hybrid of:
  - final/current `scratch.json` action state
  - latest environment/coords state
  - memory/personality details

As a result, the UI mixes:

- the sprite position from one playback step
- with the action/location summary from a different simulation moment

This is a separate issue from the backend grounding/runtime problems already identified elsewhere.


## Main Finding

### The screenshot mismatch is a UI data-source desync

For `Katya Pistsova` at playback `step 25`, the raw simulation artifacts do **not** say:

- `Arrange materials and set up prototypes on library table`
- `Oak Hill College:library:library table`

Instead, they show that Katya is still associated with the bathroom/studio area.

At the same time, Katya's final `scratch.json` for the completed run does contain:

- `act_description = Arrange materials and set up prototypes on library table`
- `act_address = the Ville:Oak Hill College:library:library table`

This means the card can legitimately display `library table` if it is reading completed-state details, even while the playback step still shows Katya elsewhere.


## Evidence

### 1. Raw playback artifacts for `step 25`

In the run bundle `20260319-5-anon-a-b-c`, Katya at `step 25` is still tied to the bathroom/studio area:

- `movement/25.json`
  - `description = setting up her portable glue gun and starting to craft handmade Christmas gift prototypes @ the Ville:artist's co-living space:Studio Bathroom 1:bathroom sink`
  - `address_label = the Ville:artist's co-living space:Studio Bathroom 1:bathroom sink`

- `environment/25.json`
  - `address = the Ville:artist's co-living space:Studio Bathroom 1:bathroom sink`
  - `x = 21`
  - `y = 21`

These two files agree with each other.

### 2. Katya's `library table` action appears later, not in the 20s

Searching the run bundle shows that Katya's action:

- `Arrange materials and set up prototypes on library table`

appears in `movement/60.json` through `movement/69.json`, not in the `20-29` range.

This is consistent with the completed `scratch.json` state and inconsistent with the card shown at `step 25`.

### 3. Final `scratch.json` contains the later action state

In:

- `personas/Katya Pistsova/bootstrap_memory/scratch.json`

the completed run state includes:

- `act_description = Arrange materials and set up prototypes on library table`
- `act_address = the Ville:Oak Hill College:library:library table`
- `curr_time = November 01, 2025, 10:09:00`

This is clearly later than playback `step 25`.

### 4. The persona popover does not use step data

In the frontend, the popover fetches persona details independently:

- `double-front/app/simulations/[sim_code]/page.tsx`
  - `dispatch(fetchPersonaDetails({ simCode, personaName }))`

The popover then renders:

- `persona.actionDescription`
- `persona.actionAddress`

in:

- `double-front/components/PersonaCard.tsx`

This is not populated from the current step payload.

### 5. The persona details endpoint is not step-aware

The frontend calls:

- `GET /api/simulations/{sim_code}/personas/{persona_name}/details`

defined in:

- `api_gateway/app/api/routes/simulations.py`

That route delegates to:

- `SupabaseService.get_persona_detailed_info(...)`
- fallback `FileService.get_persona_detailed_info(...)`

The file-based implementation:

- reads `scratch.json`
- reads the highest-numbered `environment/*.json`
- returns that as persona details

It does **not** accept a `step`.
It does **not** reconstruct per-step action/location details.

Relevant file:

- `api_gateway/app/services/file_service.py`

The current logic explicitly finds:

- the latest environment file
- the completed/current `scratch.json`

which is correct for "latest persona profile" behavior but incorrect for step-accurate playback UI.


## Root Cause

### The UI is mixing two different temporal models

The system currently has two separate read models:

1. **Playback step model**
   - used by the canvas and movement playback
   - derived from `/api/simulations/{sim}/step/{step}`

2. **Persona details model**
   - used by the popover/card
   - derived from `/api/simulations/{sim}/personas/{persona}/details`
   - effectively current/final-state oriented

These two models are not guaranteed to represent the same simulation instant.

That is the core bug.


## Important Secondary Finding

### The step payload already contains enough data for a step-aware card

The step payload for personas already includes the fields needed to render step-accurate action/location information, including:

- `description`
- `address_label`
- `intent`
- `movement`
- `planned_pos`
- `start_pos`
- `target_zone`

This means the fix does **not** require inventing a new data model from scratch.

The step payload already carries the short-lived action/location information needed for playback-aligned rendering.


## What This Is Not

This is **not** evidence that:

- the backend step artifacts for `step 25` are wrong for Katya
- the screenshot is fake or user error
- the issue is only in the backend grounding layer

Instead, the evidence supports:

- the screenshot is showing a real UI inconsistency
- the inconsistency comes from using a non-step-aware details source during step playback


## Relation to Other Known Issues

This playback-card desync is a separate class of issue from:

- semantic grounding mismatches
- runtime fallback mismatches
- reachability overrides
- movement oscillation

Those problems still exist.
This report isolates a different failure mode:

- **presentation-layer temporal inconsistency**

In other words:

- backend may still be wrong in some cases
- but even when backend step data is internally consistent, the UI can still display a contradictory action/location summary if it reads from the details endpoint


## Recommended Fix Direction

### Recommended architecture

Use two different data sources intentionally:

1. **Stable profile data** from `persona details`
   - personality
   - memories
   - schedule
   - long-lived biography/state

2. **Step-volatile playback data** from the current step payload
   - current action
   - current action location
   - current visible location
   - movement/planned position

### Recommended UI rule

During playback or timeline scrubbing:

- the popover `Actions` tab should read from the current step buffer
- not from `/personas/{name}/details`

This should apply at minimum to:

- `Current Action`
- `Action Location`
- any "current" location or status labels

### Recommended API rule

If the UI still needs a details endpoint for playback, then it should become explicitly step-aware:

- `/personas/{persona}/details?step=25`

However, that is only worth doing if the frontend cannot reuse the already-available step payload.

Given the current system, the simpler and safer approach is:

- keep the existing details endpoint for stable profile data
- use step payload for step-specific action/location rendering


## Risk Assessment

### Low risk

- reusing step payload fields already present in the playback data
- switching card action/location rendering to the step buffer

### Medium risk

- extending the details endpoint to become step-aware
- mixing step reconstruction logic into the persona details service

### Higher risk

- trying to solve this by patching `scratch.json` semantics
- using final scratch state as if it were replay-safe

That would further blur the distinction between:

- current/final simulation state
- historical playback state

## Current Status

The issue is understood well enough to classify as:

- **confirmed**
- **reproducible**
- **root-caused at the frontend/API integration boundary**

The remaining work is implementation, not further diagnosis of this particular mismatch.


## Practical Bottom Line

The screenshot mismatch does not mean the step 25 backend payload for Katya is internally inconsistent.

It means the UI is showing:

- step-based sprite state
- plus non-step-based persona details

for the same visible frame.

That is why the popover can say:

- `Arrange materials and set up prototypes on library table`

while the sprite is still visibly at:

- `Studio Bathroom 1:bathroom sink`

The correct fix is to stop using completed/current persona details as the source of truth for playback-time action/location UI.
