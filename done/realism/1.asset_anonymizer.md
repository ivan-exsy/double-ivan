## Asset Anonymizer: Description and Implementation Details

### *High-Level Description*
- **Purpose**: The anonymizer generalizes assets to neutral, reusable identifiers (e.g., removing surnames or persona-specific references) while maintaining a mapping layer for simulation-specific associations. This enables:
  - **Anonymization**: Assets like rooms, objects, or locations are stripped of personal ties (e.g., "Klaus's dorm bedroom" becomes "Dorm bedroom #1") to avoid bias, improve scalability, and support multi-tenant reuse.
  - **Association Layer**: In a given simulation, sprites (personas) are dynamically linked to these generalized assets (e.g., assigning "Dorm bedroom #1" to Klaus in Sim A, but to Maria in Sim B). This allows the same underlying world assets to be repurposed without duplicating map data.
  - **Benefits**: Reduces maintenance (one canonical asset per type), enables fork isolation (per-sim assignments), and supports realism by ensuring movements/observations reference neutral semantics rather than persona-locked names.
- **Key Trade-Offs** (from SOT docs): 
  - **Pro**: Scalable for custom sims (e.g., `sot_lifecycle.md` requires per-sim asset provisioning as a gate).
  - **Con**: Introduces translation overhead (canonical ↔ display names) and potential bugs if mappings aren't enforced (e.g., the surname filter fallback).
- **When It Applies**: Primarily in Phase 8+ runtime (post-Supabase migration), affecting movement grounding (`sot_be-fe.md`), address resolution during planning/execution (`sot_realism.md`), and API retrieval (`sot_api.md`). It's not active in legacy/JSON-only modes.
- **Current Status**: Implemented but incomplete propagation (per your RCA). The generalized architecture exists in Supabase and resolver logic, but legacy filters (e.g., surname-based) cause mismatches, like restricting room access to name substrings instead of simulation assignments.

This design evolved from early realism phases (1-7 in `sot_realism.md`) where hardcoded names caused stalls/collapses, to Phase 8's neutral mapping for better multi-sim reuse.

### Implementation Details
The system is built around Supabase as the single source of truth (SOT), with backend resolution logic. No direct frontend involvement beyond consuming resolved addresses in playback/movement. Here's the breakdown:

1. **Core Components**:
   - **Supabase Tables (Data Layer)**: From `README.md` and `sot/index.md`:
     - `double.asset_catalog`: Stores canonical, anonymized assets (e.g., ID: "dorm_bedroom_1", display: "Dorm bedroom #1", type: "room", semantics: {walkable: true, capacity: 1}). This is the neutral registry— no surnames or persona ties.
     - `double.asset_assignments`: Per-simulation mappings (e.g., sim_code: "20260318-6", persona: "Klaus Mueller", asset_id: "dorm_bedroom_1", role: "living_area"). Enables reuse: same asset in multiple sims with different occupants.
     - Related: `double.address_translations` caches resolved addresses (canonical ID → display string) to avoid repeated queries.
     - Enforcement: RLS policies (via `supabase-rls` skill if needed) ensure per-sim isolation—no cross-sim leaks.
   - **AddressResolver (Logic Layer)**: In `reverie/backend_server/persona/memory_structures/` (inferred from `README.md` Phase 8 notes).
     - **Function**: Translates between canonical (anonymized) and display (simulation-specific) addresses. E.g.:
       - Input: Canonical "dorm_bedroom_1" + sim_context → Output: "Klaus's dorm bedroom" (display for prompts/UI).
       - Handles fallbacks: If no assignment, defaults to generic (e.g., "Dorm bedroom #1").
     - **Caching**: In-memory + Supabase `address_translations` for performance (sub-50ms lookups).
     - **Integration Points**:
       - Planning (`cognitive_modules/plan.py`): Uses resolver to ground actions to anonymized assets, then assigns per-sim.
       - Execution (`cognitive_modules/execute.py`): Resolves target_zone from canonical assets; reports actual_pos back to update assignments.
       - Memory (`sot_memory.md`): Stores observations using canonical IDs to avoid persona bias in retrieval.
     - **API Exposure** (`sot_api.md`): `/api/simulations/{sim_code}/sprite-manifest` returns assignment metadata (e.g., atlas URLs for generalized sprites like "f8.png" for anonymized characters).
   - **Bootstrap/Provisioning**: From `sot_lifecycle.md`:
     - During sim creation (`POST /api/simulations/`), auto-assign assets via `assignment_mode=auto` (deterministic, walkable validation).
     - Manual override: `POST /api/simulations/{sim_code}/assign-living-areas` for custom mappings.
     - Gates: 100% coverage (all personas assigned), walkability check (via `MazeSupabaseLoader`).

2. **Flow in Runtime** (Closed-Loop, per `sot_realism.md`):
   - **Step 1: Planning**: Backend generates intent (e.g., "go to bedroom"). Resolver queries `asset_catalog` for anonymized options, then `asset_assignments` for sim-specific (e.g., Klaus → "dorm_bedroom_1").
   - **Step 2: Grounding**: Convert to target_zone (geometric bbox from asset tiles in `maze_tiles`). Use canonical ID to avoid surname bias.
   - **Step 3: Execution**: Frontend (`sot_be-fe.md`) realizes movement on anonymized collision data (`maze_chunks`). Reports actual_pos, which updates assignment if needed (e.g., via proximity observations).
   - **Step 4: Writeback**: Supabase updates `asset_assignments` and `personas_coords`. Memory writes use canonical refs (e.g., "observed in dorm_bedroom_1").
   - **Replay**: Browser fetches resolved display names via API; no recomputation.

3. **The Surname-Based Filter Bug (Remnant Issue)**:
   - From your RCA report: This is a legacy filter in arena prompting (`run_gpt_prompt_action_arena` in `prompt_template/run_gpt_prompt.py`).
     - **Behavior**: Filters options like "'s room" by substring match on persona surname (e.g., keeps "Klaus Mueller's room" only for Klaus). This assumes hardcoded names, ignoring anonymized assignments.
     - **Impact**: Breaks generalization—e.g., Ivan can't access "Maria Lopez's room" even if assigned in sim, leading to wrong grounding (e.g., "sit up in bed" → "woman's bathroom").
     - **Why It Persists**: Forked from original code pre-Phase 8. Docs (`20260227_interesting.md`) note it as a "surname-based room filtering" fragility relying on display strings, not IDs.
     - **Fix Path**: Replace with `AddressResolver` lookup (query `asset_assignments` by sim_code/persona). Enforce via semantic guard in grounding (reject if resolved asset mismatches action semantics, e.g., bed action ≠ bathroom).

4. **Limitations and Gaps** (From Docs):
   - **Not Fully Enforced**: Anchors (e.g., "bedroom") are hints, not hard constraints—grounding can ignore them (`sot_realism.md` Phase 19-21 notes).
   - **Observability**: Monitoring (`monitoring/step_*.json`) shows filtered options, not full sets—masks issues (`BACKEND_MOVEMENT_GROUNDING_TROUBLESHOOTING_REPORT.md`).
   - **Data Gaps**: Some `spatial_memory.json` lack full catalogs (e.g., Luba missing "Hobbs Cafe"), degrading options.
   - **Phased Rollout**: Full anonymization requires `USE_GRID_OBJECTS=true` and `NEXT_PUBLIC_USE_MAZE_CHUNKS=true` (env flags in `README.md`).
   - **Testing**: Validate via 60-step runs (`sot_lifecycle.md` Naturalness Gate: check multi-venue spread, no single-address collapse).
