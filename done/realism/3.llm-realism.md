## **1. Schedule Index Off-by-One Bug**

### Problem
`get_f_daily_schedule_index()` in `scratch.py` returns the wrong schedule slot. It checks `elapsed >= today_min_elapsed` **before** adding the current block's duration, so any time that falls *inside* a block gets resolved to the **next** block instead.

Impact: Ivan (`wake_up_hour=10`, sim starts 09:00) should sleep for the first 60 steps but instead immediately executes his first post-sleep sub-action ("alarm off and stretch in bed"). Because the sleep block (600 min) overshoots minute 540, the index is stuck on the first sub-task and never advances — Ivan repeats "alarm off and stretch in bed" for the entire hour, re-querying the LLM for arena selection each time (which non-deterministically picks garden vs. dorm room).

All personas are affected (off by one sub-task), but it's only visible when the sleep block extends past sim start time.

### Fixed: 

The fix is a single logic change in `scratch.py:get_f_daily_schedule_index()` — duration is now added before the  comparison, and the check uses > instead of >=, so a time falling inside a schedule block correctly returns that block's index.


### Verified behavior
- Ivan at 09:00 correctly returns "sleeping" (index 0), wakes at 10:00
- Gosha/Katya/Luba schedule alignment corrected (minor shift, previously off by one sub-task)
- Late-drop personas (e.g., `wake_up_hour=14` into 09:00 sim) sleep correctly until their hour
- Boundary exact (sleep ends at minute N, time=N): correctly advances to next action

## **2. Unified Location Resolution: 3→1 LLM Call Collapse**

### Context

The address resolution pipeline in `plan.py:_determine_action()` makes 3 sequential LLM calls (sector→arena→object) to determine where a persona performs an action. This causes:
- Error cascading: wrong sector locks in wrong arena and object (Ivan sleeps at library sofa, Katya crafts at grocery shelf)
- Lost context: by the object call, the LLM has forgotten the action's semantics
- 3x latency/cost: three Tier A round-trips per action per persona per step

### Solution

Collapse into a single LLM call where the model sees the full location tree and reasons holistically about sector+arena+object. Sleep actions get a strong prompt-level default to living_area without hard-gating, preserving narrative alternatives like "napped at the library after studying late."

#### Files to Modify

| File | Change |
|---|---|
| `persona/prompt_template/v1/action_location_unified_v1.txt` | CREATE — new unified prompt template |
| `persona/prompt_template/run_gpt_prompt.py` | ADD `run_gpt_prompt_action_location_unified()` after line ~1654 |
| `persona/cognitive_modules/plan.py` | ADD `generate_action_location()` after line ~1895; MODIFY `_determine_action()` lines 2541-2576 |
| `persona/prompt_template/model_router.py` | ADD 1 line to `TIER_A_TASKS` |

Existing functions remain untouched as legacy fallback.

#### Key Prompt Design

- Prominently shows living area; sleep example maps to home bed
- Rule: "Match activity type to location type" (creative → studios/homes, studying → library)
- Response: `sector \| arena \| object` (exact names, no extras)
- Compact for Tier A (~650-850 tokens)

#### Integration

- Feature flag: `UNIFIED_LOCATION_RESOLUTION=true` (default)
- Builds filtered location tree (sectors → arenas → objects, excluding private rooms)
- Fallback: living_area + "bed" if validation fails
- Monitoring: Logs unified suggestions via `log_raw_ai_suggestion()`

#### Rollback

Set `UNIFIED_LOCATION_RESOLUTION=false` in `.env.local` → reverts to legacy 3-call path instantly.

## **3. Deterministic Sleep Guard**

### Issue: LLM Bias in Sleep Location Resolution

The Tier A LLM (gpt-5-nano) incorrectly resolves generic sleep actions (e.g., "sleeping") to non-home locations like a library due to few-shot example biases, ignoring the "prefer home for sleeping" rule. This occurs because the LLM overweights examples without sufficient context, leading to unrealistic movement (e.g., walking to campus for sleep).

### Applied Fix: Deterministic Sleep Guard

- **Logic**: In `persona/cognitive_modules/plan.py`'s `generate_action_location()`, add a pre-LLM guard that detects generic sleep via patterns (e.g., "sleeping", "nap") without location overrides (e.g., "library", "couch"). For matches, short-circuit to return the persona's home bed deterministically (derived from `living_area` sector/arena, scanning for "bed" object). Contextual sleep falls through to the unified LLM pipeline.
- **Edge Cases Handled**: Generic sleep → home; explicit locations (e.g., "nap at the cafe") → LLM; non-sleep actions unaffected.
- **Monitoring/Verification**: Guard activations logged in `monitoring/step_N.json` (e.g., `{"sleep_guard": true}`). Verify by running sim with sleep action, checking resolution to home dorm bed and no extraneous movement.

## **5. Final Touches (Sim 20260323-1): Post-Fix Validation and Regressions**

After applying prior fixes (4A–4D) and running 90 steps (09:00–10:29), cross-simulation analysis against baselines (20260320-3, 20260322-5) confirmed elimination of teleportation (6 → 0 events) and restoration of sub-task transitions (0 → 14). However, two regressions emerged (oscillating movement, location mismatches), plus a pre-existing duration bug. Initial placement was verified as correct with no changes needed.

### *5A. Arrival Transition Counter Stuck (Critical Regression) — FIXED*

- **Issue**: Personas (e.g., Ivan sleeping, Gosha at library) oscillate between tiles indefinitely, never reaching `stationary` mode. `stationary_intent` stays `false` due to arrival counter resetting prematurely after entering target zone, preventing `in_zone` → `stationary` transition after 3 steps for `in_place` subactivities.
- **Root Cause**: In `_check_movement_mode_transitions()` (planning and continuation logic), counter only increments for `travel_to_zone` mode; switches to `in_zone` trigger reset via else branch.
- **Fix**: Update conditions to `mode in ("travel_to_zone", "in_zone")` in `plan.py` (lines 3227, 3786). Counter now persists through `in_zone`, enabling proper expiry and `stationary` transition. Zone-patrolling personas (e.g., Katya) unaffected.

### *5B. Mid-Block Action Duration Overshoot (Medium Pre-Existing Bug) — FIXED*

- **Issue**: Actions starting mid-schedule block (e.g., Ivan's sleep at 09:00) use full block duration (600 min), projecting end at 19:00 instead of wake-up at 10:00 (only 60 min remaining).
- **Root Cause**: In `_determine_action()` (`plan.py:2672`), `act_dura` pulls total block duration without subtracting elapsed time from midnight.
- **Fix**: Post-extraction, compute block end by summing prior durations (`block_end_min`), then clamp `act_dura = min(act_dura, block_end_min - today_min_elapsed)` around line 2695. Ensures remaining time only (e.g., Ivan sleeps 60 min).

### *5C. Action Descriptions Reference Unvisited Locations (High Observation) — FIXED*

- **Issue**: 3/4 personas mention Hobbs Cafe in actions but never visit (e.g., Gosha orders coffee from library; Luba supervises cafe from dorm; Katya "heads to cafe" but stays in dorm for 56 steps). Unified location resolver works, but upstream schedules generate mismatched multi-location actions.
- **Root Cause**: (1) Profiles blend incompatible locations without time anchors (e.g., Luba's "paralegal right from cafe"). (2) Hourly schedule prompt lacks rule for single-location activities.
- **Fix**:
  - **Profiles (5C-A)**: Time-block spatially distinct roles in `scratch.json` (Supabase migration 20260323000001) — e.g., Luba: cafe 7–8 AM/6–9 PM, paralegal 8 AM–5 PM from home; Gosha/Katya: anchor cafe to noon/6 PM with explicit returns.
  - **Prompt (5C-B)**: Add "ACTIVITY RULES" to `generate_hourly_schedule_v2.txt`: Each activity at one location; no multi-location combos; travel as separate entry.

## **6. API Gateway hardenning (sim 20260323-4)**

### *Original Issue*
In simulation run 20260323-3, the API gateway (FastAPI on port 8001) froze completely at step 117 out of 130 planned steps, affecting all four personas (Gosha, Ivan, Katya, Luba). The gateway became unresponsive with no logs, errors, or tracebacks—simply hanging without crashing—while the backend simulation engine continued by queuing movement reports to a fallback pending.json file. Latency showed a bimodal pattern earlier (oscillating between 2ms fast responses and up to 1,500ms slow ones), but at step 117, it spiked to 12-second timeouts across all submissions, escalating to "connection refused" by step 126 as the uvicorn process stopped accepting TCP connections. Root causes included synchronous file I/O (e.g., JSON reads/writes for observations and movement reports) blocking the async event loop, especially in hotspots like pending.json handling and directory scans; compounding factors were unbounded in-memory growth (e.g., task lists, caches, queues without cleanup), per-request HTTP client creation exhausting connections, and lack of uvicorn safety limits like request caps or keep-alive timeouts. This blocked unattended long runs, limiting simulations to ~115 steps reliably.

### *Implemented Fixes and Verification*
To address the root cause, we offloaded all synchronous file operations to thread pools using asyncio.to_thread() in key files: simulations.py (wrapping observation queuing), websockets.py (movement report writes), and file_watcher.py (file reads and directory walks). For resource leaks, we introduced a shared httpx.AsyncClient singleton with connection limits (max 20), bounded task history to 200 entries with auto-pruning, TTL-based metadata caching (5-minute expiration, max 50 entries), and periodic cleanup of websocket background tasks every 30 seconds. Safety measures included uvicorn flags for max requests (10,000) and keep-alive timeouts (30 seconds), plus optional slow callback logging for future monitoring. Verification came from re-running a 200-step simulation (20260323-4) on the updated gateway: it completed fully without freezes, timeouts, or connection issues—contrasting the prior run's failure at step 117—and showed stable latency with zero analyzer-flagged problems. Overall behavior remained coherent (e.g., natural movement averaging 2.07 tiles/step, 44 chat steps), confirming the fixes resolved the deadlock without introducing regressions, though unrelated patterns like early stationary clustering persist for future tuning.
